Sau bài này bạn sẽ

  • Giải thích được vì sao Messages API là stateless và ứng dụng phải tự gửi lại toàn bộ lịch sử hội thoại.
  • Xây dựng đúng mảng messages với các vai user / assistant, dạng chuỗi hoặc mảng content blocks.
  • Viết system prompt có role prompting qua tham số system, và biết khi nào dùng mid-conversation system message.
  • Hiểu kỹ thuật prefill, giới hạn của nó trên các model mới và các cách thay thế được tài liệu khuyến nghị.
  • Viết một vòng lặp chatbot nhiều lượt bằng Python SDK, có quản lý lịch sử và bảo mật API key.

🔁Messages API là stateless

Theo tài liệu Using the Messages API: “Messages API là stateless, nghĩa là bạn luôn gửi toàn bộ lịch sử hội thoại lên API.” Claude không tự “nhớ” lượt trước. Mỗi request là một lần đọc mới từ đầu đến cuối mảng messages.

Trên Claude.ai, bạn thấy Claude “nhớ” câu hỏi trước. Đó là vì ứng dụng Claude.ai lưu lịch sử và gửi lại cho model ở mỗi lượt. Khi tự xây ứng dụng bằng API, chính bạn phải làm việc đó: lưu các lượt user và assistant, rồi nối thêm lượt mới vào cuối.

Ví dụ đời thường

Hãy hình dung Claude là một chuyên gia tư vấn qua thư, không giữ hồ sơ nào. Mỗi lần gửi thư hỏi tiếp, bạn phải kẹp kèm toàn bộ các thư trước (cả thư bạn hỏi lẫn thư chuyên gia trả lời). Nếu quên kẹp, chuyên gia sẽ không biết “cái đó” trong câu hỏi của bạn là gì.

Hệ quả thực tế của tính stateless

  • Token đầu vào tăng dần theo số lượt: lượt thứ 10 phải gửi cả 9 lượt trước. Trường usage.input_tokens trong response sẽ lớn dần. Ví dụ trong tài liệu: request một lượt có input_tokens: 12, request ba lượt có input_tokens: 30.
  • Bạn toàn quyền kiểm soát lịch sử: có thể cắt bớt, tóm tắt, hoặc chèn lượt assistant “tổng hợp” (synthetic). Tài liệu nói rõ: các lượt trước không nhất thiết phải do Claude sinh ra.
  • Lịch sử bị giới hạn bởi context window: các model hiện hành trong bảng Models overview có context window 1M token (theo tài liệu, kiểm tra ngày 2026-11-20). Hội thoại rất dài vẫn cần chiến lược cắt gọn.
  • Dễ mở rộng (scale): server của bạn không phải giữ “phiên” trên phía Anthropic. Bất kỳ instance nào có lịch sử đều tiếp tục được hội thoại.
100.000số message tối đa trong một request (Messages API reference)
1Mtoken context window của Opus 5.5 / Sonnet 5.5 / Haiku 5.5 (Models overview, 2026-11-20)
128Ktoken đầu ra tối đa (max output) của các model mới nhất, Messages API đồng bộ

Lưu ý – Message threads (beta)

Tài liệu có giới thiệu message threads đang ở dạng beta: API có thể giữ hội thoại để các request sau chỉ gửi message mới. Một thread hết hạn sau 5 phút kể từ request cuối và bị xóa không muộn hơn 1 giờ sau lần dùng cuối (theo tài liệu, kiểm tra ngày 2026-11-20). Trang Message threads ghi beta header message-threads-2026-08-12 và cho biết tính năng này không đủ điều kiện zero data retention. Bài này học mô hình mặc định là stateless. Muốn dùng threads, hãy đọc trang Message threads riêng vì đây là tính năng beta.

Mẹo thực chiến (Pro Tip)

Người dùng than “chatbot quên mất điều tôi vừa nói”? ⇒ Hãy kiểm tra trước hết xem code có nối lượt assistant trả về vào lịch sử trước khi gửi lượt user tiếp theo không. Đây là nguyên nhân phổ biến nhất. Nguyên nhân không nằm ở model.

💬Mảng messages và các vai user / assistant

Mỗi phần tử trong messages array là một object gồm role và content. Theo Messages API reference, model được huấn luyện để làm việc với các lượt xen kẽ user và assistant.

🧑

role: "user"

Lượt người dùng

Câu hỏi, dữ liệu, ảnh, tài liệu. Cũng là nơi chứa tool_result khi dùng tool.

✳️

role: "assistant"

Lượt của Claude

Câu trả lời trước đó của Claude (hoặc lượt tổng hợp do bạn viết). Nếu nằm cuối mảng thì trở thành prefill.

🎭

system (tham số top-level)

Lời nhắc hệ thống

Không phải phần tử của messages mà là trường riêng system. Dùng để đặt vai trò, quy tắc, bối cảnh.

🛎️

role: "system" giữa hội thoại

Chỉ dẫn hệ thống bổ sung

Một số model mới cho phép chèn message system sau một lượt user để bổ sung chỉ dẫn.

Quy tắc cần nhớ

  1. Xen kẽ vai – Viết user → assistant → user… Reference ghi: các lượt liên tiếp cùng vai sẽ được gộp thành một lượt. Vì vậy hai message user đứng liền nhau không gây lỗi, nhưng Claude sẽ đọc chúng như một lượt duy nhất.
  2. Lượt cuối thường là user – Lượt cuối là câu hỏi mới để Claude trả lời. Nếu lượt cuối là assistant thì đó là prefill (xem phần 5).
  3. content là chuỗi hoặc mảng – Chuỗi là cách viết tắt cho một khối text. Muốn gửi kèm ảnh, PDF hay tool result thì dùng mảng content blocks.
  4. Synthetic assistant message được phép – Bạn có thể tự viết lượt assistant, ví dụ để tạo ví dụ mẫu trong hội thoại hoặc khôi phục ngữ cảnh.
  5. Giới hạn số lượng – Tối đa 100.000 message mỗi request (Messages API reference, kiểm tra ngày 2026-11-20). Trên thực tế, context window thường chạm ngưỡng trước.
# Request 3 lượt – ví dụ trong tài liệu "Using the Messages API"
import anthropic

client = anthropic.Anthropic()  # tự đọc ANTHROPIC_API_KEY từ biến môi trường

message = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    messages=[
        {"role": "user", "content": "Hello, Claude"},
        {"role": "assistant", "content": "Hello!"},      # lượt trước của Claude (có thể là synthetic)
        {"role": "user", "content": "Can you describe LLMs to me?"},  # câu hỏi mới ở cuối
    ],
)
print(message.content[0].text)

Lỗi thường gặp
  • Chỉ gửi câu hỏi mới mà quên lịch sử. Claude trả lời như chưa từng nói chuyện với người dùng.
  • Lưu chỉ chuỗi text của response trong khi response có nhiều khối (ví dụ tool_use, thinking). Khi có tool hoặc thinking, hãy lưu nguyên response.content. Reference yêu cầu khối thinking / redacted_thinking phải được gửi lại nguyên vẹn, đúng thứ tự.
  • Đặt system prompt thành một message {"role": "system"} ở đầu mảng như thói quen từ API khác. Với Claude, chỉ dẫn từ đầu phải nằm ở tham số top-level system. Message system trong mảng không được là phần tử đầu tiên.

🎭System prompt và role prompting

System prompt được truyền qua tham số top-level system của Messages API. Reference cho phép hai dạng: một chuỗi, hoặc một mảng TextBlockParam ({"type": "text", "text": "..."}). Dạng mảng hữu ích khi bạn cần gắn cache_control cho từng phần (sẽ học trong bài Prompt caching).

Trang Prompting best practices của Anthropic (link “Giving Claude a role with a system prompt” trong syllabus hiện dẫn tới trang này) viết: “Đặt một vai trò trong system prompt giúp Claude tập trung hành vi và giọng điệu cho trường hợp sử dụng của bạn. Chỉ một câu thôi cũng tạo ra khác biệt.” Kỹ thuật này gọi là role prompting.

# Role prompting – ví dụ trong "Prompting best practices"
message = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    system="You are a helpful coding assistant specializing in Python.",  # vai trò
    messages=[
        {"role": "user", "content": "How do I sort a list of dictionaries by key?"}
    ],
)

Nên đặt gì vào system, gì vào lượt user?

🎭Tham số system

  • Vai trò, chuyên môn, giọng điệu (“Bạn là chuyên viên CSKH của ngân hàng…”).
  • Quy tắc áp dụng cho mọi lượt: định dạng trả lời, ngôn ngữ, phạm vi được/không được làm.
  • Bối cảnh cố định: mô tả sản phẩm, chính sách. Phần này ổn định nên dễ cache.
  • Lý do đằng sau quy tắc. Tài liệu khuyên giải thích vì sao để Claude khái quát tốt hơn.

🧑Lượt user

  • Yêu cầu cụ thể của lượt hiện tại.
  • Dữ liệu biến đổi theo từng request: văn bản cần tóm tắt, ảnh, tài liệu.
  • Nội dung do người dùng cuối nhập (không tin cậy). Không trộn nó vào system prompt.
  • Lời nhắc định kỳ trong hội thoại rất dài. Tài liệu gợi ý chèn vào lượt user thay cho prefill.

Mẹo thực chiến (Pro Tip)

Chatbot trả lời đúng nội dung nhưng giọng văn không hợp thương hiệu (quá dài, quá trang trọng) ⇒ thêm vai trò và yêu cầu giọng điệu vào system, kèm lý do (ví dụ: “hiển thị trên màn hình điện thoại”). Cách này hiệu quả hơn lặp lại yêu cầu ở mỗi lượt user.

Lưu ý – Đừng “hét” với model mới

Tài liệu nhận xét các model mới (ví dụ Claude Opus 4.5, Opus 4.6) bám system prompt sát hơn các thế hệ trước. Các câu kiểu “CRITICAL: You MUST…” có thể khiến model làm quá mức. Hãy viết bình thường, ví dụ “Use this tool when…”.

🧩Prompt templates & variables

Trong ứng dụng thật, bạn hiếm khi viết tay từng prompt. Bạn muốn Claude làm cùng một việc mỗi lần, chỉ có dữ liệu đầu vào là khác nhau. Tutorial của Anthropic gọi cách làm này là prompt template: tách khung cố định của prompt khỏi đầu vào biến đổi của người dùng, rồi thay đầu vào vào prompt trước khi gửi cho Claude.

🧱Phần cố định (template)

  • Vai trò, mục tiêu, ngữ cảnh.
  • Hướng dẫn từng bước, định dạng đầu ra.
  • Ví dụ mẫu (<examples>).
  • Được viết, review và đánh giá (eval) một lần, tái sử dụng nhiều lần.

🔣Phần biến đổi (variables)

  • Email, hợp đồng, câu hỏi, đoạn code… do người dùng hoặc hệ thống cung cấp.
  • Thay đổi theo từng request.
  • Đặt chỗ bằng placeholder như {{EMAIL}} hoặc {EMAIL} (f-string).
  • Luôn bọc trong thẻ XML để Claude biết biến bắt đầu và kết thúc ở đâu.

Vì sao dùng template?

  • Đơn giản hóa việc lặp lại: người dùng cuối không cần viết, thậm chí không cần nhìn thấy prompt đầy đủ. Họ chỉ điền biến (theo tutorial chương 4).
  • Một template có thể có bao nhiêu biến cũng được.
  • Dễ kiểm thử: cố định template rồi thay nhiều bộ biến khác nhau để chạy eval (bài 15).
  • Dễ quản lý phiên bản: sửa khung prompt ở một chỗ, mọi request đều được hưởng.

Tài liệu của Anthropic dùng placeholder dạng {{TÊN_BIẾN}} trong các ví dụ (vd {{ANNUAL_REPORT}}, {{PATIENT_RECORDS}}). Trong code Python, bạn có thể thay biến bằng f-string hoặc phương thức format(), như tutorial minh họa. Tên biến không bắt buộc theo quy tắc nào, nhưng tutorial khuyên đặt tên cụ thể, liên quan để template dễ đọc ngay cả khi chưa thay biến.

# Prompt template + variables bằng Python SDK
import anthropic

client = anthropic.Anthropic()  # đọc ANTHROPIC_API_KEY từ biến môi trường, không hard-code key

# Khung cố định: biến được đặt chỗ bằng {email}, nằm trong thẻ <email>
TEMPLATE = """Bạn là trợ lý chăm sóc khách hàng của một cửa hàng điện tử.

<email>
{email}
</email>

<instructions>
Viết lại email trong thẻ <email> cho lịch sự, chuyên nghiệp hơn.
Không thay đổi nội dung yêu cầu và các con số.
</instructions>

Đặt email đã viết lại trong thẻ <rewritten_email>."""

def rewrite(email: str) -> str:
    prompt = TEMPLATE.format(email=email)          # thay biến vào khung
    msg = client.messages.create(
        model="claude-sonnet-5-5",                # model ID theo Models overview, kiểm tra 2026-11-20
        max_tokens=2048,
        messages=[{"role": "user", "content": prompt}],
    )
    # Chọn content block theo type, không theo vị trí (thinking có thể bật mặc định)
    text = "".join(b.text for b in msg.content if b.type == "text")
    start, end = text.find("<rewritten_email>"), text.find("</rewritten_email>")
    if start == -1 or end == -1:
        return text                                # không thấy thẻ: trả nguyên văn để xử lý tiếp
    return text[start + len("<rewritten_email>"):end].strip()

print(rewrite("Show up at 6am tomorrow because I'm the CEO and I say so."))
Lưu ý về thinking và vị trí content block

Theo Prompting best practices: trên Claude Opus 5, Claude Sonnet 5.5, Claude Sonnet 5 và Claude Haiku 5.5, thinking bật mặc định khi bạn không truyền tham số thinking, nên phản hồi có thể bắt đầu bằng các block thinking. Vì vậy hãy chọn block theo type thay vì lấy msg.content[0], và chừa đủ max_tokens cho thinking. (Theo tài liệu, kiểm tra 2026-11-20.)

Mẹo thực chiến (Pro Tip)

Một bên thứ ba (khách hàng, form web) gửi nội dung để điền vào prompt ⇒ dùng prompt template. Phần hướng dẫn nằm cố định trong template (hoặc trong system), còn nội dung người dùng chỉ đi vào một thẻ XML riêng như <user_input>. Cách này vừa tránh nhầm lẫn, vừa giúp phần hướng dẫn nằm trong tầm kiểm soát của bạn.

📚Multishot prompting: dạy bằng ví dụ

Anthropic viết: ví dụ là một trong những cách đáng tin cậy nhất để điều khiển định dạng, giọng văn và cấu trúc đầu ra của Claude. Một vài ví dụ được chọn kỹ, gọi là few-shot hay multishot prompting, giúp tăng độ chính xác và tính nhất quán.

Tutorial chương 7 giải thích thêm về cách gọi tên. Số “shot” là số ví dụ trong prompt: zero-shot là không có ví dụ, one-shot là 1 ví dụ, còn few-shot hay n-shot là nhiều ví dụ. Ví dụ hiệu quả cho hai mục tiêu: ra đúng đáp án và đúng định dạng. Thay vì mô tả dài dòng giọng văn mong muốn, đôi khi đưa vài câu trả lời mẫu lý tưởng lại nhanh và hiệu quả hơn.

Structured

Ví dụ và thinking

Theo Anthropic, multishot examples vẫn có tác dụng khi bật thinking. Các ví dụ có lời giải trong prompt định hướng cách Claude tiếp cận bài toán tương tự trong chính các thinking block. Anthropic gợi ý trình bày mỗi ví dụ gồm bài toán, phương pháp áp dụng và đáp án mong đợi.

Mẹo thực chiến (Pro Tip)

Đầu ra của Claude đúng nội dung nhưng định dạng mỗi lần một kiểu ⇒ thêm 3–5 ví dụ trong <examples> có cùng định dạng. Nếu Claude bắt chước cả chi tiết không mong muốn của ví dụ (cùng độ dài, cùng chủ đề, cùng cách mở đầu) ⇒ làm ví dụ đa dạng hơn.

Lỗi thường gặp
  • Ví dụ giống hệt nhau: cả 3 ví dụ đều là email ngắn và đều thuộc nhóm B, nên Claude có xu hướng nghiêng về B.
  • Trộn ví dụ vào hướng dẫn không có thẻ, khiến Claude tưởng ví dụ là dữ liệu cần xử lý.
  • Ví dụ sai định dạng hoặc có lỗi: Claude nhạy với khuôn mẫu, sẽ lặp lại cả lỗi của ví dụ.
  • Sao chép nguyên kỹ thuật “prefill <individuals> ở lượt assistant” từ tutorial cũ (viết cho Claude 3) sang model mới. Từ Claude 4.6, prefill ở lượt assistant cuối trả lỗi 400.

🧪Thực hành

  1. Bài tập 1 – Chứng minh API stateless. Gửi hai request riêng biệt tới claude-haiku-5-5. Request 1: "Tên tôi là Lan.". Request 2 (mảng chỉ có 1 message): "Tên tôi là gì?". Sau đó gửi request 3 có đủ 3 lượt: user (Tên tôi là Lan) → assistant (câu trả lời của request 1) → user (Tên tôi là gì?).
    Kết quả mong đợi: request 2 không biết tên; request 3 trả lời “Lan”. So sánh usage.input_tokens của request 2 và 3: request 3 lớn hơn vì chứa lịch sử.
  2. Bài tập 2 – Role prompting. Dùng cùng câu hỏi "Giải thích recursion" với ba system prompt: (a) không có system; (b) "Bạn là giáo viên tiểu học, giải thích cho học sinh lớp 5."; (c) "Bạn là kỹ sư Python cấp cao, trả lời bằng code và tối đa 3 câu giải thích.".
    Kết quả mong đợi: ba câu trả lời khác hẳn nhau về độ dài, từ vựng và ví dụ. Ghi lại nhận xét: chỉ một câu vai trò đã đổi giọng điệu.
  3. Bài tập 3 – Chatbot có giới hạn lịch sử. Chạy chatbot.py ở phần 7 với MAX_TURNS = 2. Ở lượt 1 nói “Mã đơn của tôi là MB-118”. Hỏi thêm 3 câu khác, rồi hỏi “Mã đơn của tôi là gì?”.
    Kết quả mong đợi: Claude không còn biết mã đơn vì lượt đầu đã bị cắt. Sau đó cải tiến: khi cắt, gọi Claude tóm tắt các lượt bị bỏ và nối bản tóm tắt vào system. Kiểm tra lại thì Claude nhớ được mã đơn.
  4. Bài tập 4 – Thay prefill. Cho đoạn code cũ dùng prefill {"role": "assistant", "content": "{"} để ép JSON. Gửi tới claude-opus-5-5 và quan sát lỗi 400. Viết lại: bỏ lượt assistant cuối; thêm vào system: “Chỉ trả về JSON hợp lệ theo dạng {"sentiment": "positive|negative|neutral"}, không có lời dẫn.” Rồi json.loads kết quả, kèm retry khi parse lỗi.
    Kết quả mong đợi: request thành công, parse được JSON. (Ở bài Structured outputs bạn sẽ dùng cách đảm bảo schema chặt chẽ hơn.)

Tóm tắt ghi nhớ

Key takeaways
  • Messages API stateless: mỗi request phải chứa toàn bộ lịch sử; input_tokens tăng theo số lượt.
  • messages gồm các lượt user / assistant xen kẽ; lượt cùng vai liên tiếp được gộp; tối đa 100.000 message/request.
  • content là chuỗi (viết tắt của một khối text) hoặc mảng content blocks: text, image, document, tool_use, tool_result, thinking…
  • System prompt dùng tham số top-level system (chuỗi hoặc mảng text blocks). Role prompting: chỉ một câu vai trò cũng đổi hành vi và giọng điệu.
  • Mid-conversation system message (role: "system" sau một lượt user) bổ sung chỉ dẫn mà không phá cache. Không được đứng đầu mảng; chỉ có trên một số model (không có trên Sonnet 5).
  • Prefill (lượt assistant cuối mảng) trả lỗi 400 trên Claude 4.6 trở về sau và Mythos Preview. Thay bằng structured outputs, chỉ dẫn trong system prompt, hoặc chuyển phần tiếp nối vào lượt user.
  • Lịch sử lưu ở phía server của bạn, cắt theo cặp lượt hoàn chỉnh; nội dung người dùng đặt trong lượt user, không ghép vào system; API key chỉ đọc từ biến môi trường.

Thuật ngữ (Glossary)

Stateless API
API phi trạng thái – server không lưu hội thoại giữa các request; ứng dụng phải gửi lại toàn bộ lịch sử.
Multi-turn conversation
Hội thoại nhiều lượt – chuỗi các lượt user/assistant nối tiếp nhau trong mảng messages.
Messages array
Mảng tin nhắn – tham số messages, mỗi phần tử gồm role và content.
Role (user / assistant)
Vai – ai “nói” trong lượt đó: người dùng/ứng dụng (user) hay Claude (assistant).
Turn
Lượt – một message của một vai; các lượt cùng vai liên tiếp được gộp làm một.
Content block
Khối nội dung – phần tử có type (text, image, document, tool_use, tool_result, thinking…) trong content.
System prompt
Lời nhắc hệ thống – tham số top-level system chứa vai trò, quy tắc, bối cảnh áp dụng cho cả hội thoại.
Role prompting
Gán vai trò – đặt vai trò cho Claude trong system prompt để định hướng hành vi và giọng điệu.
Mid-conversation system message
Tin nhắn hệ thống giữa hội thoại – message role: "system" chèn sau một lượt user; được ưu tiên hơn system cho các lượt sau và không làm mất cache phía trước.
Prefill
Điền trước câu trả lời – lượt assistant viết dở ở cuối mảng để Claude viết tiếp; không hỗ trợ trên Claude 4.6 trở về sau (lỗi 400).
Synthetic assistant message
Lượt assistant tổng hợp – lượt assistant do nhà phát triển tự viết (không do Claude sinh), được phép trong lịch sử.
Context window
Cửa sổ ngữ cảnh – tổng token model xem được trong một request (gồm system, lịch sử, đầu ra).
Message threads (beta)
Luồng tin nhắn – tính năng beta cho phép API giữ hội thoại để request sau chỉ gửi message mới.
Sliding window
Cửa sổ trượt – chiến lược chỉ giữ N lượt gần nhất của lịch sử.

Câu hỏi luyện tập

Một startup ra mắt chatbot tư vấn bảo hiểm bằng Messages API. Người dùng phản ánh: hỏi “Gói đó giá bao nhiêu?” ngay sau khi Claude giới thiệu gói Vàng thì Claude hỏi lại “Bạn muốn hỏi gói nào?”. Nguyên nhân khả dĩ nhất là gì?
  1. Model quá nhỏ nên không đủ trí nhớ dài hạn; cần đổi sang model lớn hơn.
  2. Thiếu tham số session_id để API liên kết các request.
  3. Ứng dụng chỉ gửi câu hỏi mới mà không gửi lại các lượt trước (gồm câu trả lời giới thiệu gói Vàng).
  4. System prompt quá dài nên đẩy lịch sử ra khỏi context window.
Đáp án C. Messages API stateless: ứng dụng phải gửi toàn bộ lịch sử ở mỗi request. A sai: model nào cũng không “nhớ” giữa các request; vấn đề nằm ở dữ liệu gửi lên. B sai: Messages API không có tham số session_id để giữ hội thoại. D sai: các model hiện hành có context window 1M token; một system prompt thông thường không thể đẩy hai lượt hội thoại ra ngoài.
Những phát biểu nào đúng về mảng messages của Messages API? (Chọn 2)
  1. Các lượt liên tiếp cùng vai được gộp thành một lượt.
  2. Mọi lượt assistant trong lịch sử phải là đúng nguyên văn do Claude sinh ra, nếu không API trả lỗi.
  3. Chỉ dẫn hệ thống áp dụng từ đầu hội thoại được đặt bằng một message {"role": "system"} ở vị trí đầu tiên.
  4. content có thể là chuỗi hoặc một mảng content blocks.
  5. Mỗi request chỉ chứa tối đa 100 message.
Đáp án A, D. Reference ghi các lượt cùng vai liên tiếp được gộp; content là chuỗi (viết tắt cho một khối text) hoặc mảng blocks. B sai: tài liệu cho phép synthetic assistant message. C sai: chỉ dẫn từ đầu dùng tham số top-level system; message system trong mảng không được đứng đầu. E sai: giới hạn là 100.000 message mỗi request.
Đọc đoạn code sau. Request thứ hai sẽ gặp vấn đề gì? 
history = [{"role": "user", "content": "Dịch sang tiếng Anh: Xin chào"}]
r1 = client.messages.create(model="claude-opus-5-5", max_tokens=256, messages=history)
history.append({"role": "user", "content": "Giờ dịch sang tiếng Nhật"})
r2 = client.messages.create(model="claude-opus-5-5", max_tokens=256, messages=history)
  1. API trả lỗi 400 vì hai lượt user đứng liền nhau.
  2. Không lỗi; hai lượt user được gộp thành một, nhưng Claude không thấy câu trả lời của r1 trong lịch sử.
  3. API tự lấy câu trả lời r1 chèn vào giữa vì nó nhớ request trước.
  4. Request lỗi vì thiếu tham số system.
Đáp án B. Code quên history.append({"role": "assistant", "content": r1.content}). Theo reference, lượt cùng vai liên tiếp được gộp nên không lỗi, nhưng lịch sử thiếu lượt assistant. A sai: lượt liền nhau được gộp, không bị từ chối. C sai: API stateless, không nhớ r1. D sai: system là tùy chọn.
Một công ty luật muốn trợ lý luôn trả lời với vai “chuyên viên pháp chế, trích điều luật, giọng trang trọng” trong mọi lượt hội thoại. Cách triển khai phù hợp nhất?
  1. Thêm câu “Hãy đóng vai chuyên viên pháp chế” vào đầu mỗi câu hỏi của người dùng ở phía frontend.
  2. Đặt lượt assistant cuối mảng là “Theo quy định pháp luật,” để ép giọng văn.
  3. Hạ temperature xuống 0 để câu trả lời trang trọng hơn.
  4. Đặt vai trò và yêu cầu giọng điệu trong tham số top-level system.
Đáp án D. Tài liệu: đặt vai trò trong system prompt giúp Claude tập trung hành vi và giọng điệu; chỉ một câu cũng tạo khác biệt. A sai: lặp ở mỗi lượt user tốn token, dễ thiếu sót, và trộn chỉ dẫn với nội dung người dùng. B sai: đó là prefill, trả lỗi 400 trên Claude 4.6 trở về sau. C sai: temperature không được hỗ trợ trên Claude 4.7 trở về sau, và nó cũng không quyết định vai trò hay giọng văn.
Sau khi nâng cấp từ một model đời cũ lên claude-sonnet-5-5, request phân loại cảm xúc bắt đầu trả lỗi 400. Mảng messages kết thúc bằng {"role": "assistant", "content": "Sentiment: "}. Cách xử lý được tài liệu khuyến nghị là gì?
  1. Bỏ prefill; dùng structured outputs hoặc một tool có trường enum chứa các nhãn hợp lệ.
  2. Chuyển lượt assistant đó thành message role: "system" đứng ngay sau.
  3. Thêm header beta để bật lại prefill.
  4. Đặt max_tokens: 1 để model chỉ sinh một token.
Đáp án A. Mục “Migrating away from prefilled responses”: với phân loại, dùng tool có enum hoặc structured outputs. B sai: message system không thay được vai trò “mớm lời” của prefill, và thứ tự đặt sau lượt assistant không phù hợp quy tắc vị trí. C sai: tài liệu không nêu header nào bật lại prefill. D sai: max_tokens không giải quyết lỗi 400 do prefill.
Một agent review code đã chạy 30 lượt với prompt caching. Đến lượt 31, nhóm muốn thêm quy tắc “mọi gợi ý phải có type annotation” mà không làm mất cache. Model đang dùng là claude-opus-5-5. Nên làm gì?
  1. Sửa chuỗi tham số system, thêm quy tắc vào cuối.
  2. Đặt quy tắc vào lượt assistant cuối mảng dưới dạng prefill.
  3. Thêm message {"role": "system", ...} ngay sau lượt user mới nhất.
  4. Bắt đầu hội thoại mới, chỉ gửi quy tắc trong lượt user đầu tiên.
Đáp án C. Mid-conversation system message được nối vào cuối nên prefix cũ vẫn khớp cache; Opus 5.5 có hỗ trợ. A sai: sửa system thay đổi các byte đầu nên vô hiệu cache phía sau. B sai: prefill trả lỗi 400 trên model này. D sai: mất toàn bộ ngữ cảnh 30 lượt.
Nhóm bảo mật review một chatbot nhiều lượt. Những thực hành nào phù hợp? (Chọn 2)
  1. Nhúng API key vào JavaScript frontend để gọi Claude trực tiếp từ trình duyệt cho nhanh.
  2. Đặt quy tắc vận hành trong system, còn văn bản người dùng nhập thì để trong lượt user (có thể bọc thẻ XML).
  3. Ghép trực tiếp chuỗi người dùng nhập vào system prompt để Claude coi trọng hơn.
  4. Gửi email khách hàng vào metadata.user_id để dễ tra cứu.
  5. Lưu lịch sử hội thoại chuẩn ở phía server thay vì tin toàn bộ lịch sử do client gửi lên.
Đáp án B, E. Tách nội dung tin cậy và không tin cậy giúp giảm rủi ro prompt injection. Lưu lịch sử ở server ngăn kẻ xấu giả mạo lượt assistant. A sai: lộ API key; phải đọc key từ biến môi trường ở server. C sai: nâng nội dung không tin cậy lên cấp operator, mở đường cho prompt injection. D sai: reference khuyên user_id là ID ẩn danh (opaque), không chứa thông tin cá nhân.

  4. Không hợp lệ: message role: "system" không được là phần tử đầu tiên; chỉ dẫn từ đầu phải dùng tham số top-level system.
Đáp án D. Tài liệu Using the Messages API: message system giữa hội thoại phải nằm ngay sau một lượt user và không được là phần tử đầu tiên; đặt sai vị trí trả lỗi 400. A, B và C sai vì đều giả định request thành công, trong khi vị trí này không hợp lệ. Cách đúng: "system": "Trả lời bằng tiếng Việt." ở top-level.
Một chatbot chăm sóc khách hàng có hội thoại trung bình 200 lượt. Chi phí input_tokens tăng nhanh và các chi tiết đầu cuộc trò chuyện (mã đơn hàng) vẫn cần được nhớ. Chiến lược quản lý lịch sử nào cân bằng nhất?
  1. Giữ N lượt gần nhất, đồng thời tóm tắt các lượt cũ (kèm dữ kiện quan trọng như mã đơn) rồi chèn bản tóm tắt vào system hoặc lượt user.
  2. Luôn gửi toàn bộ 200 lượt vì context window đủ lớn.
  3. Chỉ gửi lượt user mới nhất để tiết kiệm tối đa.
  4. Dùng prefill để nhắc lại mã đơn ở cuối mỗi request.
Đáp án A. Kết hợp cửa sổ trượt và tóm tắt giúp chi phí ổn định mà vẫn giữ dữ kiện then chốt. B sai: đúng về mặt kỹ thuật nhưng chi phí và độ trễ tăng mỗi lượt, đúng là vấn đề cần giải quyết. C sai: mất toàn bộ ngữ cảnh. D sai: prefill lỗi 400 trên model mới; tài liệu gợi ý chèn lời nhắc vào lượt user.
Ứng dụng của bạn dùng extended/adaptive thinking và tool use. Khi lưu lịch sử, bạn chỉ lưu resp.content[0].text làm lượt assistant. Điều này có vấn đề gì?
  1. Không vấn đề gì; API chỉ cần phần text.
  2. Làm mất các khối như thinking hoặc tool_use; reference yêu cầu khối thinking được gửi lại nguyên vẹn và đúng thứ tự, nên cần lưu nguyên resp.content.
