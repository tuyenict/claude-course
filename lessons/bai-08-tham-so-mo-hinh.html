Sau bài này bạn sẽ

  • Đặt max_tokens hợp lý: hiểu đây là hard limit cho đầu ra (kể cả phần thinking), biết giới hạn tối đa của model và khi nào phải dùng streaming.
  • Hiểu khái niệm temperature, top_p, top_k và biết rằng ở API version 2026-10-21 ba tham số này đã bị gỡ bỏ – gửi lên sẽ nhận lỗi 400.
  • Dùng stop_sequences để dừng sinh văn bản tại một chuỗi tùy chọn và đọc trường stop_sequence trong response.
  • Nhận biết và xử lý đúng cả 7 giá trị stop_reason: end_turn, max_tokens, stop_sequence, tool_use, pause_turn, refusal, model_context_window_exceeded.
  • Đọc khối usage để theo dõi token, chi phí; phân biệt stop reason (response thành công) với lỗi HTTP 4xx/5xx.

🎛️Tổng quan: các “núm vặn” của một request

Ở bài 6 và bài 7, bạn đã gửi được request đầu tiên và hội thoại nhiều lượt. Bài này đi sâu vào hai đầu của một lời gọi Messages API: các tham số điều khiển việc sinh văn bản ở phía request, và các trường mô tả kết quả ở phía response – đặc biệt là stop_reason.

Theo Messages API reference, một request bắt buộc có ba tham số model, max_tokens, messages. Phần còn lại là tùy chọn: system, stop_sequences, stream, metadata, output_config, tools, thinking… Mỗi response thành công trả về một Message object có content, stop_reason, stop_sequence, stop_details và usage.

Ví dụ đời thường

Hãy coi Claude như một phóng viên viết bài cho bạn. max_tokens là số chữ tối đa tòa soạn cho phép. stop_sequences là từ khóa “HẾT”: hễ viết tới đó là dừng bút. Còn stop_reason là tờ ghi chú phóng viên kẹp kèm bài: “Tôi viết xong”, “Hết chỗ”, “Gặp chữ HẾT”, hay “Tôi cần tra cứu thêm (tool_use)”.

📏max_tokens – giới hạn cứng cho đầu ra

Messages API reference mô tả max_tokens là “số token tối đa được sinh trước khi dừng”. Có ba điểm cần nhớ:

  • Là mức trần, không phải mục tiêu. “Model có thể dừng trước khi chạm mức này.” Đặt max_tokens=4096 không khiến Claude viết dài 4096 token; nó chỉ ngăn Claude viết dài hơn.
  • Bắt buộc, giá trị nhỏ nhất là 0. Đặt 0 để pre-warm prompt cache mà không sinh phản hồi (sẽ học ở bài Prompt caching).
  • Mỗi model có mức tối đa riêng. Theo Models overview (kiểm tra ngày 2026-11-20), Claude Fable 5.2, Opus 5.5, Sonnet 5.5 và Haiku 5.5 có max output 128K token trên Messages API đồng bộ; các model cũ hơn như Claude Haiku 4.5 hay Sonnet 4.5 là 64K. Trên Message Batches API, một số model hỗ trợ tới 300K token đầu ra với beta header output-300k-2026-03-24.

Thinking cũng tính vào max_tokens

Các model mới có adaptive thinking. Ví dụ, trên Claude Opus 5.5 adaptive thinking luôn bật và không tắt được. Tài liệu Effort nhấn mạnh: max_tokens “là giới hạn cứng cho tổng đầu ra (thinking cộng phần trả lời)”, và “thinking vẫn tính vào max_tokens ngay cả khi nội dung thinking không được trả về”. Vì vậy, nếu đặt max_tokens quá nhỏ cho một bài toán khó, model có thể dùng hết ngân sách cho việc suy nghĩ và câu trả lời bị cắt cụt.

max_tokens lớn ⇒ nên dùng streaming

Trang Errors (mục Long requests) khuyên tránh đặt max_tokens lớn mà không dùng streaming hoặc Message Batches API, vì một số mạng có thể cắt kết nối đang “im lặng” quá lâu. SDK của Anthropic kiểm tra để request không streaming không vượt quá ngưỡng timeout 10 phút. Ví dụ code của trang Stop reasons ghi chú: Python SDK yêu cầu streaming khi max_tokens vượt khoảng 21k.

# Python SDK (anthropic >= 2.0.0, API version 2026-10-21)
import anthropic

client = anthropic.Anthropic()  # đọc ANTHROPIC_API_KEY từ biến môi trường – không hard-code key

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=10,                  # cố tình đặt rất nhỏ
    messages=[{"role": "user", "content": "Giải thích vật lý lượng tử"}],
)
print(response.stop_reason)          # "max_tokens" – câu trả lời bị cắt
print(response.usage.output_tokens)  # bằng (hoặc xấp xỉ) giới hạn đã đặt
Mẹo thực chiến (Pro Tip)

Cần câu trả lời ngắn? ⇒ Hãy yêu cầu độ dài trong prompt (“trả lời trong 2 câu”), đừng dùng max_tokens nhỏ. max_tokens chỉ cắt ngang câu chữ, không làm Claude viết gọn hơn. Tài liệu Effort cũng nói: effort hầu như không thay đổi độ dài câu trả lời – hãy dùng prompt để chỉnh độ dài và giọng văn.

Lỗi thường gặp

Đặt max_tokens sát nút cho agent dùng tool. Nếu output bị cắt giữa một khối tool_use, JSON đầu vào của tool không hoàn chỉnh. Tài liệu khuyên: khi stop_reason == "max_tokens" và khối cuối là tool_use, hãy gửi lại request với max_tokens cao hơn, không cố thực thi tool đó.

🌡️Temperature, top_p, top_k – khái niệm và thay đổi ở API 2026-10-21

Temperature là gì?

Theo Glossary của Anthropic, temperature là tham số điều khiển mức ngẫu nhiên trong dự đoán của model khi sinh văn bản:

  • Temperature cao ⇒ đầu ra sáng tạo, đa dạng hơn; nhiều cách diễn đạt; với truyện hư cấu, cả nội dung câu trả lời cũng thay đổi.
  • Temperature thấp ⇒ đầu ra “bảo thủ”, sát với cách diễn đạt và câu trả lời có xác suất cao nhất.
  • Ngay cả với temperature bằng 0, kết quả không hoàn toàn tất định (deterministic): cùng một input có thể cho output khác nhau giữa các lần gọi API – điều này đúng cả với dịch vụ của Anthropic lẫn qua các nhà cung cấp cloud.

top_p (nucleus sampling) và top_k là hai cách khác để giới hạn tập token ứng viên khi lấy mẫu. Cả ba được gọi chung là sampling parameters. Khóa “Building with the Claude API” trên Anthropic Academy có hẳn một bài “Temperature” trong chương Accessing Claude with the API, nên khái niệm này vẫn quan trọng để hiểu cách LLM sinh văn bản.

Thay đổi quan trọng: tham số lấy mẫu đã bị gỡ bỏ

Đây là điểm khác biệt lớn so với nhiều tài liệu cũ trên mạng. Theo trang Migrating to API version 2026-10-21 và trang API versions (kiểm tra ngày 2026-11-20):

  • Ở API version 2026-10-21, “một request gửi temperature, top_p hoặc top_k trả về lỗi 400, ngay cả khi dùng giá trị mặc định”, trên mọi model. Áp dụng cho Messages API, token counting và từng request trong Message Batch.
  • Các SDK và CLI ở bản major mới nhất (vd Python anthropic 2.0.0, TypeScript @anthropic-ai/sdk 1.0.0) không còn ba tham số này.
  • Khi không gửi, request lấy mẫu với giá trị mặc định, gồm temperature = 1.0 – giống một request 2023-06-01 không gửi tham số.
  • Các model chỉ chấp nhận giá trị mặc định – như Claude 4.7 trở về sau – lấy mẫu như trước. Trên model còn chấp nhận giá trị khác (vd Claude Sonnet 4.6), request từng hạ temperature để có kết quả ổn định hơn sẽ mất tác dụng đó, và “không có thiết lập nào khác thay thế”.
  • Nếu một request phụ thuộc vào giá trị không mặc định: hoặc thôi gửi tham số, hoặc giữ request đó ở version 2023-06-01.

Vậy muốn đầu ra ổn định, nhất quán thì làm gì?

Hướng dẫn của Anthropic là bỏ các trường này và dùng prompting để định hướng hành vi của model. Các kỹ thuật thực tế (sẽ học kỹ ở các bài sau):

  • Prompt rõ ràng, cụ thể và có ví dụ mẫu (few-shot) – bài 12, 13.
  • Structured outputs (output_config.format với JSON schema) khi cần định dạng cố định – bài 10.
  • stop_sequences để cắt đầu ra tại điểm mong muốn – phần tiếp theo.
  • Evals để đo độ nhất quán thực tế thay vì tin vào một con số tham số – bài 15, 16.
Lưu ý – effort không phải temperature

output_config.effort (low, medium, high, xhigh, max) điều chỉnh lượng token Claude bỏ ra (thinking, tool call, text) – đánh đổi giữa độ kỹ lưỡng với tốc độ và chi phí. Nó không điều chỉnh độ ngẫu nhiên. Mặc định là medium trên Claude Opus 5.5 và Haiku 5.5, high trên các model khác hỗ trợ effort (tài liệu Effort, kiểm tra ngày 2026-11-20). Effort sẽ được học kỹ ở bài 22 (Extended Thinking & Effort).

Lỗi thường gặp

Copy code mẫu cũ có temperature=0 rồi nâng SDK lên bản mới ⇒ request trả về 400 invalid_request_error (hoặc SDK báo tham số không tồn tại). Cách sửa: xóa temperature, top_p, top_k khỏi mọi request, kể cả code tạo Message Batch.

Mẹo thực chiến (Pro Tip)

Đề bài hay tình huống hỏi “làm sao để Claude trả lời nhất quán hơn trên API mới?” ⇒ Đáp án đúng là cải thiện prompt / dùng structured outputs / đo bằng eval, không phải “đặt temperature = 0” (bị gỡ ở 2026-10-21) hay “tăng effort” (effort điều chỉnh độ kỹ lưỡng, không phải độ ngẫu nhiên).

⛔stop_sequences – dừng tại chuỗi tùy chọn

Bình thường Claude dừng khi đã hoàn tất lượt của mình một cách tự nhiên, khi đó stop_reason là "end_turn". Nếu muốn model dừng khi gặp một chuỗi văn bản cụ thể, dùng tham số stop_sequences – một mảng chuỗi tùy chọn. Theo Messages API reference: khi model gặp một trong các chuỗi đó, stop_reason sẽ là "stop_sequence" và trường stop_sequence trong response chứa đúng chuỗi đã khớp. Nếu không có chuỗi nào khớp, stop_sequence là null.

# Dừng khi Claude viết "END" hoặc "STOP"
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    stop_sequences=["END", "STOP"],
    messages=[{"role": "user", "content": "Hãy viết một đoạn văn, khi xong thì viết END"}],
)
if response.stop_reason == "stop_sequence":
    print(f"Dừng tại chuỗi: {response.stop_sequence}")  # "END" hoặc "STOP"

Lưu ý – prefill trên model mới

Nhiều hướng dẫn cũ kết hợp stop_sequences với prefill (lượt assistant cuối dang dở). Theo trang Errors, Claude 4.6 trở về sau và Claude Mythos Preview không hỗ trợ prefill: gửi request kết thúc bằng lượt assistant sẽ nhận 400 invalid_request_error. Với các model này, hãy dùng chỉ dẫn trong prompt hoặc structured outputs thay cho prefill.

🏁stop_reason – 7 lý do Claude dừng

Mọi response thành công của Messages API đều có trường stop_reason cho biết vì sao Claude ngừng sinh. Trang Stop reasons and fallback khuyên: hãy kiểm tra trường này để quyết định dùng kết quả ngay, tiếp tục hội thoại, thử lại, hay chuyển sang model dự phòng (fallback model). Ở chế độ không streaming, giá trị này luôn khác null.

end_turn – và trường hợp response rỗng

end_turn là giá trị phổ biến nhất. Tuy vậy, tài liệu cảnh báo: đôi khi Claude trả về response rỗng (khoảng 2–3 token, không có nội dung) với stop_reason: "end_turn". Nguyên nhân thường gặp:

  • Thêm khối text ngay sau các tool_result – việc này “dạy” Claude rằng sau mỗi kết quả tool thì kết thúc lượt.
  • Gửi lại câu trả lời đã hoàn chỉnh của Claude mà không thêm gì.

Cách sửa: gửi tool_result mà không kèm text. Nếu vẫn xảy ra, thêm một lời nhắc tiếp tục trong một lượt user mới; đừng thử lại y nguyên với response rỗng. Lời nhắc tiếp tục chỉ là biện pháp cuối cùng.

# SAI – thêm text ngay sau tool_result
{"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": "toolu_123", "content": "6912"},
    {"type": "text", "text": "Here's the result"},   # đừng làm vậy
]}

# ĐÚNG – chỉ có tool_result
{"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": "toolu_123", "content": "6912"},
]}

max_tokens – xử lý câu trả lời bị cắt

Có hai hướng: tăng max_tokens rồi gửi lại, hoặc yêu cầu Claude viết tiếp. Mẫu “đảm bảo câu trả lời đầy đủ” trong tài liệu ghép phần đã nhận, rồi gửi lại với lượt assistant chứa phần đó và một lượt user “Please continue from where you left off.” (request kết thúc bằng lượt user, nên không phải prefill).

def get_complete_response(client, prompt, max_attempts=3):
    messages = [{"role": "user", "content": prompt}]
    full_response = ""
    for _ in range(max_attempts):
        response = client.messages.create(
            model="claude-opus-5-5", messages=messages, max_tokens=4096
        )
        full_response += next(
            (b.text for b in response.content if b.type == "text"), ""
        )
        if response.stop_reason != "max_tokens":
            break                       # đã xong tự nhiên (hoặc lý do khác)
        # Bị cắt: gửi phần đã có và yêu cầu viết tiếp (giới hạn số lần để tránh lặp vô hạn)
        messages = [
            {"role": "user", "content": prompt},
            {"role": "assistant", "content": full_response},
            {"role": "user", "content": "Please continue from where you left off."},
        ]
    return full_response

tool_use và pause_turn – hai lý do “cần gửi tiếp”

🛠️tool_use

  • Claude muốn ứng dụng của bạn chạy một client tool.
  • Chạy tool, gửi lượt user chứa các khối tool_result.
  • Tài liệu khuyên dùng tool runner của SDK cho đa số trường hợp.
  • Nếu cùng lúc có server tool đang chờ (khối server_tool_use/mcp_tool_use chưa có kết quả): gửi lại content y nguyên, lượt user chỉ chứa tool_result, cùng mảng tools. Thêm text sau tool_result ⇒ lỗi 400.

⏸️pause_turn

  • Vòng lặp server tool phía Anthropic (vd web search) chạm giới hạn – mặc định 10 vòng/request.
  • Không bao giờ xuất hiện khi Claude dừng để gọi tool do bạn chạy (khi đó là tool_use).
  • Thêm content của response y nguyên làm lượt assistant, gửi lại cùng tools, không thêm lượt user phía sau.
  • Nếu response có container, gửi lại ID của nó để giữ file.

refusal và stop_details

refusal được trả về như một response HTTP 200 bình thường, không phải lỗi. Đối tượng stop_details (chỉ khác null khi stop_reason là refusal) có type: "refusal", category (một trong cyber, bio, frontier_llm, reasoning_extraction, general_harms, hoặc null) và explanation (văn bản giải thích, không đảm bảo ổn định). Tài liệu cho biết request bị từ chối thường có thể thành công khi thử lại trên một model Claude khác; với Claude Haiku 5.5 không có fallback phía server nên phải tự làm fallback phía client.

model_context_window_exceeded

Giá trị này cho phép bạn đặt max_tokens lớn mà không cần biết chính xác kích thước input: nếu context window đầy trước, Claude dừng với model_context_window_exceeded. Theo tài liệu (kiểm tra ngày 2026-11-20): giá trị này hiện chỉ được định kiểu trong namespace beta của SDK (vd client.beta.messages trong Python); từ Sonnet 4.5 trở về sau API trả giá trị này mà không cần beta header, còn model cũ hơn cần header model-context-window-exceeded-2025-08-26.

stop_reason khi streaming

Khi dùng streaming (bài 9), stop_reason là null trong sự kiện message_start, được cung cấp trong sự kiện message_delta, và không có trong các sự kiện khác.

Mẹo thực chiến (Pro Tip)

Agent dùng web search thỉnh thoảng trả về câu trả lời “dở dang” với stop_reason: "pause_turn" ⇒ đừng coi là lỗi; hãy gửi lại content y nguyên làm lượt assistant để Claude làm tiếp, và đặt giới hạn số lần lặp phía bạn (vd max_requests=5) để tránh vòng lặp vô tận.

Lỗi thường gặp

Chỉ đọc response.content[0].text mà không kiểm tra stop_reason. Hậu quả: hiển thị câu trả lời bị cắt như thể đã hoàn chỉnh, bỏ qua yêu cầu gọi tool, hoặc vỡ chương trình khi content rỗng hay khối đầu là thinking/tool_use. Luôn rẽ nhánh theo stop_reason và duyệt content theo type.

📊Giải phẫu response và khối usage

Dưới đây là một response mẫu (rút từ trang Stop reasons, thêm chú thích). Các trường cần nắm:

{
  "id": "msg_01234",            // ID duy nhất; định dạng có thể thay đổi theo thời gian
  "type": "message",           // luôn là "message"
  "role": "assistant",
  "content": [{"type": "text", "text": "Here's the answer to your question..."}],
  "stop_reason": "end_turn",     // vì sao dừng
  "stop_sequence": null,        // chuỗi dừng đã khớp (nếu có)
  "stop_details": null,         // chỉ có giá trị khi stop_reason = "refusal"
  "usage": {
    "input_tokens": 100,          // token đầu vào (không gồm phần đọc/ghi cache)
    "output_tokens": 50           // token đầu ra – gồm cả thinking
  }
}

Các trường trong usage

Theo Messages API reference, usage là thống kê “tính tiền và rate limit”: Anthropic tính phí và giới hạn tốc độ theo số token. Lưu ý quan trọng: API chuyển request sang định dạng nội bộ, và đầu ra đi qua bước phân tích, nên số token trong usage không khớp 1–1 với nội dung bạn nhìn thấy. Ví dụ, output_tokens vẫn khác 0 ngay cả khi Claude trả về chuỗi rỗng.

TrườngÝ nghĩa
input_tokensSố token đầu vào đã dùng.
output_tokensSố token đầu ra – con số chính thức để tính tiền.
cache_creation_input_tokensToken đầu vào dùng để tạo mục cache (chi tiết theo TTL trong cache_creation: ephemeral_5m_input_tokens, ephemeral_1h_input_tokens).
cache_read_input_tokensToken đầu vào đọc từ cache.
output_tokens_details.thinking_tokensSố token đầu ra dành cho suy luận nội bộ; luôn ≤ output_tokens.
server_tool_useSố lần gọi server tool: web_search_requests, web_fetch_requests.
service_tier / speed / inference_geoTier đã dùng (standard, priority, batch), chế độ tốc độ, vùng địa lý thực hiện inference.

Tổng token đầu vào của một request = input_tokens + cache_creation_input_tokens + cache_read_input_tokens.

Mẹo thực chiến (Pro Tip)

Muốn ghi log chi phí cho từng request ⇒ lưu cả ba trường input (input_tokens, cache_creation_input_tokens, cache_read_input_tokens) và output_tokens. Chỉ lưu input_tokens sẽ đánh giá thiếu khi có dùng prompt caching. Khi dùng metadata.user_id để theo dõi người dùng, chỉ dùng UUID/hash – tài liệu yêu cầu không đưa tên, email, số điện thoại.

🧯Stop reason khác lỗi HTTP – viết bộ xử lý tổng quát

🏁Stop reasons

  • Nằm trong body của response thành công.
  • Cho biết việc sinh văn bản đã kết thúc bình thường.
  • Response vẫn có nội dung hợp lệ (dù có thể bị cắt).
  • Ví dụ: max_tokens, refusal, pause_turn.

🚨Errors

  • Mã trạng thái HTTP 4xx/5xx.
  • Cho biết request không xử lý được.
  • Trong SDK Python: ngoại lệ anthropic.APIStatusError (vd 429 rate limit, 500 server error).
  • Ví dụ: gửi temperature ở version 2026-10-21 ⇒ 400.
import anthropic

client = anthropic.Anthropic()  # ANTHROPIC_API_KEY từ biến môi trường

def handle_response(response):
    match response.stop_reason:
        case "tool_use":
            return handle_tool_use(response)
        case "max_tokens":
            return handle_truncation(response)
        case "model_context_window_exceeded":
            return handle_context_limit(response)
        case "pause_turn":
            return handle_pause(response)
        case "refusal":
            return handle_refusal(response)
        case _:  # end_turn, stop_sequence…
            return next((b.text for b in response.content if b.type == "text"), "")

try:
    response = client.messages.create(
        model="claude-opus-5-5",
        max_tokens=1024,
        messages=[{"role": "user", "content": "Hello!"}],
    )
    print(handle_response(response))
except anthropic.APIStatusError as e:     # lỗi HTTP – không có stop_reason
    print("API error", e.status_code)

Tài liệu cũng khuyên hiển thị rõ khi bị cắt cụt: nếu stop_reason là max_tokens hoặc model_context_window_exceeded, nối thêm một thông báo (vd “[Câu trả lời bị cắt do giới hạn max_tokens]”) để người đọc biết nội dung chưa đầy đủ.

Lưu ý bảo mật

Khi stop_reason là tool_use, các tham số tool do model sinh ra có thể chịu ảnh hưởng của nội dung bên ngoài (trang web, tài liệu người dùng tải lên) – rủi ro prompt injection. Hãy kiểm tra block.input trước khi thực thi, chỉ cấp cho tool quyền tối thiểu cần thiết (least privilege), và đặt giới hạn số vòng lặp. Không ghi API key vào code hay log; đọc từ biến môi trường ANTHROPIC_API_KEY.

🧪Thực hành

Chuẩn bị: Python 3.10+ (cần match), pip install "anthropic>=2.0.0", đặt biến môi trường ANTHROPIC_API_KEY. Model dùng trong bài: claude-haiku-5-5 (rẻ, nhanh) hoặc claude-opus-5-5 – lấy từ Models overview, kiểm tra ngày 2026-11-20.

  1. Bài tập 1 – Quan sát max_tokens. Gọi API ba lần với cùng prompt “Giải thích cơ chế của prompt caching” và max_tokens lần lượt là 20, 300, 4096. In stop_reason và usage.output_tokens.
    Kết quả mong đợi: với 20 (và có thể 300) thấy stop_reason = "max_tokens", câu bị cắt ngang; với 4096 thấy end_turn và output_tokens nhỏ hơn 4096 – chứng minh max_tokens chỉ là mức trần. Lưu ý thinking cũng tiêu tốn một phần ngân sách này.
  2. Bài tập 2 – Dùng stop_sequences để cắt phần thừa.

  3. Bài tập 3 – Kiểm chứng việc gỡ temperature. Thêm temperature vào request ở bài tập 2. SDK bản mới không còn tham số này, nên gửi qua extra_body={"temperature": 0}. Bọc lời gọi trong try/except anthropic.APIStatusError.
    Kết quả mong đợi: nhận lỗi 400 với API version 2026-10-21. Ghi lại thông báo lỗi; sau đó xóa tham số và xác nhận request chạy lại bình thường.

Viết hàm render(response) trả về văn bản và nối “[Câu trả lời bị cắt do giới hạn max_tokens]” khi stop_reason == "max_tokens", “[Đã chạm giới hạn context window]” khi model_context_window_exceeded, và “Yêu cầu bị từ chối: …” kèm stop_details.category khi refusal. Ghi log usage (cả ba trường input và output_tokens) ra file JSON Lines.
    Kết quả mong đợi: chạy lại bài tập 1 qua render(), các response bị cắt hiển thị thông báo rõ ràng; file log có một dòng mỗi request, không chứa API key hay nội dung nhạy cảm.

Tóm tắt ghi nhớ

Key takeaways
  • max_tokens là tham số bắt buộc, là mức trần cứng cho đầu ra (gồm cả thinking); model có thể dừng sớm hơn. Các model hiện hành có max output 128K (Messages API đồng bộ). max_tokens lớn ⇒ dùng streaming.
  • Muốn câu trả lời ngắn ⇒ yêu cầu trong prompt, không hạ max_tokens.
  • temperature điều khiển độ ngẫu nhiên (mặc định 1.0; ngay cả 0 cũng không hoàn toàn tất định). Ở API 2026-10-21, temperature/top_p/top_k bị gỡ: gửi lên ⇒ 400 trên mọi model. Dùng prompting, structured outputs, eval để có kết quả nhất quán.
  • stop_sequences (request, mảng) ⇒ stop_reason: "stop_sequence" và stop_sequence (response, chuỗi đã khớp).
  • 7 stop_reason: end_turn, max_tokens, stop_sequence, tool_use, pause_turn, refusal, model_context_window_exceeded. Luôn kiểm tra trước khi dùng content.
  • pause_turn chỉ đến từ vòng lặp server tool (mặc định 10 vòng); gửi lại content y nguyên, không thêm lượt user. refusal là HTTP 200, đọc stop_details.
  • Tổng input = input_tokens + cache_creation_input_tokens + cache_read_input_tokens. Stop reason ≠ lỗi HTTP.

Thuật ngữ (Glossary)

max_tokens
Số token đầu ra tối đa – tham số bắt buộc, giới hạn cứng tổng đầu ra (thinking + trả lời).
Temperature
Nhiệt độ lấy mẫu – điều khiển độ ngẫu nhiên khi sinh văn bản; đã bị gỡ khỏi API version 2026-10-21.
top_p (nucleus sampling)
Lấy mẫu hạt nhân – giới hạn tập token ứng viên khi lấy mẫu; đã bị gỡ ở 2026-10-21.
top_k
Lấy mẫu top-k – giới hạn số token ứng viên khi lấy mẫu; đã bị gỡ ở 2026-10-21.
Sampling parameters
Tham số lấy mẫu – tên gọi chung cho temperature, top_p, top_k.
Deterministic
Tất định – cùng input luôn cho cùng output; Claude không đảm bảo điều này kể cả khi temperature = 0.
stop_sequences
Chuỗi dừng – tham số request, mảng chuỗi khiến model dừng khi sinh ra.
stop_sequence
Chuỗi dừng đã khớp – trường response, chứa chuỗi đã kích hoạt việc dừng (hoặc null).
stop_reason
Lý do dừng – trường response cho biết vì sao Claude ngừng sinh.
end_turn
Kết thúc lượt tự nhiên – Claude đã trả lời xong.
pause_turn
Tạm dừng lượt – vòng lặp server tool chạm giới hạn số vòng; gửi lại để tiếp tục.
refusal
Từ chối – bộ phân loại an toàn can thiệp; HTTP 200, chi tiết trong stop_details.
stop_details
Chi tiết lý do dừng – object có category, explanation; chỉ khác null khi refusal.
model_context_window_exceeded
Vượt cửa sổ ngữ cảnh – đầu ra lấp đầy context window trước khi chạm max_tokens.
Truncation
Cắt cụt – câu trả lời bị dừng giữa chừng do giới hạn token.
Fallback model
Model dự phòng – model khác dùng để thử lại khi request bị từ chối.
usage
Thống kê token – input/output/cache token, cơ sở tính tiền và rate limit.
Effort
Mức nỗ lực – output_config.effort, điều chỉnh lượng token model bỏ ra; không thay thế temperature.
Prefill
Điền trước câu trả lời – kết thúc request bằng lượt assistant dang dở; không hỗ trợ trên Claude 4.6 trở về sau.
API version (anthropic-version)
Phiên bản API – header quyết định hành vi API; bản mới nhất 2026-10-21.

Câu hỏi luyện tập

Một startup làm chatbot FAQ muốn câu trả lời luôn ngắn gọn (khoảng 2–3 câu). Lập trình viên đặt max_tokens=60 và người dùng phàn nàn câu trả lời hay bị cụt giữa chừng. Cách khắc phục phù hợp nhất là gì?
  1. Giảm max_tokens xuống 30 để Claude buộc phải viết ngắn hơn.
  2. Đặt temperature=0 để câu trả lời gọn và ổn định.
  3. Yêu cầu độ dài trong prompt (vd “trả lời trong 2–3 câu”) và đặt max_tokens đủ rộng làm lưới an toàn.
  4. Thêm stop_sequences=["."] để dừng sau câu đầu tiên.
Đáp án C. max_tokens chỉ là mức trần cứng, không khiến Claude viết gọn hơn; độ dài nên điều khiển bằng prompt. A sai: giảm thêm chỉ làm câu bị cắt nhiều hơn. B sai: ở API 2026-10-21, gửi temperature trả lỗi 400; và temperature không điều khiển độ dài. D sai: dừng ở dấu chấm đầu tiên cho câu trả lời chỉ một câu, dễ dừng nhầm ở số thập phân hay chữ viết tắt.
Đọc response sau: 
{"content": [{"type": "text", "text": "Ba bước triển khai: 1) Chuẩn bị dữ liệu 2) Huấn"}],
 "stop_reason": "max_tokens", "stop_sequence": null,
 "usage": {"input_tokens": 812, "output_tokens": 256}}
Ứng dụng nên làm gì?
  1. Hiển thị ngay vì response có HTTP 200 nên đã hoàn chỉnh.
  2. Coi là bị cắt cụt: tăng max_tokens rồi gửi lại, hoặc yêu cầu Claude viết tiếp; nếu hiển thị thì báo rõ là chưa đầy đủ.
  3. Bắt ngoại lệ APIStatusError và thử lại với backoff.
  4. Chuyển sang model dự phòng vì Claude đã từ chối trả lời.
Đáp án B. stop_reason: "max_tokens" nghĩa là đầu ra chạm giới hạn – câu trả lời dừng giữa chữ “Huấn”. Tài liệu khuyên tăng max_tokens hoặc tiếp tục, và hiển thị thông báo bị cắt. A sai: HTTP 200 không có nghĩa là trả lời trọn vẹn. C sai: đây không phải lỗi HTTP nên không có exception. D sai: từ chối có stop_reason: "refusal".
Một nhóm nâng SDK Python lên anthropic 2.0.0 (API version 2026-10-21). Code cũ có temperature=0.2 và top_p=0.9 cho tác vụ trích xuất dữ liệu. Những phát biểu nào đúng? (Chọn 2)
  1. Request gửi temperature, top_p hoặc top_k sẽ trả lỗi 400, kể cả khi dùng giá trị mặc định.
  2. Chỉ cần đổi temperature về 1.0 là request hợp lệ.
  3. Thay temperature=0.2 bằng output_config.effort="low" sẽ cho cùng mức ngẫu nhiên thấp.
  4. Nên bỏ các tham số này và cải thiện tính nhất quán bằng prompt, ví dụ mẫu, structured outputs và đo bằng eval.
  5. Ba tham số vẫn hoạt động trên mọi model ở version mới, chỉ bị bỏ qua khi bật thinking.
Đáp án A, D. Migration guide nói rõ: ở 2026-10-21, gửi bất kỳ tham số nào trong ba tham số trả 400 trên mọi model, ngay cả ở giá trị mặc định; hướng dẫn là bỏ đi và dùng prompting. B sai: giá trị mặc định cũng bị từ chối. C sai: effort điều chỉnh lượng token bỏ ra, không phải độ ngẫu nhiên; tài liệu nói “không có thiết lập nào khác thay thế”. E sai: đó là mô tả hạn chế ở version cũ trên model cũ, không phải ở 2026-10-21.

  3. response.usage.stop_sequence
  4. response.stop_sequence, khi stop_reason == "stop_sequence"
Đáp án D. Trường stop_sequence (số ít) chứa chuỗi đã khớp, hoặc null nếu không có. A sai: stop_sequences (số nhiều) là tham số request, không có trong response. B sai: stop_details chỉ dùng cho refusal. C sai: usage chỉ chứa thống kê token.

  1. Thêm lượt user “Hãy tiếp tục” rồi gửi lại.
  2. Chạy web search phía client rồi trả tool_result.
  3. Thêm content của response y nguyên làm lượt assistant, gửi lại với cùng tools và không có lượt user phía sau.
  4. Coi là lỗi và thử lại cả request ban đầu từ đầu.
Đáp án C. pause_turn xảy ra khi vòng lặp server tool chạm giới hạn số vòng (mặc định 10). Để tiếp tục, gửi lại nội dung assistant nguyên vẹn, không thêm lượt user. A sai: tài liệu yêu cầu không thêm lượt user sau lượt assistant. B sai: web search là server tool do Anthropic chạy; khi cần bạn chạy tool thì stop reason là tool_use. D sai: pause_turn không phải lỗi, làm lại từ đầu sẽ mất công và tốn token.

Nhóm phát triển thấy Claude thường trả về response rỗng với stop_reason: "end_turn". Nguyên nhân có khả năng nhất?
  1. max_tokens=1024 quá nhỏ.
  2. Thêm khối text ngay sau tool_result, khiến Claude học cách kết thúc lượt sau mỗi kết quả tool.
  3. Thiếu tham số temperature.
  4. Model không hỗ trợ tool use.
Đáp án B. Trang Stop reasons nêu đúng nguyên nhân này; cách sửa là chỉ gửi tool_result. A sai: nếu thiếu token thì stop_reason là max_tokens, không phải end_turn. C sai: temperature đã bị gỡ và không liên quan. D sai: Opus 5.5 hỗ trợ tool use; lỗi nằm ở cấu trúc message.
Ứng dụng tư vấn nhận response có stop_reason: "refusal" và stop_details.category: "cyber" với mã HTTP 200. Phát biểu nào đúng?
  1. Đây là response bình thường (không phải lỗi); ứng dụng nên đọc stop_details và có thể thử lại trên một model Claude khác (fallback).
  2. SDK sẽ ném APIStatusError 400, cần bắt exception.
  3. stop_details luôn có giá trị cho mọi stop_reason.
  4. Nên tăng max_tokens để Claude có đủ chỗ trả lời.
Đáp án A. Tài liệu: bộ phân loại an toàn trả refusal như response HTTP 200; stop_details cho biết nhóm chính sách; request thường có thể thành công khi thử lại trên model khác. B sai: không có exception. C sai: stop_details là null với mọi stop reason khác refusal. D sai: từ chối không liên quan đến giới hạn token.
Đội tài chính muốn tính chính xác tổng số token đầu vào của mỗi request khi có dùng prompt caching. Công thức đúng là gì?
  1. input_tokens
  2. input_tokens + output_tokens
  3. cache_read_input_tokens + output_tokens
  4. input_tokens + cache_creation_input_tokens + cache_read_input_tokens
Đáp án D. Messages API reference: “Tổng input tokens của một request là tổng của input_tokens, cache_creation_input_tokens và cache_read_input_tokens.” A sai: thiếu phần cache. B và C sai: output_tokens là token đầu ra, không thuộc input.
Một kỹ sư đặt max_tokens rất lớn cho Claude Opus 5.5 để sinh báo cáo dài. Những điều nào cần lưu ý? (Chọn 2)
  1. max_tokens lớn khiến Claude cố viết đủ số token đó.
  2. Thinking cũng tính vào max_tokens, kể cả khi nội dung thinking không được trả về.
  3. max_tokens là tham số tùy chọn, bỏ trống thì API tự chọn mức tối đa.
  4. Request không streaming với max_tokens lớn luôn an toàn vì SDK tự chia nhỏ.
  5. Với max_tokens lớn nên dùng streaming hoặc Message Batches API để tránh kết nối bị cắt/timeout.
Đáp án B, E. Tài liệu Effort: thinking tính vào max_tokens, là giới hạn cứng cho tổng đầu ra. Trang Errors: tránh max_tokens lớn mà không streaming/batch, SDK kiểm tra ngưỡng timeout 10 phút. A sai: đây chỉ là mức trần, model có thể dừng sớm. C sai: max_tokens là tham số bắt buộc. D sai: SDK không tự chia nhỏ; nó cảnh báo/kiểm tra request không streaming có nguy cơ vượt timeout.
Đọc code xử lý stream: 
with client.messages.stream(model="claude-opus-5-5", max_tokens=1024,
                            messages=msgs) as stream:
    for event in stream:
        if event.type == "message_start":
            print(event.message.stop_reason)
Giá trị in ra là gì và nên đọc stop_reason ở đâu?
  1. "end_turn"; đọc ở message_start là đúng.
  2. Một chuỗi ngẫu nhiên; nên đọc ở content_block_delta.
  3. None; stop_reason được cung cấp trong sự kiện message_delta.
  4. Lỗi vì stream không có stop_reason; phải gọi lại không streaming.
Đáp án C. Khi streaming, stop_reason là null trong message_start, có giá trị trong message_delta, và không xuất hiện ở sự kiện khác. A sai: lúc bắt đầu, model chưa biết sẽ dừng vì sao. B sai: content_block_delta chứa phần văn bản, không chứa stop_reason. D sai: stream vẫn có stop_reason trong message_delta.
