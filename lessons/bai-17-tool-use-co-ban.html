Sau bài này bạn sẽ

  • Giải thích được tool use (còn gọi là function calling) là một "hợp đồng" giữa ứng dụng và model: Claude chỉ yêu cầu gọi tool, không tự chạy code.
  • Phân biệt ba nhóm tool theo nơi code chạy: user-defined tools, Anthropic-schema tools và server tools.
  • Viết được một tool definition đầy đủ name, description, input_schema (và tùy chọn input_examples), với mô tả đủ chi tiết.
  • Đọc được khối tool_use trong response khi stop_reason là "tool_use", và gửi lại khối tool_result đúng quy tắc định dạng.
  • Báo lỗi tool bằng is_error: true, xử lý trường hợp tool_use bị cắt do max_tokens.
  • Ước lượng được phần token phát sinh khi dùng tool và nhận diện rủi ro indirect prompt injection trong kết quả tool.

🛠️Tool use là gì?

Tool use cho phép Claude gọi các hàm do bạn định nghĩa hoặc do Anthropic cung cấp. Claude tự quyết định khi nào gọi tool dựa trên yêu cầu của người dùng và phần mô tả của tool, rồi trả về một lời gọi có cấu trúc. Lời gọi đó được ứng dụng của bạn thực thi (client tools) hoặc Anthropic thực thi (server tools).

Tài liệu Anthropic gọi tool use là một tool-use contract. Bạn khai báo có những thao tác nào và dữ liệu vào/ra của chúng có hình dạng ra sao. Claude quyết định gọi thao tác nào, lúc nào, với tham số gì. Điểm mấu chốt: model không bao giờ tự chạy bất cứ thứ gì. Nó chỉ sinh ra một yêu cầu có cấu trúc. Code của bạn (hoặc server của Anthropic) chạy thao tác, rồi kết quả được đưa trở lại cuộc hội thoại.

Ví dụ đời thường

Hãy hình dung Claude là một trợ lý ngồi trong phòng kín, chỉ liên lạc với bên ngoài qua phiếu yêu cầu. Bạn đưa cho trợ lý một danh mục các mẫu phiếu (tool definitions): "phiếu tra thời tiết – cần ghi tên thành phố", "phiếu tra tồn kho – cần ghi mã sản phẩm". Trợ lý điền phiếu (tool_use) và chuyển ra ngoài. Nhân viên của bạn thực hiện, ghi kết quả vào phiếu trả lời (tool_result) có số phiếu khớp với phiếu gốc (tool_use_id). Trợ lý đọc kết quả rồi trả lời khách.

Với kỹ sư đã quen API truyền thống, tool use giống một giao diện có kiểu dữ liệu: định nghĩa schema, xử lý callback, trả kết quả. Khác biệt duy nhất là "bên gọi" là một mô hình ngôn ngữ, chọn hàm dựa trên nội dung hội thoại.

Khi nào nên dùng tool, khi nào không

✅Nên dùng tool

  • Hành động có side effects: gửi email, ghi file, cập nhật bản ghi. Model chỉ mô tả được, tool mới làm được.
  • Dữ liệu mới hoặc bên ngoài: giá hiện tại, thời tiết hôm nay, nội dung database.
  • Cần đầu ra đúng hình dạng: một object JSON có trường cụ thể, thay vì văn xuôi.
  • Gọi vào hệ thống sẵn có: database, API nội bộ, filesystem.

⛔Không cần tool

  • Model trả lời được từ kiến thức huấn luyện: tóm tắt, dịch, câu hỏi kiến thức chung.
  • Hỏi–đáp một lượt, không có tác dụng phụ: không có gì để "chạy".
  • Độ trễ của tool lấn át câu trả lời đơn giản: mỗi lời gọi tool tốn ít nhất một vòng request thêm.
Mẹo thực chiến (Pro Tip)

Tài liệu Anthropic đưa ra một dấu hiệu rất thực tế: nếu bạn đang viết regex để rút một quyết định ra khỏi câu trả lời của model, thì quyết định đó lẽ ra phải là một lời gọi tool. Việc phân tích văn bản tự do để lấy ý định có cấu trúc cho thấy cấu trúc đó nên nằm trong schema.

Claude quyết định gọi tool như thế nào

Với tool_choice mặc định là {"type": "auto"}, ở mỗi lượt Claude tự quyết định gọi tool hay trả lời trực tiếp. Claude gọi tool khi yêu cầu khớp với năng lực mà tool mô tả và câu trả lời chưa có sẵn trong ngữ cảnh. Claude trả lời trực tiếp với kiến thức ổn định, tác vụ sáng tạo và các lượt trò chuyện.

Bạn có thể điều chỉnh ranh giới này bằng system prompt:

  • "Use the tools to investigate before responding." – tăng mức dùng tool (nhẹ).
  • "Always call a tool first before responding." – đẩy mạnh hơn.
  • "Use your judgment about whether to call a tool or respond directly." – giữ hành vi gọi tool thận trọng.

Muốn bắt buộc gọi tool thay vì chỉ nhắc bằng prompt thì dùng tham số tool_choice (chi tiết ở Bài 18). Lưu ý theo tài liệu (kiểm tra ngày 2026-11-20): một số model như Claude Opus 5.5 và Claude Sonnet 5.5 không hỗ trợ ép tool (any/tool trả lỗi 400); khi đó dùng auto kết hợp strict tool use.

Khi thiếu tham số bắt buộc

Nếu prompt không đủ thông tin để điền mọi tham số bắt buộc, tài liệu cho biết Claude Opus nhiều khả năng sẽ nhận ra và hỏi lại. Claude Sonnet có thể hỏi (nhất là khi được nhắc suy nghĩ trước khi gọi tool), nhưng cũng có thể tự suy ra một giá trị hợp lý. Ví dụ hỏi "Thời tiết thế nào?" mà không nói địa điểm, Claude có thể đoán "location": "New York, NY". Hành vi này không được bảo đảm.

🗺️Tool chạy ở đâu? Ba nhóm tool

Trục phân loại quan trọng nhất của tool là code chạy ở đâu. Mỗi tool thuộc một trong ba nhóm, và nhóm quyết định ứng dụng của bạn phải làm gì.

📐Định nghĩa tool: name, description, input_schema

Client tools được khai báo trong tham số cấp cao nhất tools của request – một mảng các tool definition. Mỗi định nghĩa do bạn tự viết gồm các trường sau.

TrườngBắt buộc?Ý nghĩa (theo tài liệu Anthropic)

Ví dụ: tool get_weather

// Một phần tử trong mảng "tools" của request
{
  "name": "get_weather",
  "description": "Get the current weather in a given location",
  "input_schema": {
    "type": "object",                      // object ở cấp ngoài cùng
    "properties": {
      "location": {
        "type": "string",
        "description": "The city and state, e.g. San Francisco, CA"
      },
      "unit": {
        "type": "string",
        "enum": ["celsius", "fahrenheit"], // chỉ nhận 1 trong 2 giá trị
        "description": "The unit of temperature, either 'celsius' or 'fahrenheit'"
      }
    },
    "required": ["location"]                // location bắt buộc, unit tùy chọn
  }
}

Tool này tên get_weather, nhận một object với location (chuỗi, bắt buộc) và unit (chuỗi, tùy chọn, chỉ là celsius hoặc fahrenheit). Mỗi thuộc tính trong properties cũng nên có description riêng – đó là "hướng dẫn điền phiếu" cho Claude.

Mô tả tool – yếu tố quan trọng nhất

Tài liệu Anthropic nhấn mạnh: mô tả cực kỳ chi tiết là yếu tố quan trọng nhất, vượt xa mọi yếu tố khác đối với hiệu quả của tool. Mô tả nên giải thích:

  • Tool làm gì.
  • Khi nào nên dùng (và khi nào không nên dùng).
  • Mỗi tham số có nghĩa gì và ảnh hưởng thế nào tới hành vi của tool.
  • Các lưu ý, giới hạn quan trọng – ví dụ tool không trả về thông tin gì.

Mục tiêu: ít nhất 3–4 câu cho mỗi mô tả tool, nhiều hơn nếu tool phức tạp.

👍Mô tả tốt

{
  "name": "get_stock_price",
  "description": "Retrieves the current stock price
   for a given ticker symbol. The ticker symbol must be
   a valid symbol for a publicly traded company on a major
   US stock exchange like NYSE or NASDAQ. The tool will
   return the latest trade price in USD. It should be used
   when the user asks about the current or most recent
   price of a specific stock. It will not provide any
   other information about the stock or company.",
  "input_schema": { "type": "object",
    "properties": { "ticker": { "type": "string",
      "description": "The stock ticker symbol,
       e.g. AAPL for Apple Inc." } },
    "required": ["ticker"] }
}
  • Nói rõ làm gì, phạm vi (sàn Mỹ), đơn vị (USD), khi nào dùng, không trả gì.
  • Tham số có mô tả và ví dụ.

👎Mô tả kém

{
  "name": "get_stock_price",
  "description": "Gets the stock price
   for a ticker.",
  "input_schema": { "type": "object",
    "properties": {
      "ticker": { "type": "string" } },
    "required": ["ticker"] }
}
  • Quá ngắn: sàn nào? giá gì? đơn vị? dùng lúc nào?
  • Tham số ticker không có mô tả ⇒ Claude phải đoán định dạng.

(Chuỗi mô tả được ngắt dòng cho dễ đọc; trong JSON thật nó nằm trên một dòng.)

Các nguyên tắc thiết kế tool khác (Best practices)

  1. Ưu tiên mô tả, cân nhắc input_examples cho tool phức tạp – với input lồng nhau, nhiều tham số tùy chọn hoặc nhạy định dạng (ngày giờ, mã), thêm ví dụ đã được kiểm tra theo schema.
  2. Gom các thao tác liên quan vào ít tool hơn – thay vì create_pr, review_pr, merge_pr, dùng một tool có tham số action. Ít tool mạnh hơn ⇒ Claude bớt phân vân khi chọn.
  3. Đặt tên có namespacing – khi tool trải nhiều dịch vụ, thêm tiền tố: github_list_prs, slack_send_message. Đặc biệt quan trọng khi dùng tool search.
  4. Chỉ trả về thông tin "tín hiệu cao" – trả định danh ổn định, có nghĩa (slug, UUID) thay vì tham chiếu nội bộ khó hiểu; chỉ trả các trường Claude cần cho bước tiếp theo. Response cồng kềnh lãng phí context.
  5. Hỏi "giải thích", đừng hỏi "suy luận" – nếu một tham số yêu cầu Claude nói vì sao gọi tool, hãy xin một lời giải thích ngắn hoặc bằng chứng. Tham số đòi "chuỗi suy luận từng bước" có thể dẫn tới refusal loại reasoning_extraction.

input_examples – cho Claude xem mẫu

# Python – thêm ví dụ input vào tool definition
tools = [{
    "name": "get_weather",
    "description": "Get the current weather in a given location",
    "input_schema": weather_schema,        # schema như ví dụ ở trên
    "input_examples": [
        {"location": "San Francisco, CA", "unit": "fahrenheit"},
        {"location": "Tokyo, Japan", "unit": "celsius"},
        {"location": "New York, NY"},   # cho thấy 'unit' là tùy chọn
    ],
}]
  • Ví dụ phải hợp lệ: tự kiểm tra từng ví dụ theo input_schema. API thường trả lỗi 400 với ví dụ sai; có trường hợp (vd schema có pattern) API bỏ qua bước kiểm tra và Claude nhìn thấy ví dụ sai.
  • Chi phí token: mỗi ví dụ thêm khoảng 100 input token nếu chỉ vài giá trị phẳng, khoảng 200 token nếu có object lồng nhau (theo tài liệu, kiểm tra ngày 2026-11-20).
  • Hỗ trợ cho user-defined tools và một số Anthropic-schema client tools.

Tool use system prompt – chuyện gì xảy ra phía sau

Khi bạn gửi tham số tools, API tự dựng một system prompt đặc biệt từ các tool definition, cấu hình tool và system prompt của bạn. Theo tài liệu, khung của nó có dạng:

In this environment you have access to a set of tools you can use to answer the user's question.
{{ FORMATTING INSTRUCTIONS }}
String and scalar parameters should be specified as is, while lists and objects should use JSON format. ...
Here are the functions available in JSONSchema format:
{{ TOOL DEFINITIONS IN JSON SCHEMA }}
{{ USER SYSTEM PROMPT }}
{{ TOOL CONFIGURATION }}

Hệ quả thực tế: tên, mô tả, schema của tool đều là một phần của prompt – tốn input token và ảnh hưởng trực tiếp tới hành vi của Claude. Viết mô tả tool chính là viết prompt.

Mẹo thực chiến (Pro Tip)

Claude chọn nhầm giữa hai tool na ná nhau (vd search_orders và search_customers) ⇒ việc đầu tiên là viết lại description nêu rõ khi nào dùng tool này và khi nào không; nếu vẫn nhầm, cân nhắc gom thành một tool có tham số phân loại, hoặc thêm namespacing.

Lỗi thường gặp
  • Đặt tên tool có dấu cách, dấu chấm hoặc tiếng Việt có dấu (vd "tra cứu.đơn") ⇒ vi phạm regex ^[a-zA-Z0-9_-]{1,128}$, request bị từ chối.
  • Quên "type": "object" ở cấp ngoài cùng của input_schema, hoặc quên liệt kê trường bắt buộc trong required.
  • Mô tả một dòng kiểu "Gets data" ⇒ Claude gọi tool sai lúc, hoặc không gọi.

📤Khối tool_use và stop_reason: "tool_use"

Khi Claude quyết định gọi một client tool, response có stop_reason bằng "tool_use" và chứa một hoặc nhiều content block loại tool_use.

// Response mẫu (rút gọn) – theo tài liệu "Handle tool calls"
{
  "id": "msg_01Aq9w938a90dw8q",
  "model": "claude-opus-5-5",
  "stop_reason": "tool_use",            // ⇐ tín hiệu: "hãy chạy tool giúp tôi"
  "role": "assistant",
  "content": [
    {
      "type": "text",                      // Claude thường nói trước mình sắp làm gì
      "text": "I'll check the current weather in San Francisco for you."
    },
    {
      "type": "tool_use",
      "id": "toolu_01A09q90qw90lq917835lq9", // định danh duy nhất của lời gọi
      "name": "get_weather",                // tool nào
      "input": { "location": "San Francisco, CA", "unit": "celsius" }
    }
  ]
}

id

Định danh lời gọi

Duy nhất cho từng khối tool_use. Dùng để ghép với kết quả: tool_result.tool_use_id phải bằng đúng giá trị này.

🏷️

name

Tên tool được gọi

Trùng với name trong tool definition. Ứng dụng dùng nó để dispatch tới đúng hàm.

📦

input

Tham số đầu vào

Một object (SDK trả về dạng đã parse, không phải chuỗi JSON) tuân theo input_schema của tool.

Lưu ý content là một mảng: Claude thường kèm một khối text giải thích trước khi gọi tool. Đây là phong cách tự nhiên giúp người dùng hiểu Claude đang làm gì. Code của bạn nên coi phần text đó như mọi văn bản do model sinh ra – không dựa vào câu chữ hay định dạng cụ thể của nó, và phải duyệt mảng để tìm khối có type == "tool_use" thay vì giả định nó nằm ở content[0].

assistantIt's currently 15°C in San Francisco. stop_reason: "end_turn"
Mẹo thực chiến (Pro Tip)

Viết code dựa trên stop_reason, không dựa trên việc "có chữ nào đó trong text". stop_reason == "tool_use" ⇒ chạy tool rồi gửi kết quả; giá trị khác (end_turn, max_tokens, stop_sequence, refusal…) ⇒ thoát vòng và xử lý theo từng trường hợp.

📥Gửi kết quả bằng khối tool_result

Nhận được response tool_use, ứng dụng chạy tool rồi gửi một request mới chứa kết quả trong khối tool_result. Tài liệu Anthropic mô tả quy trình năm bước.

  1. Chạy tool – với mỗi khối tool_use, chạy tool có tên trong name, truyền input vào.
  2. Giữ lịch sử – trong request mới, giữ các message trước đó và thêm nguyên vẹn content của response làm một message assistant (đừng chỉ lấy phần text).
  3. Thêm message user chứa một khối tool_result cho mỗi khối tool_use – kể cả khi tool lỗi.
  4. Gửi lại cùng mảng tools như request đầu. Claude dùng kết quả để tiếp tục trả lời.
  5. Lặp – nếu response tiếp theo lại có stop_reason: "tool_use", làm lại các bước trên (vòng lặp đầy đủ học ở Bài 18).

Quy tắc định dạng bắt buộc

  • Ngay sau, không xen giữa: khối tool_result phải đi ngay sau khối tool_use tương ứng trong lịch sử hội thoại. Không được chèn bất kỳ message nào giữa message assistant có tool_use và message user có tool_result.
  • tool_result đứng trước: trong message user chứa kết quả, các khối tool_result phải nằm ĐẦU mảng content. Text (nếu có) phải nằm SAU tất cả tool result.
  • Nếu lượt assistant đó còn gọi một server tool chưa có kết quả, message user phải chỉ chứa khối tool_result (chi tiết ở Bài 19).

Lỗi thường gặp

Thông báo lỗi dạng "tool_use ids were found without tool_result blocks immediately after" nghĩa là: bạn quên gửi tool_result cho một (hoặc vài) tool_use, gửi sai tool_use_id, hoặc chèn message khác vào giữa. Hãy kiểm tra: mỗi tool_use.id trong message assistant cuối đều có đúng một tool_result tương ứng ở message user kế tiếp.

Khác biệt so với API khác

Một số API dùng role riêng như tool hay function. Claude API thì không: tool được tích hợp thẳng vào cấu trúc message user/assistant. Message assistant chứa nội dung do AI sinh và tool_use; message user chứa nội dung phía client và tool_result.

Báo lỗi với is_error

Khi client tool thất bại hoặc lời gọi không hợp lệ, vẫn gửi tool_result nhưng đặt is_error: true. Claude có thể gọi lại tool bằng một khối tool_use mới, hoặc giải thích cho người dùng – vì vậy hãy giới hạn số lần thử lại trong vòng lặp của bạn.

Mẹo thực chiến (Pro Tip)

Viết thông báo lỗi có tính hướng dẫn. Thay vì chuỗi chung chung "failed", hãy nói điều gì sai và Claude nên thử gì tiếp, vd "Rate limit exceeded. Retry after 60 seconds.". Claude có đủ ngữ cảnh để phục hồi mà không phải đoán.

Với server tools thì khác: bạn không gửi is_error. Khi server tool gặp lỗi (vd lỗi mạng lúc web search), API trả lỗi nằm bên trong khối kết quả của tool đó, và Claude thường tự chuyển hướng hoặc giải thích cho người dùng.

🔁Ghép lại: một vòng tool use hoàn chỉnh

Ví dụ dưới đây dựa trên ví dụ chính thức trong trang "Tool use with Claude": định nghĩa tool get_weather, nhận tool_use, chạy hàm, gửi tool_result, rồi in câu trả lời cuối.

Python

import json
import anthropic

client = anthropic.Anthropic()  # đọc ANTHROPIC_API_KEY từ biến môi trường – không hard-code key
MODEL = "claude-opus-5-5"       # model ID theo Models overview (kiểm tra ngày 2026-11-20)

tools = [{
    "name": "get_weather",
    "description": "Get the current weather for a given location.",
    "input_schema": {
        "type": "object",
        "properties": {
            "location": {"type": "string",
                         "description": "City and state, e.g. San Francisco, CA"}
        },
        "required": ["location"],
    },
}]

def get_weather(location: str) -> str:
    # Thay bằng lời gọi API thời tiết thật của bạn
    return "15 degrees Celsius, partly cloudy"

messages = [{"role": "user", "content": "What's the weather in San Francisco?"}]

# ① Request đầu: gửi messages + tools
response = client.messages.create(
    model=MODEL, max_tokens=1024, tools=tools,
    # Chỉ cho phép tối đa 1 lời gọi tool mỗi lượt (đơn giản hóa cho bài này)
    tool_choice={"type": "auto", "disable_parallel_tool_use": True},
    messages=messages,
)

if response.stop_reason == "tool_use":
    # ② Tìm khối tool_use trong mảng content (không giả định nó ở content[0])
    tool_use = next(b for b in response.content if b.type == "tool_use")
    print(f"Claude called {tool_use.name} with {json.dumps(tool_use.input)}")

    # ③ Ứng dụng tự chạy tool – có bắt lỗi để trả is_error
    try:
        result = {"type": "tool_result", "tool_use_id": tool_use.id,
                  "content": get_weather(**tool_use.input)}
    except Exception as e:
        result = {"type": "tool_result", "tool_use_id": tool_use.id,
                  "content": f"Error: {e}", "is_error": True}

    # ④ Thêm nguyên content của assistant + message user chứa tool_result
    messages += [
        {"role": "assistant", "content": response.content},
        {"role": "user", "content": [result]},
    ]

    # ⑤ Request thứ hai – CÙNG mảng tools
    followup = client.messages.create(
        model=MODEL, max_tokens=1024, tools=tools,
        tool_choice={"type": "auto", "disable_parallel_tool_use": True},
        messages=messages,
    )
    print(next(b.text for b in followup.content if b.type == "text"))
else:
    # Claude trả lời thẳng, không cần tool
    print(next((b.text for b in response.content if b.type == "text"), ""))

💰Chi phí token khi dùng tool

Tool use được tính phí như mọi request Claude API: theo tổng input token (gồm cả tham số tools) và output token sinh ra. Server tools có thể tính thêm phí theo lượt dùng.

Token phát sinh do tool đến từ ba nguồn:

  • Tham số tools trong request (tên, mô tả, schema của tool).
  • Các khối tool_use trong request và response.
  • Các khối tool_result trong request.

Ngoài ra, khi có tools, API tự thêm một system prompt đặc biệt để bật tool use. Số token của phần này tùy model và tùy tool_choice:

Mẹo thực chiến (Pro Tip)

Hóa đơn tăng sau khi thêm 30 tool vào chatbot ⇒ nhớ rằng mọi tool definition được gửi ở mỗi request. Hãy chỉ gửi những tool cần cho tác vụ, rút gọn kết quả tool về các trường "tín hiệu cao", và về sau dùng prompt caching (Module 4) hoặc tool search cho thư viện tool lớn.

🔐Bảo mật khi dùng tool

Tool cho Claude "tay chân" để tác động lên hệ thống thật. Điều đó mở ra các rủi ro mà một chatbot thuần văn bản không có.

Prompt injection gián tiếp qua tool_result

Kết quả tool thường chứa nội dung từ nguồn bạn không kiểm soát: trang web, email đến, file người dùng tải lên, API bên thứ ba. Tài liệu Anthropic khuyến cáo coi nội dung đó là không tin cậy: kẻ tấn công có thể nhúng chỉ thị nhằm điều hướng Claude – gọi là indirect prompt injection.

  • Giữ nội dung không tin cậy bên trong khối tool_result, không đưa vào system prompt hay khối text thường của user.
  • Tham khảo thêm hướng dẫn "Mitigate jailbreaks and prompt injections" của Anthropic để gia cố.

Nguyên tắc từ phía ứng dụng

  1. Least privilege – mỗi tool chỉ làm đúng việc cần thiết. Tool tra cứu dùng tài khoản DB chỉ đọc; đừng đưa tool run_sql tùy ý.
  2. Kiểm tra input trước khi chạy – coi tool_use.input như dữ liệu người dùng: kiểm tra kiểu, phạm vi, whitelist; dùng truy vấn tham số hóa để tránh SQL injection, không ghép chuỗi vào lệnh shell (theo IPA「安全なウェブサイトの作り方」).
  3. Xác nhận của con người cho hành động không đảo ngược được – gửi email, chuyển tiền, xóa dữ liệu ⇒ chèn bước human-in-the-loop trước khi thực thi.
  4. Không lộ bí mật – API key gọi dịch vụ bên ngoài đặt trong biến môi trường/secret manager phía server; không đưa vào mô tả tool hay tool_result.
  5. Giới hạn số lần thử lại và ghi log – mỗi lời gọi tool (tên, input đã lọc thông tin nhạy cảm, kết quả, lỗi) được ghi lại để kiểm toán.
Lỗi thường gặp

"Claude chỉ gọi tool khi người dùng yêu cầu hợp lệ, nên khỏi cần kiểm tra input." – Sai. Input của tool do model sinh ra dựa trên hội thoại, có thể bị ảnh hưởng bởi người dùng xấu hoặc nội dung bị nhiễm độc từ tool trước. Mọi kiểm tra quyền và dữ liệu phải nằm ở code của bạn, không phải trong prompt.

    Kết quả mong đợi: request có tools tốn nhiều input token hơn – gồm phần tool use system prompt (theo bảng ở trên) cộng với token của tool definition.

Tóm tắt ghi nhớ

Key takeaways
  • Tool use là một hợp đồng: bạn khai báo tool, Claude quyết định gọi; model không bao giờ tự chạy code.
  • Ba nhóm tool theo nơi chạy: user-defined (client), Anthropic-schema (client: bash, text_editor, memory, computer, browser), server tools (web_search, web_fetch, code_execution, tool_search).
  • Tool definition: name (regex ^[a-zA-Z0-9_-]{1,128}$), description, input_schema (JSON Schema), tùy chọn input_examples. Mô tả chi tiết là yếu tố quan trọng nhất – ít nhất 3–4 câu.
  • Client tool: response có stop_reason: "tool_use" + khối tool_use (id, name, input).
  • Trả lời bằng message user chứa tool_result (tool_use_id, content, is_error): ngay sau message assistant, tool_result đứng đầu mảng, mỗi tool_use một kết quả, gửi kèm cùng mảng tools.
  • Lỗi tool ⇒ is_error: true với thông báo có hướng dẫn; giới hạn số lần thử lại. tool_use bị cắt do max_tokens ⇒ gửi lại với max_tokens cao hơn.
  • Tool tốn token: tool definitions, khối tool_use/tool_result và một tool use system prompt tự động (vd 286 token với Claude Opus 5.5).
  • Coi tool_result từ nguồn ngoài là không tin cậy (indirect prompt injection); áp dụng least privilege và kiểm tra input trong code.

Thuật ngữ (Glossary)

Tool use (function calling)
Sử dụng công cụ – cơ chế để Claude yêu cầu ứng dụng (hoặc Anthropic) gọi một hàm/API bên ngoài bằng lời gọi có cấu trúc.
Tool-use contract
Hợp đồng tool use – bạn khai báo thao tác và hình dạng dữ liệu; Claude quyết định khi nào, gọi thế nào; code của bạn hoặc server chạy thao tác.
Client tool
Công cụ phía client – tool do ứng dụng của bạn thực thi và trả tool_result.
User-defined tool
Tool do người dùng định nghĩa – bạn viết schema và cài đặt; loại phổ biến nhất.
Anthropic-schema tool
Tool có schema do Anthropic công bố – memory, bash, text_editor, computer, browser; schema được huấn luyện sẵn, ứng dụng vẫn thực thi.
Server tool
Công cụ phía server – Anthropic thực thi (web_search, web_fetch, code_execution, tool_search); response chứa khối server_tool_use.
Tool definition
Định nghĩa công cụ – phần tử trong mảng tools: name, description, input_schema, tùy chọn input_examples.
input_schema
Lược đồ đầu vào – object JSON Schema mô tả các tham số tool nhận.
JSON Schema
Lược đồ JSON – chuẩn mô tả cấu trúc dữ liệu JSON (type, properties, required, enum…).
input_examples
Ví dụ đầu vào – mảng input mẫu hợp lệ theo schema, giúp Claude gọi tool phức tạp đúng định dạng.
tool_use block
Khối tool_use – content block trong response assistant, gồm id, name, input.
tool_result block
Khối kết quả công cụ – content block trong message user, gồm tool_use_id, content, is_error.
tool_use_id
Mã ghép kết quả – bằng id của khối tool_use mà kết quả trả lời.
is_error
Cờ lỗi – true khi tool thất bại hoặc lời gọi không hợp lệ.
stop_reason: "tool_use"
Lý do dừng: gọi tool – tín hiệu Claude đang chờ ứng dụng chạy tool và trả kết quả.
Tool use system prompt
System prompt cho tool – prompt API tự dựng từ tool definitions khi có tools, tốn thêm token cố định theo model.
Namespacing
Tiền tố phân vùng tên – đặt tên tool có tiền tố dịch vụ (github_list_prs) để tránh nhầm lẫn.
Tool runner
Bộ chạy tool tự động của SDK – SDK tự chạy tool và gửi kết quả về thay cho bạn.
Indirect prompt injection
Chèn lệnh độc hại gián tiếp – chỉ thị độc hại nằm trong dữ liệu ngoài (web, email, file) đi vào qua tool_result.
Least privilege
Đặc quyền tối thiểu – chỉ cấp cho tool đúng quyền cần thiết.

Câu hỏi luyện tập

Một startup thương mại điện tử muốn chatbot trả lời "Đơn hàng #A123 của tôi đang ở đâu?" bằng dữ liệu từ hệ thống vận chuyển nội bộ. Nhóm mới làm quen Claude API hỏi: khi Claude "gọi" tool get_order_status, chuyện gì thực sự xảy ra?
  1. Claude kết nối trực tiếp tới database vận chuyển bằng thông tin trong description và tự chạy truy vấn.
  2. Anthropic tự động gọi API nội bộ của công ty thay cho ứng dụng.
  3. Claude trả về khối tool_use có tên tool và input; ứng dụng của công ty tự chạy hàm rồi gửi kết quả lại bằng tool_result.
  4. Claude sinh ra code Python và API tự thực thi đoạn code đó trong sandbox.
Đáp án C. Theo "tool-use contract", model không bao giờ tự chạy gì; với user-defined client tool, ứng dụng nhận tool_use, thực thi và trả tool_result. A sai: Claude không có kết nối mạng tới hệ thống của bạn và chỉ thấy schema, không thấy cài đặt. B sai: Anthropic chỉ thực thi server tools (web search, code execution…), không gọi API nội bộ của bạn. D sai: đó là mô tả gần với server tool code_execution, không phải cơ chế của client tool.
Đọc request sau. Vì sao API từ chối? 
"tools": [{
  "name": "tra cứu đơn hàng",
  "description": "Look up an order by ID...",
  "input_schema": {"type": "object",
    "properties": {"order_id": {"type": "string"}},
    "required": ["order_id"]}
}]
  1. name chứa dấu cách và ký tự có dấu, vi phạm regex ^[a-zA-Z0-9_-]{1,128}$.
  2. input_schema bắt buộc phải có trường input_examples.
  3. required phải nằm ngoài input_schema, ngang hàng với name.
  4. Tham số order_id phải có kiểu integer mới hợp lệ.
Đáp án A. Tên tool chỉ được chứa chữ cái Latin, số, _ và -, dài 1–128 ký tự; nên đổi thành lookup_order. B sai: input_examples là tùy chọn và nằm cạnh input_schema, không nằm trong nó. C sai: required là từ khóa JSON Schema, nằm đúng chỗ bên trong input_schema. D sai: kiểu string hoàn toàn hợp lệ cho mã đơn hàng.
Nhóm phát triển nhận response có stop_reason: "tool_use". Theo tài liệu "Handle tool calls", request tiếp theo phải thỏa mãn những điều nào? (Chọn 2)
  1. Chỉ giữ phần text của response làm message assistant, bỏ khối tool_use để tiết kiệm token.
  2. Thêm nguyên vẹn content của response làm message assistant, rồi một message user có một tool_result cho mỗi tool_use.
  3. Gửi kết quả trong một message có role: "tool".
  4. Gửi kèm cùng mảng tools như request đầu tiên.
  5. Bỏ qua tool_result cho những tool bị lỗi, chỉ gửi kết quả thành công.
Đáp án B, D. Tài liệu yêu cầu thêm nguyên content của assistant, một tool_result cho mỗi tool_use (kể cả khi lỗi), và gửi lại cùng tools. A sai: thiếu khối tool_use thì tool_result không có gì để ghép, gây lỗi. C sai: Claude API không có role tool; kết quả nằm trong message user. E sai: tool lỗi vẫn phải có tool_result với is_error: true.
Lập trình viên gửi message sau và nhận lỗi 400. Nguyên nhân là gì? 
{"role": "user", "content": [
  {"type": "text", "text": "Đây là kết quả tra cứu:"},
  {"type": "tool_result", "tool_use_id": "toolu_01X...",
   "content": "Còn 42 cái"}
]}
  1. content của tool_result phải là một mảng, không được là chuỗi.
  2. Message chứa tool_result phải có role: "assistant".
  3. Thiếu trường is_error: false bắt buộc.
  4. Khối text đứng trước tool_result; các khối tool_result phải nằm đầu mảng content.
Đáp án D. Quy tắc: trong message user chứa kết quả, tool_result phải đứng ĐẦU, text (nếu có) đứng SAU. A sai: content có thể là chuỗi hoặc danh sách block. B sai: tool_result luôn nằm trong message user. C sai: is_error là tùy chọn, chỉ cần đặt true khi có lỗi.
Một ngân hàng có hai tool search_transactions và search_statements. Claude thường xuyên chọn nhầm. Theo tài liệu Anthropic, cải tiến nào nên làm đầu tiên?
  1. Chuyển sang model lớn hơn mà không đổi gì khác.
  2. Viết lại description thật chi tiết cho từng tool: làm gì, khi nào dùng, khi nào không dùng, trả về gì, mỗi tham số nghĩa là gì.
  3. Rút gọn mô tả còn một câu để Claude đỡ rối.
  4. Đổi tên tool thành tool1 và tool2 để tránh trùng từ "search".
Đáp án B. Tài liệu nói mô tả cực kỳ chi tiết là "yếu tố quan trọng nhất" với hiệu quả tool, nên dài ít nhất 3–4 câu. A sai: đổi model có thể giúp nhưng không giải quyết gốc rễ là mô tả mơ hồ, và tốn chi phí hơn. C sai: ngược với khuyến nghị; mô tả ngắn để lại nhiều câu hỏi bỏ ngỏ. D sai: tên vô nghĩa làm việc chọn tool khó hơn; nên dùng tên có ý nghĩa, có namespacing.
Tool gọi API tỷ giá bị lỗi "429 Too Many Requests". Cách gửi kết quả nào phù hợp nhất?
  1. {"type": "tool_result", "tool_use_id": "...", "content": "Rate limit exceeded. Retry after 60 seconds.", "is_error": true}
  2. Không gửi gì, chờ 60 giây rồi gửi lại request đầu tiên từ đầu.
  3. {"type": "tool_result", "tool_use_id": "...", "content": "failed"}
  4. Gửi một message user dạng text "API lỗi rồi" thay cho tool_result.
Đáp án A. Dùng is_error: true kèm thông báo có hướng dẫn (điều gì sai, nên thử gì tiếp) – đúng ví dụ trong tài liệu. B sai: tool_use phải được trả lời bằng tool_result; bỏ lửng làm hỏng cấu trúc hội thoại. C sai: thiếu is_error và thông báo "failed" quá chung chung, Claude không biết cách phục hồi. D sai: thiếu khối tool_result cho tool_use ⇒ lỗi "tool_use ids were found without tool_result blocks immediately after".
Đọc đoạn code sau. Rủi ro lớn nhất là gì? 
response = client.messages.create(..., max_tokens=200, tools=tools, messages=messages)
block = response.content[-1]
if block.type == "tool_use":
    run_tool(block.name, block.input)
  1. response.content không bao giờ chứa khối tool_use khi có text.
  2. Phải đọc block.arguments thay vì block.input.
  3. Code không kiểm tra stop_reason; nếu response dừng vì max_tokens, khối tool_use cuối có thể chưa hoàn chỉnh mà vẫn bị chạy.
  4. max_tokens không ảnh hưởng tới tool use nên không có rủi ro gì.
Đáp án C. Tài liệu nêu: nếu bị cắt vì max_tokens và khối cuối là tool_use dở dang, phải gửi lại với max_tokens cao hơn. Code nên rẽ nhánh theo stop_reason. A sai: response thường có cả text lẫn tool_use. B sai: trường đúng là input. D sai: max_tokens nhỏ có thể cắt ngang lời gọi tool.
Một công ty xây trợ lý đọc email đến và có tool send_email. Những biện pháp nào phù hợp với khuyến nghị bảo mật? (Chọn 2)
  1. Giữ nội dung email đến bên trong khối tool_result và coi nó là dữ liệu không tin cậy (nguy cơ indirect prompt injection).
  2. Dán nội dung email đến vào system prompt để Claude chú ý hơn.
  3. Yêu cầu người dùng xác nhận trước khi ứng dụng thực sự chạy send_email, và kiểm tra địa chỉ người nhận trong code.
  4. Ghi API key của dịch vụ email vào description của tool để Claude tự gửi.
  5. Tin tưởng hoàn toàn tool_use.input vì Claude đã được huấn luyện an toàn.
Đáp án A, C. Tài liệu khuyên giữ nội dung không tin cậy trong tool_result, không đưa vào system prompt; hành động không đảo ngược nên có human-in-the-loop và kiểm tra trong code. B sai: đưa nội dung không tin cậy vào system prompt làm tăng tác động của prompt injection. D sai: lộ bí mật trong prompt, và Claude không tự gửi email – ứng dụng mới thực thi. E sai: input do model sinh dựa trên hội thoại có thể bị thao túng; phải kiểm tra theo least privilege.
Một nhóm DevOps muốn Claude chạy lệnh shell trong container nội bộ của họ (không phải sandbox của Anthropic). Lựa chọn nào phù hợp nhất?
  1. Server tool web_fetch.
  2. Tự định nghĩa tool run_command với mô tả một dòng.
  3. Server tool code_execution, vì Anthropic sẽ chạy lệnh trong container của họ.
  4. Anthropic-schema tool bash: Claude gọi theo schema đã được huấn luyện, còn ứng dụng của nhóm thực thi lệnh trong container và trả tool_result.
Đáp án D. bash là Anthropic-schema client tool: schema "trained-in" nên Claude gọi ổn định hơn tool tự chế, và việc thực thi vẫn ở môi trường của bạn. A sai: web_fetch chỉ lấy nội dung trang web. B sai: tự chế được nhưng kém tin cậy hơn schema được huấn luyện, và mô tả một dòng là thực hành kém. C sai: code_execution chạy trong sandbox của Anthropic, không phải container nội bộ của nhóm.
Kỹ sư FinOps thấy input token mỗi request tăng sau khi bật tool cho chatbot dùng Claude Opus 5.5 (tool_choice mặc định). Giải thích nào đúng theo tài liệu?
  1. Tool use luôn bị tính phí cố định theo số lần gọi tool, kể cả user-defined tools.
  2. Input token tăng do tool definitions trong tools, các khối tool_use/tool_result, và một tool use system prompt tự động (286 token với Claude Opus 5.5 ở chế độ auto).
  3. API tự gửi kèm toàn bộ mã nguồn hàm của bạn cho Claude.
  4. Token chỉ tăng ở output, input không đổi.
Đáp án B. Mục Pricing liệt kê đúng ba nguồn token phát sinh, cộng với system prompt tool use theo model (Claude Opus 5.5: 286 token cho auto/none, theo tài liệu kiểm tra ngày 2026-11-20). A sai: client tools tính như request thường; phí theo lượt chỉ áp dụng cho một số server tools (vd web search). C sai: Claude không bao giờ nhận cài đặt, chỉ nhận schema và kết quả. D sai: phần lớn token phát sinh nằm ở input.
