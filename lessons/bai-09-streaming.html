Sau bài này bạn sẽ

  • Giải thích được vì sao nên bật streaming ("stream": true) và khi nào nó gần như bắt buộc (request dài, max_tokens lớn).
  • Đọc được luồng server-sent events (SSE) của Messages API: message_start → các content block → message_delta → message_stop.
  • Phân biệt các loại delta: text_delta, input_json_delta, thinking_delta, signature_delta.
  • Dùng streaming helper của Python SDK và TypeScript SDK (messages.stream(), text_stream, get_final_message() / finalMessage()).
  • Ghép đúng tool input từ các mảnh JSON, hiểu fine-grained tool streaming (eager_input_streaming).
  • Xử lý error event giữa stream, ping, sự kiện lạ, và khôi phục stream bị ngắt theo đúng thế hệ model.

🌊Streaming là gì và vì sao cần

Khi tạo một Message, bạn có thể đặt "stream": true để nhận phản hồi dần dần qua server-sent events (SSE), thay vì chờ toàn bộ câu trả lời được sinh xong rồi mới nhận một lần.

Ở chế độ thường (non-streaming), ứng dụng gửi request rồi im lặng chờ đến khi Claude viết xong chữ cuối cùng. Với câu trả lời dài, người dùng nhìn màn hình trống hàng chục giây. Ở chế độ streaming, chữ đầu tiên xuất hiện ngay khi model bắt đầu sinh. Đại lượng người dùng cảm nhận rõ nhất vì thế là time to first token (TTFT), chứ không phải tổng thời gian.

Ví dụ đời thường

Non-streaming giống như đặt in cả cuốn sách rồi mới được đọc. Streaming giống như nghe người kể chuyện: câu chuyện vẫn dài như vậy, nhưng bạn bắt đầu nghe ngay từ câu đầu tiên, và có thể bảo "dừng lại" giữa chừng nếu thấy lạc đề.

Ba lý do chính để dùng streaming

  1. Trải nghiệm người dùng – chatbot, trợ lý viết, giao diện hỏi đáp hiển thị chữ ngay khi có, giảm cảm giác "treo".
  2. Request chạy lâu – tài liệu lỗi của Anthropic khuyến nghị dùng streaming Messages API hoặc Message Batches API cho request chạy lâu, đặc biệt là trên 10 phút. Một số mạng có thể ngắt kết nối "im lặng" (idle) sau một khoảng thời gian, khiến request non-streaming thất bại mà không nhận được phản hồi.
  3. max_tokens lớn – SDK chính thức kiểm tra rằng request non-streaming của bạn không dự kiến vượt quá timeout 10 phút. Với max_tokens lớn, SDK yêu cầu dùng streaming để tránh HTTP timeout.

📡Server-sent events và luồng sự kiện

Mỗi server-sent event gồm một tên sự kiện (dòng event: ...) và dữ liệu JSON đi kèm (dòng data: ...). Trường type trong JSON luôn trùng với tên sự kiện, ví dụ event: message_stop đi với {"type": "message_stop"}.

Mọi stream đều tuân theo cùng một trình tự:

  1. message_start – chứa một object Message với content rỗng (cùng id, model, usage ban đầu).
  2. Một chuỗi content block – mỗi block có content_block_start, số lượng bất kỳ content_block_delta, rồi content_block_stop. Mỗi block có index ứng với vị trí của nó trong mảng content của Message cuối cùng.
  3. Một hoặc nhiều message_delta – thay đổi ở cấp cao nhất của Message, như stop_reason, stop_sequence và usage.
  4. message_stop – sự kiện kết thúc.

Xen giữa có thể có bất kỳ số lượng sự kiện ping nào, và đôi khi có sự kiện error.

Ví dụ: request và luồng phản hồi đầy đủ

Request giống hệt non-streaming, chỉ thêm "stream": true. Lưu ý API key đọc từ biến môi trường, không viết thẳng vào lệnh.

🧩Các loại delta trong content block

Mỗi content_block_delta mang một delta cập nhật cho content block tại index tương ứng. Loại delta phụ thuộc vào loại block.

Loại deltaThuộc blockTrường dữ liệuGhi chú
text_deltatexttextMảnh văn bản; nối liên tiếp là ra câu trả lời
input_json_deltatool_usepartial_jsonChuỗi JSON từng phần; tool_use.input cuối cùng luôn là object
thinking_deltathinkingthinkingNội dung suy luận khi bật thinking cùng streaming
signature_deltathinkingsignatureGửi ngay trước content_block_stop; dùng để xác minh tính toàn vẹn của thinking block

Text delta

event: content_block_delta
data: {"type": "content_block_delta","index": 0,"delta": {"type": "text_delta", "text": "ello frien"}}

Chú ý mảnh "ello frien": ranh giới mảnh không trùng với ranh giới từ hay câu. Đừng xử lý từng mảnh như một từ hoàn chỉnh (ví dụ để dịch hay lọc từ cấm) – hãy làm trên văn bản đã gom.

Input JSON delta

Với block tool_use, các delta là cập nhật cho trường input. Để đạt độ chi tiết tối đa, delta là chuỗi JSON từng phần, trong khi tool_use.input cuối cùng luôn là object. Bạn gom các chuỗi lại và parse khi nhận content_block_stop, hoặc dùng thư viện parse JSON từng phần (tài liệu nêu Pydantic), hoặc dùng streaming helper của SDK.

event: content_block_delta
data: {"type": "content_block_delta","index": 1,"delta": {"type": "input_json_delta","partial_json": "{\"location\": \"San Fra"}}}

Mặc định, API đệm (buffer) từng cặp key–value trong input cho đến khi đủ, rồi mới phát ra thành nhiều content_block_delta chứa JSON từng phần. Vì thế với tool, có thể có khoảng lặng giữa các event trong lúc model sinh một giá trị dài.

Thinking delta và signature delta

Khi dùng thinking với streaming, nội dung suy luận tới qua thinking_delta. Ngay trước content_block_stop của thinking block có một signature_delta đặc biệt. Nếu cấu hình thinking đặt display: "omitted", không có chữ suy luận nào được stream: block mở ra, nhận một thinking_delta với chuỗi rỗng, rồi một signature_delta, rồi đóng.

event: content_block_delta
data: {"type": "content_block_delta", "index": 0, "delta": {"type": "thinking_delta", "thinking": "I need to find the GCD of 1071 and 462 using the Euclidean algorithm.\n\n1071 = 2 × 462 + 147"}}

event: content_block_delta
data: {"type": "content_block_delta", "index": 0, "delta": {"type": "signature_delta", "signature": "EqQBCgIYAhIM1gbcDa9GJwZA2b3hGgxBdjrkzLoky3dl1pkiMOYds..."}}

Block đến "nguyên khối", không có delta

Một số block tới trọn vẹn ngay trong content_block_start, không có delta nào: redacted_thinking, kết quả của server tool như web_search_tool_result, và block fallback ở ranh giới model khi có server-side fallback. Code của bạn phải chấp nhận block có 0 delta.

Mẹo thực chiến (Pro Tip)

Đừng giả định block index: 0 luôn là text. Khi có thinking (ví dụ ở các model thinking luôn bật như Claude Opus 5.5), block đầu có thể là thinking; khi có tool, có thể có block tool_use xen giữa. Luôn rẽ nhánh theo content_block.type và delta.type, gom theo index.

🧰Streaming bằng SDK Python và TypeScript

Tài liệu Anthropic khuyên dùng SDK chính thức khi stream. Python SDK và TypeScript SDK có nhiều cách stream; Python SDK hỗ trợ cả stream đồng bộ (sync) lẫn bất đồng bộ (async). Chỉ khi tự tích hợp HTTP trực tiếp bạn mới phải tự phân tích từng event.

Cách 1 – Chỉ lấy chữ: text_stream / .on("text")

# Python – in chữ ngay khi tới
import anthropic

client = anthropic.Anthropic()  # đọc ANTHROPIC_API_KEY từ biến môi trường

with client.messages.stream(
    max_tokens=1024,
    messages=[{"role": "user", "content": "Hello"}],
    model="claude-opus-5-5",
) as stream:
    for text in stream.text_stream:   # chỉ lặp qua các text delta
        print(text, end="", flush=True)
// TypeScript – đăng ký handler cho sự kiện "text"
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic(); // đọc ANTHROPIC_API_KEY từ biến môi trường

await client.messages
  .stream({
    messages: [{ role: "user", content: "Hello" }],
    model: "claude-opus-5-5",
    max_tokens: 1024,
  })
  .on("text", (text) => {
    process.stdout.write(text);
  });

Cách 2 – Duyệt từng event (có kiểu)

Lặp trực tiếp trên stream để nhận cả event thô của API lẫn các event "mở rộng" mà SDK thêm vào. Theo trang helpers của Python SDK, các event mở rộng gồm:

input_jsonCó một JSON content_block_deltaevent.partial_json (mảnh), event.snapshot (JSON đã gom)
content_block_stopMột ContentBlock đã gom đầy đủevent.content_block

// TypeScript – duyệt event thô, chỉ in text_delta
const stream = client.messages.stream({
  model: "claude-opus-5-5",
  messages: [{ role: "user", content: "Hello" }],
  max_tokens: 256,
});

for await (const event of stream) {
  if (event.type === "content_block_delta" && event.delta.type === "text_delta") {
    process.stdout.write(event.delta.text);
  }
}

Cách 3 – Stream ngầm, chỉ lấy Message cuối

# Python – max_tokens lớn: SDK yêu cầu stream để tránh HTTP timeout
with client.messages.stream(
    max_tokens=128000,
    messages=[{"role": "user", "content": "Write a detailed analysis..."}],
    model="claude-opus-5-5",
) as stream:
    message = stream.get_final_message()   # chặn tới khi xong, trả về Message đầy đủ

for block in message.content:
    if block.type == "text":
        print(block.text)
// TypeScript – tương đương
const stream = client.messages.stream({
  max_tokens: 128000,

Phiên bản async (Python)

# AsyncAnthropic + async with + async for – hợp với web server (FastAPI, aiohttp…)
import asyncio, anthropic

client = anthropic.AsyncAnthropic()

async def main():
    async with client.messages.stream(
        max_tokens=1024,
        messages=[{"role": "user", "content": "Say hello there!"}],
        model="claude-opus-5-5",
    ) as stream:
        async for text in stream.text_stream:
            print(text, end="", flush=True)
        final = await stream.get_final_message()
        print("\nstop_reason:", final.stop_reason)

asyncio.run(main())

Các method hữu ích của MessageStream (Python)

  • close() – hủy request (ví dụ người dùng bấm "Dừng"). Thoát khỏi khối with cũng hủy stream.
  • until_done() – chờ tới khi stream được đọc hết.
  • get_final_message() – chờ xong rồi trả về Message đã gom.
  • get_final_text() – chờ xong rồi trả về nội dung các text block nối lại.

🌊messages.create(stream=True)

  • Trả về iterable các event thô.
  • Không tự gom Message cuối ⇒ tốn ít bộ nhớ hơn.
  • Bạn tự xử lý index, delta, usage.
  • Dùng khi chỉ chuyển tiếp (proxy) event hoặc cần kiểm soát tối đa.

🧰messages.stream()

  • Phát event thô và event tiện lợi (text, input_json…).
  • Tự gom thành Message (get_final_message()).
  • Có text_stream, close(), until_done().
  • Lựa chọn mặc định cho hầu hết ứng dụng.
Lỗi thường gặp

Gọi get_final_message() sau khi thoát khối with trong khi chưa đọc hết stream bên trong. Trang helpers ghi rõ: chỉ gọi được sau khi thoát nếu toàn bộ stream đã được tiêu thụ bên trong context manager – vì thoát khối with sẽ hủy stream.

🛠️Streaming với tool use và fine-grained tool streaming

Khi Claude quyết định gọi tool (tool use), stream sẽ có thêm một block tool_use. Block này mở bằng content_block_start chứa input: {} – một object rỗng chỉ để giữ chỗ. Giá trị thật tới dần qua các input_json_delta.

Hợp đồng ghép mảnh (accumulation contract)

  1. Gặp content_block_start có type: "tool_use" ⇒ khởi tạo chuỗi rỗng: input_json = "".
  2. Mỗi content_block_delta có type: "input_json_delta" ⇒ nối thêm: input_json += event.delta.partial_json.
  3. Gặp content_block_stop ⇒ parse chuỗi đã gom (bọc trong try).

Sự "lệch kiểu" giữa input: {} (object) lúc đầu và partial_json (chuỗi) là có chủ đích: object rỗng đánh dấu vị trí trong mảng content, các chuỗi delta mới xây nên giá trị thật.

Fine-grained tool streaming – eager_input_streaming

Fine-grained tool streaming giao tool input tới client ngay khi Claude sinh ra, không đệm và không kiểm tra JSON ở phía server. Bỏ bước đệm giúp giảm thời gian tới mảnh đầu tiên của một tham số lớn (một tài liệu, một khối code). Theo tài liệu (kiểm tra 2026-11-20), tính năng ở trạng thái stable và dùng được trên mọi model.

  • Bật từng tool bằng trường tùy chọn "eager_input_streaming": true trong tool definition, và bật streaming cho request.
  • Bỏ trường này ⇒ streaming đệm như chuẩn (API đệm và kiểm tra từng giá trị tham số trước khi gửi).
  • Header beta cũ fine-grained-tool-streaming-2025-05-14 bật tính năng cho các tool không đặt trường; trường theo từng tool thay thế header này, và đặt false tường minh sẽ giữ chế độ đệm kể cả khi request gửi header.
# Python – bật fine-grained streaming cho một tool, gom và parse có bảo vệ
import json, anthropic

client = anthropic.Anthropic()
tool_inputs: dict[int, str] = {}   # index -> chuỗi JSON đã gom

with client.messages.stream(
    model="claude-opus-5-5",
    max_tokens=1024,
    tools=[{
        "name": "get_weather",
        "description": "Get current weather for a city",
        "eager_input_streaming": True,          # bật cho riêng tool này
        "input_schema": {
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"],
        },
    }],
    messages=[{"role": "user", "content": "Weather in Paris?"}],
) as stream:
    for event in stream:
        match event.type:
            case "content_block_start" if event.content_block.type == "tool_use":
                tool_inputs[event.index] = ""
            case "content_block_delta" if event.delta.type == "input_json_delta":
                tool_inputs[event.index] += event.delta.partial_json
            case "content_block_stop" if event.index in tool_inputs:
                raw = tool_inputs[event.index]
                try:
                    print("Tool input:", json.loads(raw))
                except json.JSONDecodeError:
                    # Chuỗi gom được KHÔNG đảm bảo là JSON hợp lệ
                    print("Invalid tool input:", raw)
Lỗi thường gặp

Vì API không đệm và không kiểm tra input khi bật eager_input_streaming, bạn có thể nhận JSON dở dang hoặc không hợp lệ. Phản hồi kết thúc với stop_reason = max_tokens cũng có thể cắt ngang một tham số. Luôn bọc lệnh parse, kiểm tra stop_reason, rồi quyết định retry với max_tokens lớn hơn hay sửa input dở dang.

Trả JSON hỏng lại cho Claude

Khi input không parse được, bạn không chạy được tool – hãy báo lỗi lại cho Claude. Tài liệu đề xuất bọc chuỗi gốc trong một object một khóa INVALID_JSON, tuần tự hóa thành chuỗi, rồi đặt vào tool_result với is_error: true:

{
  "type": "tool_result",
  "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
  "is_error": true,
  "content": "{\"INVALID_JSON\": \"<the unparseable input you received>\"}"
}

Hãy dựng object này bằng thư viện JSON (json.dumps, JSON.stringify) thay vì nối chuỗi thủ công, để dấu nháy và ký tự đặc biệt được escape đúng.

Mẹo thực chiến (Pro Tip)

Tool write_file nhận cả nội dung file dài, người dùng phàn nàn "đứng hình" vài giây rồi mới hiện code ⇒ bật eager_input_streaming: true cho riêng tool đó. Mảnh JSON tới ngay từ lúc Claude bắt đầu tham số, và thường dài hơn, ít bị cắt giữa từ hơn. Đổi lại, nhớ thêm parse có bảo vệ.

Lưu ý về model và tool_choice

Ví dụ tool streaming trong tài liệu Streaming dùng tool_choice: {"type": "any"} với claude-opus-5. Tuy nhiên trang Claude API errors ghi: Claude Opus 5.5, Sonnet 5.5 (và một số model khác) không hỗ trợ forced tool use – gửi "any" hoặc "tool" sẽ nhận lỗi 400. Với các model này, dùng auto (mặc định).

🧠Streaming thinking và server tools

Thinking

Khi bật thinking cùng streaming, thinking block được stream trước, rồi mới tới text block. Ví dụ trong tài liệu dùng thinking: {"type": "adaptive", "display": "summarized"} – thiết lập "summarized" stream một bản tóm tắt quá trình suy luận thay vì toàn bộ chuỗi suy nghĩ.

# Python – in cả thinking_delta và text_delta
with client.messages.stream(
    model="claude-opus-5-5",
    max_tokens=20000,
    thinking={"type": "adaptive", "display": "summarized"},
    messages=[{"role": "user",
               "content": "What is the greatest common divisor of 1071 and 462?"}],
) as stream:
    for event in stream:
        if event.type == "content_block_delta":
            delta = event.delta
            match delta.type:
                case "thinking_delta":
                    print(delta.thinking, end="", flush=True)
                case "text_delta":
                    print(delta.text, end="", flush=True)

Luồng phản hồi: block index: 0 có kiểu thinking (nhiều thinking_delta, kết thúc bằng một signature_delta), rồi block index: 1 kiểu text với câu trả lời "The greatest common divisor of 1071 and 462 is **21**."

Server tools (ví dụ web search)

Với server tool như web search ("type": "web_search_20250305"), stream có thể gồm: text block → block server_tool_use → block web_search_tool_result (tới nguyên khối) → các text block tiếp theo. message_delta cuối cùng có thể kèm usage.server_tool_use.web_search_requests.

Rủi ro prompt injection

Nội dung từ web search hay tool bên ngoài có thể chứa prompt injection. Streaming không làm rủi ro này mất đi: đừng tự động thực thi hành động nguy hiểm chỉ dựa trên văn bản đang stream; áp dụng nguyên tắc least privilege cho tool và xin xác nhận của người dùng trước thao tác ghi/xóa.

🚑Lỗi giữa stream và khôi phục

Error event

Ở chế độ streaming, request có thể đã nhận HTTP 200 rồi mới gặp lỗi. Khi đó lỗi không tới dưới dạng mã HTTP mà là một error event trong luồng SSE. Ví dụ lúc tải cao, bạn có thể nhận overloaded_error – thứ mà ở chế độ non-streaming thường tương ứng với HTTP 529:

event: error
data: {"type": "error", "error": {"type": "overloaded_error", "message": "Overloaded"}}
Mẹo thực chiến (Pro Tip)

Cơ chế tự retry của SDK (mặc định 2 lần, exponential backoff) áp dụng cho lỗi ở mức request như lỗi kết nối, 429, 5xx. Còn lỗi xảy ra sau khi đã nhận 200 giữa stream thì "không theo các cơ chế chuẩn" đó ⇒ ứng dụng cần tự bắt lỗi trong vòng lặp event, lưu phần đã nhận và quyết định khôi phục.

Khôi phục stream bị ngắt – phụ thuộc thế hệ model

Khi stream bị ngắt do mạng, timeout hay lỗi khác, bạn có thể tiếp tục từ chỗ bị ngắt thay vì sinh lại toàn bộ.

⏮️Claude 4.5 trở về trước

  1. Lưu toàn bộ nội dung đã nhận.
  2. Tạo request mới, đặt phần phản hồi dở dang làm đầu của một assistant message mới.
  3. Stream tiếp phần còn lại.

⏭️Claude 4.6 trở về sau

  1. Lưu toàn bộ nội dung đã nhận.
  2. Tạo request mới với một user message chứa phần phản hồi dở dang và lời dặn tiếp tục.
  3. Stream tiếp phần còn lại.
userYour previous response was interrupted and ended with [previous_response]. Continue from where you left off.
assistant(Claude viết tiếp phần còn thiếu…)

Lý do cách làm đổi ở thế hệ 4.6: các model Claude 4.6 trở về sau không hỗ trợ prefill assistant message – request kết thúc bằng một assistant message bị điền sẵn sẽ nhận lỗi 400 invalid_request_error.

Thực hành tốt khi khôi phục

  • Dùng tính năng của SDK – dựa vào khả năng gom message và xử lý lỗi sẵn có.
  • Chú ý loại content – message có thể chứa nhiều block (text, tool_use, thinking). Block tool_use và thinking không thể khôi phục một phần; bạn chỉ tiếp tục được từ text block gần nhất.
Lỗi thường gặp

Dùng mẹo "đặt phần dở dang vào assistant message" (cách của 4.5) cho claude-opus-5-5 ⇒ nhận lỗi 400 vì model không hỗ trợ prefill. Với model 4.6 trở về sau, hãy đặt phần dở dang vào user message kèm lời dặn "continue".

🏗️Đưa streaming lên giao diện web an toàn

Mô hình phổ biến: trình duyệt ↔ backend của bạn ↔ Claude API. Backend giữ API key, gọi messages.stream(), rồi chuyển tiếp từng mảnh chữ xuống trình duyệt (qua SSE hoặc WebSocket của riêng bạn).

Checklist bảo mật (theo tinh thần IPA「安全なウェブサイトの作り方」)

  • Không lộ API key – không gọi Claude API trực tiếp từ JavaScript phía trình duyệt bằng key của bạn. Trang lỗi của Anthropic còn ghi: với một số tổ chức (vd có thiết lập lưu trữ dữ liệu đặc biệt), request có header Origin từ trình duyệt sẽ bị từ chối 401 – hãy gửi từ backend.
  • Chống XSS khi hiển thị – văn bản stream về là dữ liệu không tin cậy (có thể bị prompt injection dẫn dắt). Gán bằng textContent hoặc escape trước khi chèn HTML; nếu render Markdown, dùng thư viện sanitize.
  • Giới hạn tài nguyên – đặt max_tokens hợp lý, cho người dùng hủy (stream.close()), và đóng kết nối upstream khi client ngắt để không tốn token vô ích.
  • Ghi log có kiểm soát – lưu id của message và header request-id để tra cứu với Anthropic support; tránh log dữ liệu cá nhân thô.

    Kết quả mong đợi: tổng thời gian hai cách gần như nhau, nhưng thời gian tới chữ đầu tiên của (b) ngắn hơn rõ rệt; số output_tokens trong usage tương đương. 
    import time, anthropic
client = anthropic.Anthropic()
prompt = [{"role": "user", "content": "Viết bài 800 từ về lịch sử Internet"}]

t0 = time.perf_counter(); first = None
with client.messages.stream(model="claude-opus-5-5", max_tokens=4096, messages=prompt) as s:
    for text in s.text_stream:
        if first is None:
            first = time.perf_counter() - t0
    msg = s.get_final_message()
print(f"TTFT={first:.2f}s  total={time.perf_counter()-t0:.2f}s  usage={msg.usage}")
  2. Bài tập 2 – Bộ phân tích event thủ công. Dùng client.messages.create(..., stream=True) (event thô) và tự viết vòng lặp: tạo dict blocks theo index ở content_block_start, nối text_delta, đọc stop_reason và usage.output_tokens mới nhất ở message_delta, bỏ qua ping và mọi type lạ.
    Kết quả mong đợi: văn bản ghép được trùng với get_final_text() của cách dùng helper; stop_reason là end_turn (hoặc max_tokens nếu bạn đặt max_tokens rất nhỏ, ví dụ 20 – hãy thử cả hai).
  3. Bài tập 3 – Tool input lớn với eager_input_streaming. Định nghĩa tool make_file (filename, lines_of_text) như trong tài liệu, yêu cầu "viết một bài thơ dài và tạo file poem.txt". Chạy hai lần: không có và có "eager_input_streaming": true; in mỗi partial_json ngay khi tới (Python: event input_json; TypeScript: stream.on("inputJson", ...)).
    Kết quả mong đợi: khi bật, mảnh JSON bắt đầu xuất hiện sớm hơn; ở content_block_stop bạn parse trong try. Nếu parse lỗi, tạo tool_result với is_error: true và content {"INVALID_JSON": ...} bằng json.dumps. Không thực sự ghi file ra đĩa ngoài thư mục tạm (least privilege).

Gửi request mới cho claude-opus-5-5 với user message theo mẫu "Your previous response was interrupted and ended with [...]. Continue from where you left off."
    Kết quả mong đợi: Claude viết tiếp mạch văn; ghép hai phần thành bài hoàn chỉnh. Thử đặt phần dở dang vào assistant message cuối và quan sát lỗi 400 (model 4.6+ không hỗ trợ prefill).

📌Tóm tắt ghi nhớ

Key takeaways
  • "stream": true ⇒ phản hồi tới qua SSE; giảm time to first token, không đổi tổng token hay chi phí.
  • Trình tự: message_start → (mỗi block: content_block_start → N × content_block_delta → content_block_stop) → ≥ 1 message_delta → message_stop; ping xen giữa bất kỳ lúc nào.
  • index của block = vị trí trong mảng content cuối. Gom theo index, rẽ nhánh theo type; bỏ qua event lạ.
  • usage trong message_delta là lũy kế – lấy giá trị cuối, không cộng dồn.
  • Delta: text_delta, input_json_delta (chuỗi JSON từng phần, parse ở content_block_stop), thinking_delta, signature_delta (ngay trước stop). Một số block tới nguyên khối.
  • SDK: messages.stream() + text_stream / get_final_message() (TS: .on("text"), finalMessage()); create(stream=True) cho event thô, ít bộ nhớ hơn.
  • max_tokens lớn / request > 10 phút ⇒ dùng streaming hoặc Message Batches; SDK chặn request non-streaming dự kiến vượt 10 phút.
  • eager_input_streaming: true (từng tool) ⇒ tool input tới sớm nhưng có thể là JSON hỏng ⇒ parse có bảo vệ, trả INVALID_JSON với is_error: true.
  • Lỗi sau HTTP 200 tới dưới dạng error event (vd overloaded_error). Khôi phục: 4.5 trở về trước dùng assistant message dở dang; 4.6 trở về sau dùng user message "continue". tool_use/thinking không khôi phục một phần.
  • Bảo mật: API key chỉ ở backend, escape văn bản stream trước khi render, cho phép hủy stream, least privilege cho tool.

📖Thuật ngữ (Glossary)

Streaming
Truyền dữ liệu từng phần – nhận phản hồi dần dần thay vì một lần; bật bằng "stream": true.
Server-sent events (SSE)
Sự kiện gửi từ máy chủ – chuẩn HTTP để server đẩy chuỗi sự kiện (event: + data:) xuống client qua một kết nối giữ mở.
Time to first token (TTFT)
Thời gian tới token đầu tiên – độ trễ từ lúc gửi request tới lúc nhận mảnh văn bản đầu tiên.
Content block
Khối nội dung – một phần tử trong mảng content (text, tool_use, thinking…), có index riêng.
Delta
Phần thay đổi / mảnh cập nhật – dữ liệu gia tăng trong content_block_delta hoặc message_delta.
message_start / message_stop
Sự kiện mở đầu (Message với content rỗng) và kết thúc của stream.
content_block_start / delta / stop
Bộ ba sự kiện mở, cập nhật và đóng một content block.
message_delta
Sự kiện cập nhật cấp Message: stop_reason, stop_sequence, usage (lũy kế).
ping
Sự kiện giữ kết nối – có thể xuất hiện bất kỳ lúc nào; bỏ qua.
Error event
Sự kiện lỗi – lỗi xảy ra giữa stream sau khi đã có HTTP 200, vd overloaded_error.
text_delta
Mảnh văn bản của text block (trường text).
input_json_delta
Mảnh chuỗi JSON từng phần (partial_json) của tool input.
thinking_delta / signature_delta
Mảnh nội dung suy luận, và chữ ký xác minh toàn vẹn thinking block (gửi ngay trước content_block_stop).
Partial JSON
JSON từng phần – chuỗi JSON chưa hoàn chỉnh; chỉ parse được khi đủ.
Accumulate / accumulator
Gom / bộ gom – ghép các event thành Message hoàn chỉnh (vd get_final_message()).
Fine-grained tool streaming
Streaming tool chi tiết – stream tool input không đệm, không kiểm tra JSON; bật bằng eager_input_streaming.
eager_input_streaming
Trường tùy chọn trong tool definition; true bật fine-grained streaming cho tool đó.
Buffering
Đệm – API giữ lại từng key–value của tool input tới khi đủ rồi mới gửi (mặc định).
Error recovery
Khôi phục lỗi – lưu phần đã nhận và gửi request tiếp tục từ chỗ bị ngắt.
Message Batches API
API xử lý lô – gửi nhiều request bất đồng bộ, poll lấy kết quả; không cần kết nối liên tục.
TCP keep-alive
Giữ kết nối TCP – tùy chọn socket giảm ảnh hưởng của việc mạng ngắt kết nối rảnh.

📝Câu hỏi luyện tập

Một startup xây chatbot hỗ trợ khách hàng. Người dùng phàn nàn rằng sau khi gửi câu hỏi, màn hình trống khoảng 15 giây rồi cả đoạn trả lời mới hiện ra. Tổng thời gian xử lý chấp nhận được. Cách nào cải thiện trải nghiệm phù hợp nhất?
  1. Chuyển sang Message Batches API để xử lý nhanh hơn.
  2. Giảm temperature về 0 để model sinh nhanh hơn.
  3. Bật "stream": true (hoặc dùng messages.stream()) và hiển thị từng text_delta ngay khi nhận.
  4. Tăng max_tokens để model không bị cắt ngang.
Đáp án C. Vấn đề là thời gian tới chữ đầu tiên (TTFT); streaming đưa văn bản tới dần qua SSE nên người dùng thấy chữ gần như ngay lập tức. A sai: Batches là xử lý bất đồng bộ, poll kết quả – không dành cho thời gian thực. B sai: temperature điều chỉnh độ ngẫu nhiên, không phải cơ chế giao kết quả. D sai: tăng max_tokens không làm chữ hiện sớm hơn.
Những phát biểu nào đúng về trình tự sự kiện của một streaming Message? (Chọn 2)
  1. message_start chứa một object Message có content rỗng.
  2. Mỗi content block luôn có ít nhất một content_block_delta.
  3. ping chỉ xuất hiện đúng một lần, ngay sau message_start.
  4. index của content block ứng với vị trí của nó trong mảng content của Message cuối cùng.
  5. message_stop chứa stop_reason và usage cuối cùng.
Đáp án A, D. Theo tài liệu, message_start mang Message với content rỗng, và index khớp vị trí trong mảng content cuối. B sai: có block tới nguyên khối, không delta (redacted_thinking, web_search_tool_result…). C sai: có thể có bất kỳ số lượng ping ở bất cứ đâu. E sai: stop_reason và usage nằm trong message_delta; message_stop chỉ là {"type": "message_stop"}.
Đoạn code ghi nhận chi phí của một nhóm dev nhận được hai sự kiện sau trong cùng một stream: 
event: message_delta
data: {"type":"message_delta","delta":{"stop_reason":null},"usage":{"output_tokens":40}}
event: message_delta
data: {"type":"message_delta","delta":{"stop_reason":"end_turn"},"usage":{"output_tokens":89}}
Nên ghi nhận output_tokens của message này là bao nhiêu?
  1. 129 – cộng hai giá trị.
  2. 89 – giá trị của message_delta cuối cùng.
  3. 40 – giá trị đầu tiên là chính xác nhất.
  4. 49 – hiệu của hai giá trị.
Đáp án B. Tài liệu cảnh báo: số token trong usage của message_delta là lũy kế (cumulative), nên giá trị cuối đã bao gồm các giá trị trước. A sai: cộng dồn sẽ tính trùng. C sai: 40 chỉ là số tại thời điểm giữa chừng. D sai: hiệu không có ý nghĩa ghi nhận chi phí.
Một job nội bộ sinh báo cáo phân tích rất dài với max_tokens=128000. Job không cần hiển thị gì trong lúc chạy, chỉ cần object Message cuối. Gọi messages.create() thường thì SDK báo lỗi. Giải pháp nào gọn nhất?
  1. Giảm max_tokens xuống thật nhỏ rồi gọi nhiều lần nối lại.
  2. Tự gọi HTTP bằng requests với timeout 60 phút để vượt qua kiểm tra của SDK.
  3. Dùng create(stream=True) rồi tự viết bộ gom mọi loại event.
  4. Dùng with client.messages.stream(...) as stream: rồi stream.get_final_message().
Đáp án D. Tài liệu chỉ rõ: SDK yêu cầu streaming cho max_tokens lớn để tránh HTTP timeout, và get_final_message() trả về Message giống hệt create(). A sai: phức tạp, dễ đứt mạch nội dung, không cần thiết. B sai: mạng có thể ngắt kết nối rảnh; tài liệu khuyên dùng streaming/Batches cho request dài. C sai: chạy được nhưng phải tự làm việc mà helper đã có sẵn – không "gọn nhất".
Đọc đoạn code xử lý tool input sau (event thô): 
buf = {}
for event in stream:
    if event.type == "content_block_start" and event.content_block.type == "tool_use":
        buf[event.index] = ""
    elif event.type == "content_block_delta" and event.delta.type == "input_json_delta":
        buf[event.index] += event.delta.partial_json
        args = json.loads(buf[event.index])   # (*)
        run_tool(args)
Vấn đề chính của dòng (*) là gì?
  1. Nó parse chuỗi JSON từng phần ở mỗi delta; chuỗi chỉ hoàn chỉnh khi tới content_block_stop, nên sẽ ném lỗi hoặc chạy tool nhiều lần với input dở dang.
  2. Phải dùng event.delta.text thay cho partial_json.
  3. input_json_delta chỉ xuất hiện khi bật eager_input_streaming.
  4. Nên khởi tạo buf[event.index] = {} vì input trong content_block_start là object.
Đáp án A. Hợp đồng ghép mảnh: khởi tạo chuỗi rỗng, nối partial_json, parse ở content_block_stop (có try). B sai: text là trường của text_delta, không phải tool input. C sai: input_json_delta có cả ở streaming chuẩn (đệm); eager_input_streaming chỉ bỏ bước đệm. D sai: input: {} chỉ là chỗ giữ; delta là chuỗi nên phải gom vào chuỗi.
Ứng dụng soạn code bật "eager_input_streaming": true cho tool write_file. Thỉnh thoảng chuỗi input gom được ở content_block_stop không parse được. Cách xử lý được tài liệu đề xuất là gì?
  1. Bỏ qua tool call và kết thúc hội thoại im lặng.
  2. Tự đoán và vá JSON rồi chạy tool như bình thường mà không báo cho Claude.
  3. Trả về một tool_result với is_error: true, content là chuỗi tuần tự hóa của {"INVALID_JSON": "<input nhận được>"} dựng bằng thư viện JSON.
  4. Bật thêm header fine-grained-tool-streaming-2025-05-14 để API kiểm tra JSON.
Đáp án C. Tài liệu: không chạy được tool thì báo lại cho Claude; bọc chuỗi gốc dưới khóa INVALID_JSON, đặt vào tool_result với is_error: true, dựng bằng thư viện JSON để escape đúng. A sai: Claude không biết chuyện gì xảy ra, trải nghiệm hỏng. B sai: tự vá có thể chạy tool với tham số sai – rủi ro, nhất là với thao tác ghi file. D sai: header đó chính là cách cũ để bật fine-grained streaming (không kiểm tra JSON), không phải để bật kiểm tra.
Trong giờ cao điểm, log của một ứng dụng streaming ghi nhận request trả HTTP 200, nhưng giữa chừng nhận được dòng sau: 
event: error
data: {"type": "error", "error": {"type": "overloaded_error", "message": "Overloaded"}}
Nhận định nào đúng?
  1. Đây là lỗi xác thực API key; cần tạo key mới.
  2. Đây là lỗi giữa stream, tương ứng HTTP 529 ở chế độ non-streaming; ứng dụng cần tự bắt trong vòng lặp event, giữ phần đã nhận và retry/khôi phục.
  3. SDK chắc chắn đã tự retry lỗi này nên không cần xử lý gì.
  4. Không thể xảy ra vì lỗi luôn được trả bằng mã HTTP trước khi stream bắt đầu.
Đáp án B. Tài liệu: trong streaming, lỗi có thể xảy ra sau khi API đã trả 200 và không theo cơ chế chuẩn; overloaded_error thường tương ứng HTTP 529. A sai: lỗi xác thực là authentication_error (401). C sai: tự retry của SDK áp cho lỗi ở mức request; lỗi sau 200 thì "không theo các cơ chế chuẩn". D sai: tài liệu nêu rõ lỗi có thể tới giữa stream.
Stream từ claude-opus-5-5 bị đứt mạng sau khi đã nhận được nửa bài viết (chỉ có text block). Nhóm dev muốn tiếp tục thay vì sinh lại từ đầu. Cách nào đúng theo tài liệu?
  1. Gửi lại request cũ, thêm một assistant message cuối chứa phần đã nhận để model viết tiếp (prefill).
  2. Gửi lại y nguyên request cũ; API tự nhớ vị trí bị ngắt.
  3. Gửi request mới với stop_sequences bằng câu cuối đã nhận.
  4. Gửi request mới với một user message chứa phần đã nhận và lời dặn "Your previous response was interrupted and ended with [...]. Continue from where you left off."
Đáp án D. Với Claude 4.6 trở về sau, bước 2 của chiến lược khôi phục là thêm user message chứa phần dở dang và lời dặn tiếp tục. A sai: đó là cách cho Claude 4.5 trở về trước; các model 4.6+ không hỗ trợ prefill và trả lỗi 400. B sai: Messages API stateless, không nhớ stream cũ. C sai: stop_sequences dùng để dừng sinh, không để tiếp tục.
Nhóm frontend muốn hiển thị câu trả lời stream của Claude trên trang web nội bộ. Những biện pháp nào phù hợp về bảo mật? (Chọn 2)
  1. Nhúng ANTHROPIC_API_KEY vào bundle JavaScript để trình duyệt gọi thẳng Claude API cho nhanh.
  2. Gọi Claude API từ backend (key trong biến môi trường/secret manager) và chuyển tiếp các mảnh văn bản xuống trình duyệt.
  3. Chèn từng text_delta bằng innerHTML để giữ định dạng Markdown/HTML do model sinh.
  4. Tắt max_tokens để câu trả lời không bao giờ bị cắt.
  5. Coi văn bản stream là dữ liệu không tin cậy: gán bằng textContent hoặc sanitize trước khi render.
Đáp án B, E. Key chỉ ở backend; đầu ra model có thể bị prompt injection dẫn dắt nên phải escape/sanitize để chống XSS. A sai: lộ key cho mọi người dùng; tài liệu còn ghi một số tổ chức bị từ chối 401 với request có Origin từ trình duyệt. C sai: innerHTML với dữ liệu không tin cậy là lỗ hổng XSS kinh điển. D sai: max_tokens là tham số bắt buộc và là công cụ giới hạn tài nguyên.
Vòng lặp xử lý stream của một dịch vụ được viết như sau: 
switch (event.type) {
  case "message_start": ...; break;
  case "content_block_delta": ...; break;
  case "message_stop": ...; break;
  default: throw new Error("Unknown event: " + event.type);
}
Rủi ro lớn nhất của nhánh default này là gì?
  1. Nó ném lỗi khi gặp ping, content_block_start/stop, message_delta hay loại sự kiện mới mà API có thể bổ sung – trong khi tài liệu yêu cầu xử lý sự kiện lạ một cách an toàn.
  2. Không có rủi ro; API cam kết chỉ có đúng 3 loại sự kiện này.
  3. Nhánh default làm tăng số token bị tính phí.
  4. message_stop không bao giờ được gửi nên vòng lặp không kết thúc.
Đáp án A. Stream có ping bất kỳ lúc nào, cùng content_block_start/stop, message_delta, error; và theo chính sách versioning, loại sự kiện mới có thể được thêm – code phải bỏ qua chúng an toàn. B sai: có nhiều loại hơn và có thể tăng thêm. C sai: xử lý phía client không ảnh hưởng token. D sai: message_stop luôn là sự kiện cuối của một stream bình thường.
