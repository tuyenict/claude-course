Sau bài này bạn sẽ

  • Gửi được hình ảnh cho Claude qua Messages API bằng image content block với ba loại nguồn: base64, url và file (file_id của Files API).
  • Nắm các giới hạn quan trọng: số ảnh mỗi request, kích thước tối đa, định dạng hỗ trợ, quy tắc “many-image request”.
  • Tự ước lượng số visual token của một ảnh bằng công thức ⌈width/28⌉ × ⌈height/28⌉ và hiểu hai mức phân giải (Standard / High-resolution).
  • Gửi PDF bằng document block, hiểu Claude xử lý PDF thế nào (văn bản + ảnh từng trang) và ước tính chi phí theo trang.
  • Kết hợp PDF với prompt caching, Message Batches và Files API; áp dụng các nguyên tắc bảo mật khi xử lý file do người dùng tải lên.

Mọi con số (giới hạn, giá, model ID) là theo tài liệu, kiểm tra ngày 2026-11-20 – các giá trị này có thể thay đổi, hãy đối chiếu lại tài liệu gốc trước khi đưa vào hệ thống thật.

Ví dụ 1 – ảnh base64 (Python)

# pip install anthropic   –   API key đọc từ biến môi trường ANTHROPIC_API_KEY
import base64
import anthropic

client = anthropic.Anthropic()  # KHÔNG hard-code API key trong mã nguồn

with open("hoa-don.jpg", "rb") as f:
    image_data = base64.standard_b64encode(f.read()).decode("utf-8")

message = client.messages.create(
    model="claude-opus-5-5",      # model ID lấy từ Models overview (kiểm tra 2026-11-20)
    max_tokens=1024,
    messages=[{
        "role": "user",
        "content": [
            {   # 1) Ảnh đặt TRƯỚC câu hỏi – cấu trúc khuyến nghị
                "type": "image",
                "source": {
                    "type": "base64",
                    "media_type": "image/jpeg",   # phải khớp định dạng thật của file
                    "data": image_data,
                },
            },
            {"type": "text", "text": "Mô tả nội dung hóa đơn này."},  # 2) Câu hỏi sau ảnh
        ],
    }],
)
print(message.content[0].text)

Files API đã ra khỏi beta

Theo trang Files API: API này không còn là beta và không cần beta header. Header cũ files-api-2025-04-14 vẫn chạy (trả về định dạng phản hồi kiểu beta) nhưng việc bỏ nó là tùy chọn. Với SDK, dùng client.files thay cho client.beta.files. Các thao tác upload, list, lấy metadata, xóa, download đều miễn phí; nội dung file chỉ bị tính tiền như input token khi được dùng trong Messages request.

Nhiều ảnh trong một request

Bạn có thể gửi nhiều ảnh trong một request; Claude phân tích chúng cùng lúc – hữu ích khi so sánh ảnh, tìm khác biệt, hoặc đọc một chuỗi trang tài liệu. Tài liệu khuyên đặt nhãn văn bản ngắn trước mỗi ảnh (Image 1:, Image 2:…) để có thể gọi tên chúng trong prompt và ở các lượt sau.

"content": [
  {"type": "text",  "text": "Image 1:"},
  {"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": "..."}},
  {"type": "text",  "text": "Image 2:"},
  {"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": "..."}},
  {"type": "text",  "text": "Hai ảnh này khác nhau ở điểm nào?"}
]

Trong hội thoại nhiều lượt, ảnh mới được thêm ở các lượt user sau theo cùng cách. Claude vẫn “thấy” mọi ảnh ở các lượt trước (vì toàn bộ lịch sử được gửi lại), nên câu hỏi kiểu “Ảnh này có giống hai ảnh đầu không?” vẫn hoạt động mà không phải đính kèm lại ảnh cũ trong nội dung lượt mới.

Mẹo thực chiến (Pro Tip)

Agent chụp màn hình liên tục / hội thoại nhiều lượt có nhiều ảnh ⇒ dùng Files API + file_id. Mỗi lượt API phải gửi lại toàn bộ lịch sử; nếu ảnh là base64, toàn bộ byte ảnh bị gửi lại mỗi lượt, làm request phình to và tăng độ trễ. file_id giữ payload nhỏ bất kể có bao nhiêu ảnh tích lũy.

Mẹo thực chiến (Pro Tip)

Ảnh trước, câu hỏi sau. Giống như đặt tài liệu dài lên trước câu hỏi trong prompt văn bản, Claude làm việc tốt nhất khi ảnh đứng trước text. Đặt ảnh sau hoặc xen kẽ vẫn chạy tốt, nhưng nếu được, hãy ưu tiên cấu trúc “ảnh → text”.

🔢Độ phân giải & chi phí token của ảnh

Claude không xử lý ảnh theo từng pixel mà theo patch: mỗi patch là một khối 28×28 pixel và được tính là một visual token. Do đó:

Công thức

visual tokens = ⌈width / 28⌉ × ⌈height / 28⌉  (⌈ ⌉ là làm tròn lên)

Hai mức phân giải (resolution tier)

Mỗi model có độ phân giải gốc tối đa, biểu diễn bằng giới hạn cạnh dài và giới hạn số visual token. Ảnh vượt một trong hai giới hạn sẽ được thu nhỏ (downscale) trước khi xử lý.

🖥️Standard

  • Áp dụng cho: các model còn lại (trước Claude 4.7, ví dụ Claude Haiku 4.5, Claude Sonnet 4.5).
  • Cạnh dài tối đa: 1.568 px.
  • Tối đa 1.568 visual token / ảnh.

🔬High-resolution

  • Áp dụng cho: Claude 4.7 và các model mới hơn.
  • Cạnh dài tối đa: 2.576 px.
  • Tối đa 4.784 visual token / ảnh.
  • Tự động bật – không cần beta header hay opt-in.

Khi thu nhỏ, Claude chọn kích thước lớn nhất giữ nguyên tỉ lệ khung hình mà thỏa cả hai giới hạn – nhờ vậy chi phí token có trần. Với hầu hết ảnh chụp và ảnh màn hình, giới hạn token mới là yếu tố quyết định kích thước cuối, không phải giới hạn cạnh. Ví dụ trong tài liệu: ảnh 1920×1080 thu về 1456×819 chứ không phải 1568×882. Ước tính chi phí tiền

Chi phí = số token × giá input của model. Ví dụ trong tài liệu (kiểm tra 2026-11-20):

  • Claude Haiku 4.5 ($1 / triệu input token, mức Standard): ảnh 1000×1000 (1.296 token) ≈ $1,30 / 1.000 ảnh.
  • Claude Opus 5.5 ($4 / triệu input token, mức High-res): cùng ảnh 1000×1000 ≈ $5,18 / 1.000 ảnh; ảnh 4K (4.784 token) ≈ $19,14 / 1.000 ảnh.

Ảnh ở mức High-res có thể tốn tới khoảng gấp ba số visual token so với cùng ảnh đó trên model mức Standard. Nếu bạn không cần độ chi tiết cao (vốn hữu ích cho computer use, hiểu ảnh chụp màn hình, tài liệu dày đặc chữ), hãy downsample ảnh trước khi gửi để kiểm soát chi phí và độ trễ.

Mẹo thực chiến (Pro Tip)

Phân loại hàng triệu ảnh sản phẩm, chỉ cần nhận diện loại mặt hàng ⇒ resize ảnh nhỏ lại trước khi gửi (ví dụ quanh 1000×1000 hoặc nhỏ hơn) + model rẻ + Message Batches. Ngược lại, đọc chữ nhỏ trên bản vẽ kỹ thuật ⇒ giữ độ phân giải cao, hoặc cắt (crop) vùng cần đọc rồi gửi phần cắt.

Khi ảnh bị resize: tọa độ & trường transformations

Với các tác vụ cần bounding box hoặc điểm ảnh (OCR theo vùng, trích form, tìm nút bấm trên UI), cần nhớ: tọa độ Claude trả về là tọa độ pixel tuyệt đối trên ảnh sau khi resize, gốc (0, 0) ở góc trên-trái. Sau resize, Claude còn đệm (pad) cạnh phải và cạnh dưới lên bội số gần nhất của 28 px (vùng đệm không có nội dung). Tài liệu nhấn mạnh:

  • Hãy yêu cầu rõ tọa độ pixel tuyệt đối trong prompt (ví dụ [x1, y1, x2, y2]); Claude làm kém khi bị yêu cầu tọa độ chuẩn hóa kiểu 0–1000. Muốn chuẩn hóa thì tự làm trong code.
  • Luôn quy đổi theo kích thước sau resize, không phải kích thước sau khi pad.
  • Cách chắc chắn nhất: tự resize ảnh trước khi gửi theo đúng thuật toán của Claude, để ảnh bạn có chính là ảnh Claude xử lý.
  • Giới hạn token có thể kích hoạt resize dù cả hai cạnh đều dưới giới hạn cạnh. Ví dụ: trang A4 quét 130 DPI = 1075×1520 px, tốn 39 × 55 = 2145 token > 1.568 ⇒ trên model mức Standard bị resize về 924×1307. Model mức High-res thì không resize ảnh này.

Để biến việc resize “âm thầm” thành lỗi rõ ràng, đặt trường tùy chọn transformations trên khối image:

{
  "type": "image",
  "source": { "type": "base64", "media_type": "image/png", "data": "..." },
  "transformations": { "oversized_image": "error" }   // mặc định là "downsize"
}

Khi đó, nếu ảnh cần bị thu nhỏ, request bị từ chối với lỗi 400 invalid_request_error nêu kích thước ảnh và kích thước lớn nhất được chấp nhận. Mỗi ảnh có thiết lập riêng, nên một request có thể trộn ảnh “quan trọng tọa độ” (đặt "error") với ảnh “resize cũng không sao” (logo…). Khối document (PDF) không nhận trường này.

Ngoại lệ: computer use / browser use

Ảnh chụp màn hình và ảnh zoom bạn trả về cho bộ công cụ computer use và browser use trong tool_result không được tự động resize: API từ chối ảnh vượt giới hạn của model bằng lỗi validation. Hãy resize trong ứng dụng trước khi trả về, rồi quy đổi tọa độ Claude trả về sang kích thước màn hình thật.

🔍Chất lượng ảnh & giới hạn của Vision

Hướng dẫn chất lượng ảnh

  1. Độ rõ nét – ảnh phải rõ, không quá mờ hay vỡ hạt.
  2. Chữ trong ảnh – nếu ảnh chứa chữ quan trọng, đảm bảo chữ đọc được, không quá nhỏ. Đừng cắt mất ngữ cảnh quan trọng chỉ để phóng to chữ.
  3. Resize – tính đến việc ảnh quá lớn sẽ bị thu nhỏ (có thể làm chữ khó đọc). Cân nhắc tự resize, crop, hoặc cả hai; đặt "oversized_image": "error" nếu không muốn bị resize.
  4. Nén ảnh – nén bằng định dạng có tổn hao (JPEG, WebP lossy) giúp request nhỏ hơn, giảm độ trễ, nhưng có thể tạo nhiễu (artifact) làm giảm chất lượng, nhất là khi nén nhiều lần; nén JPEG mạnh có thể làm chữ khó đọc. Hãy kiểm tra trực tiếp ảnh thật được gửi lên API.

📄PDF support: gửi tài liệu bằng document block

Bạn có thể hỏi Claude về mọi văn bản, hình ảnh, biểu đồ và bảng trong PDF qua document block. Tài liệu nêu các use case mẫu: phân tích báo cáo tài chính (hiểu biểu đồ/bảng), trích thông tin chính từ văn bản pháp lý, hỗ trợ dịch tài liệu, chuyển thông tin tài liệu sang định dạng có cấu trúc. Tất cả model đang hoạt động đều hỗ trợ PDF.

  • Cả hai giới hạn (kích thước, số trang) áp dụng cho toàn bộ request, gồm cả nội dung khác gửi kèm PDF.
  • PDF dày đặc (nhiều trang chữ nhỏ, bảng phức tạp, đồ họa nặng) có thể làm đầy context window trước khi chạm giới hạn trang. Hãy chia tài liệu thành nhiều phần; với file lớn, giảm độ phân giải ảnh nhúng trong PDF cũng có ích.

Các định dạng khác PDF

File văn bản thuần (.txt, .csv, .md) dùng được trực tiếp trong document block: tải lên Files API với MIME type text/plain và tham chiếu bằng file_id. Định dạng nhị phân như .xlsx, .docx không được hỗ trợ trong document block – hãy chuyển sang văn bản hoặc PDF trước. Với .docx có hình ảnh, tài liệu khuyên chuyển sang PDF để tận dụng khả năng đọc ảnh và citations.

Ba cách đưa PDF vào request

  1. PDF đã có trên mạng ⇒ tham chiếu bằng URL: {"type": "url", "url": "https://..."}.
  2. PDF nằm trên máy / không có URL ⇒ gửi base64: {"type": "base64", "media_type": "application/pdf", "data": "..."}.
  3. PDF lớn hoặc dùng lại nhiều lần ⇒ tải lên Files API rồi dùng {"type": "file", "file_id": "file_..."}.

{

Claude xử lý PDF như thế nào?

Theo tài liệu, quá trình gồm ba bước:

  1. Hệ thống trích xuất nội dung tài liệu – chuyển mỗi trang thành một ảnh và trích văn bản của từng trang, đặt kèm ảnh của trang đó.
  2. Claude phân tích cả văn bản và ảnh – vì có ảnh của từng trang, bạn có thể hỏi về biểu đồ, sơ đồ và các nội dung không phải chữ.
  3. Claude dùng nội dung PDF trong câu trả lời nếu liên quan, dựa trên cả phần chữ lẫn phần hình.

Ước tính chi phí PDF

Số token của một PDF phụ thuộc vào tổng văn bản trích được và số trang:

  • Token văn bản: mỗi trang thường dùng 1.500–3.000 token tùy mật độ nội dung. Tính theo giá API chuẩn, không có phí PDF riêng.
  • Token ảnh: ảnh của mỗi trang dùng tối đa 1.568 visual token trên mọi model, vì API luôn đưa ảnh trang về giới hạn của mức Standard (kể cả trên model mức High-res).

Dùng endpoint token counting để ước tính chính xác cho PDF cụ thể của bạn. Ước lượng thô (tự tính từ các con số trên, không phải số liệu tài liệu công bố): một PDF 100 trang có thể tốn khoảng 100 × (1.500–3.000) token văn bản cộng tối đa 100 × 1.568 token ảnh – tức vài trăm nghìn input token; hãy tính chi phí trước khi chạy hàng loạt.

Mẹo thực chiến (Pro Tip)

Cần bounding box chính xác trên nội dung PDF ⇒ đừng gửi PDF trực tiếp. Trang PDF được raster hóa phía server ở kích thước bạn không kiểm soát, nên tọa độ trả về không thể ánh xạ tin cậy về trang gốc. Hãy tự raster hóa từng trang thành ảnh, resize trước, rồi gửi dưới dạng image block.

🛡️Bảo mật khi xử lý ảnh & tài liệu

Ảnh và PDF thường đến từ người dùng cuối – tức là dữ liệu không tin cậy. Theo tinh thần các tài liệu IPA「安全なウェブサイトの作り方」/「セキュア・プログラミング講座」 (kiểm tra đầu vào, phân quyền tối thiểu, không để lộ dữ liệu của người khác), cần lưu ý:

  • Không nhận file_id từ người dùng cuối. Trang Files API cảnh báo: file được phân phạm vi theo workspace, không theo người dùng hay phiên. Bất kỳ API key nào có quyền vào workspace đều đọc được mọi file trong đó. Nếu chấp nhận file_id do người dùng gửi, một người có thể đọc file của người khác. Hãy coi file_id là tham chiếu phía server và tự lưu ánh xạ “người dùng ↔ file” trong ứng dụng.
  • Ứng dụng nhiều khách hàng (multitenant) ⇒ tạo workspace riêng cho mỗi tenant (workspace là ranh giới cô lập file) và dùng API key giới hạn theo workspace – đúng nguyên tắc least privilege.
  • Prompt injection qua ảnh/PDF: chữ trong ảnh hoặc trong PDF có thể chứa chỉ dẫn độc hại (“bỏ qua hướng dẫn trước đó…”). Hãy nói rõ trong system prompt rằng nội dung tài liệu là dữ liệu cần phân tích, không phải lệnh; không cấp cho model quyền gọi tool nguy hiểm chỉ dựa trên nội dung tài liệu; kiểm tra đầu ra trước khi thực thi hành động.
  • Kiểm tra đầu vào: xác thực MIME type thật, kích thước, số trang trước khi gửi; từ chối sớm PDF có mật khẩu (API không hỗ trợ); không đưa URL do người dùng nhập thẳng vào source.url mà không kiểm soát.
  • Dữ liệu nhạy cảm: PDF support đủ điều kiện Zero data retention (trừ Covered Models) và HIPAA – nhưng HIPAA chỉ áp dụng cho PDF gửi inline qua Messages API, không áp dụng khi gửi qua Files API. Files API không đủ điều kiện ZDR. Xóa file khi không còn dùng hoặc đặt expires_in_seconds.
  • API key luôn lấy từ biến môi trường ANTHROPIC_API_KEY, không hard-code, không đưa vào mã phía trình duyệt.
Lỗi thường gặp

Đưa file_id ra frontend rồi để frontend gửi lại file_id lên backend để “hỏi về tài liệu của tôi”. Kẻ tấn công chỉ cần đổi file_id là đọc được hợp đồng của khách hàng khác trong cùng workspace (lỗi kiểu IDOR – tham chiếu đối tượng trực tiếp không an toàn). Backend phải tự tra file_id từ ID người dùng đã xác thực.

    import math
from PIL import Image

def count_image_tokens(w: int, h: int) -> int:
    return math.ceil(w / 28) * math.ceil(h / 28)

def resized_size(w, h, max_edge=1568, max_tokens=1568):
    """Mặc định: mức Standard. Model High-res: max_edge=2576, max_tokens=4784."""
    def fits(a, b):
        return (math.ceil(a / 28) * 28 <= max_edge
                and math.ceil(b / 28) * 28 <= max_edge
                and count_image_tokens(a, b) <= max_tokens)
    if fits(w, h):
        return (w, h)
    if h > w:                                   # xử lý ảnh dọc bằng cách đảo chiều
        rh, rw = resized_size(h, w, max_edge, max_tokens)
        return (rw, rh)
    ratio, lo, hi = w / h, 1, w                 # tìm nhị phân cạnh dài lớn nhất còn "vừa"
    while lo + 1 < hi:
        mid = (lo + hi) // 2
        if fits(mid, max(round(mid / ratio), 1)):
            lo = mid
        else:
            hi = mid
    return (lo, max(round(lo / ratio), 1))

print(count_image_tokens(1000, 1000))   # 1296
print(resized_size(1920, 1080))         # (1456, 819) – mức Standard
print(resized_size(1075, 1520))         # (924, 1307) – ví dụ trang A4 130 DPI

img = Image.open("screenshot.png")
img.resize(resized_size(*img.size)).save("screenshot-resized.png")

Tóm tắt ghi nhớ

Key takeaways
  • Ảnh → khối image; PDF và file text/plain → khối document. Nguồn: base64 (kèm media_type), url, hoặc file (file_id từ Files API). Bedrock và Google Cloud (Google managed) chỉ hỗ trợ base64.
  • Đặt ảnh/PDF trước câu hỏi; nhiều ảnh thì gắn nhãn Image 1:, Image 2:…
  • Giới hạn ảnh: 600 ảnh/request API (100 với model context 200k), 20 ảnh/message trên claude.ai, tối đa 8000×8000 px, 10 MB/ảnh (base64) trên Claude API, 5 MB trên Bedrock; > 20 ảnh thì giới hạn kích thước chặt hơn (giữ cạnh ≤ 3.000 px).
  • Định dạng: JPEG, PNG, GIF, WebP; ảnh động chỉ lấy khung đầu.
  • Token ảnh = ⌈w/28⌉ × ⌈h/28⌉. Standard: cạnh ≤ 1.568 px, ≤ 1.568 token; High-res (Claude 4.7 trở về sau): cạnh ≤ 2.576 px, ≤ 4.784 token. Ảnh vượt trần bị thu nhỏ giữ tỉ lệ.
  • Tọa độ trả về theo ảnh đã resize; nên tự resize trước, hoặc dùng "transformations": {"oversized_image": "error"} để biến resize thành lỗi 400.
  • PDF: ≤ 128 MB/request (Claude API), ≤ 600 trang (100 nếu context < 1M), không mật khẩu. Mỗi trang = văn bản (~1.500–3.000 token) + ảnh (≤ 1.568 visual token).
  • Kết hợp PDF với prompt caching (cache_control), Message Batches, Files API (GA, không cần beta header, 500 MB/file, 1 TB/tổ chức).
  • Bảo mật: không nhận file_id từ người dùng; mỗi tenant một workspace; coi nội dung ảnh/PDF là dữ liệu không tin cậy (prompt injection); HIPAA chỉ cho PDF gửi inline.

Thuật ngữ (Glossary)

Vision
Khả năng hiểu hình ảnh – Claude nhận ảnh làm đầu vào, phân tích và trả lời bằng văn bản; không tạo/chỉnh sửa ảnh.
Image content block
Khối nội dung hình ảnh – {"type": "image", "source": {...}} trong content của message.
Document block
Khối tài liệu – {"type": "document", ...} dùng cho PDF và văn bản thuần; có trường tùy chọn title, context, citations.
Base64 source
Nguồn mã hóa base64 – nhúng byte file vào request, bắt buộc có media_type.
URL source
Nguồn theo đường dẫn – {"type": "url", "url": ...}; API tự tải file.
Files API / file_id
API quản lý file – tải lên một lần, tham chiếu bằng file_id; phạm vi theo workspace.
Media type (MIME type)
Kiểu nội dung – ví dụ image/png, application/pdf, text/plain.
Visual token / Patch
Token hình ảnh / ô ảnh – mỗi khối 28×28 pixel của ảnh là một visual token.
Resolution tier
Mức phân giải – Standard (1.568 px / 1.568 token) và High-resolution (2.576 px / 4.784 token, Claude 4.7 trở về sau).
Downsample / Downscale
Giảm độ phân giải / thu nhỏ ảnh – giảm token, chi phí và độ trễ.
Padding
Đệm ảnh – Claude đệm cạnh phải và dưới lên bội số của 28 px; vùng đệm không có nội dung.
Bounding box
Khung bao – tọa độ [x1, y1, x2, y2] của một vùng trong ảnh, tính theo pixel của ảnh sau resize.
transformations.oversized_image
Thiết lập xử lý ảnh quá cỡ – "downsize" (mặc định) hoặc "error" để từ chối thay vì thu nhỏ.
Many-image request
Request nhiều ảnh – request có hơn 20 ảnh, chịu giới hạn kích thước mỗi ảnh chặt hơn.
Rasterize
Raster hóa – chuyển trang PDF (vector/văn bản) thành ảnh điểm.
Prompt caching
Bộ nhớ đệm prompt – cache phần prompt lặp lại (ví dụ PDF) bằng cache_control.
Message Batches API
API xử lý theo lô – gửi nhiều request bất đồng bộ, mỗi request có custom_id.
Zero data retention (ZDR)
Không lưu giữ dữ liệu – chế độ dữ liệu không được lưu sau khi xử lý; PDF support đủ điều kiện, Files API thì không.
Workspace
Không gian làm việc – ranh giới cô lập file của Files API; nên tạo một workspace cho mỗi tenant.
Prompt injection
Chèn lệnh độc hại vào prompt – chỉ dẫn độc hại ẩn trong chữ của ảnh/PDF nhằm điều khiển model.

Câu hỏi luyện tập

Một agent computer use chạy ổn trong 15 lượt đầu, nhưng từ khoảng lượt 21 trở đi API bắt đầu trả invalid_request_error có nhắc tới “many-image requests”. Mỗi ảnh chụp màn hình có kích thước 3840×2160. Cách khắc phục phù hợp nhất là gì?
  1. Chuyển ảnh sang định dạng GIF để giảm dung lượng.
  2. Tăng max_tokens để model có đủ chỗ xử lý nhiều ảnh.
  3. Resize mỗi ảnh để không cạnh nào vượt 3.000 px, hoặc cắt bớt ảnh cũ để request còn ≤ 20 khối image.
  4. Chuyển ảnh từ base64 sang URL vì ảnh URL không bị tính vào giới hạn.
Đáp án C. Khi request có hơn 20 ảnh (tính cả ảnh trong lịch sử và trong tool_result), giới hạn kích thước mỗi ảnh chặt hơn được áp dụng; tài liệu khuyên resize cạnh ≤ 3.000 px hoặc giữ ≤ 20 khối image/document. A sai: định dạng không thay đổi kích thước pixel, và GIF động chỉ lấy khung đầu. B sai: max_tokens giới hạn đầu ra, không liên quan giới hạn ảnh đầu vào. D sai: mọi khối image đều được đếm, bất kể loại nguồn.
Một lập trình viên gửi khối nội dung sau và nhận lỗi. Nguyên nhân là gì? 
{"type": "image",
 "source": {"type": "base64",
            "media_type": "application/pdf",
            "data": "JVBERi0xLjcK..."}}
  1. PDF phải gửi bằng khối "type": "document", không phải "image"; image chỉ nhận JPEG/PNG/GIF/WebP.
  2. PDF chỉ được gửi qua URL, không được dùng base64.
  3. Thiếu beta header pdfs bắt buộc cho PDF.
  4. Khối image phải luôn đứng sau khối text, nên request bị từ chối.
Đáp án A. PDF dùng document block với media_type: "application/pdf"; image block chỉ hỗ trợ image/jpeg, image/png, image/gif, image/webp. B sai: PDF hỗ trợ cả url, base64 và file. C sai: tài liệu PDF support không yêu cầu beta header; tính năng ở trạng thái stable. D sai: tài liệu khuyên đặt ảnh trước text, và thứ tự khác vẫn hoạt động, không gây lỗi.
Những phát biểu nào đúng về chi phí token của ảnh? (Chọn 2)
  1. Mỗi pixel của ảnh được tính là một token, nên ảnh 1000×1000 tốn 1.000.000 token.
  2. Ảnh 1000×1000 tốn 1.296 visual token vì ⌈1000/28⌉ × ⌈1000/28⌉ = 36 × 36.
  3. Claude đọc metadata EXIF của ảnh, nên ảnh có metadata dài sẽ tốn thêm token.
  4. Trên các model từ Claude 4.7 trở về sau (mức High-resolution), một ảnh tốn tối đa 4.784 visual token.
  5. Mọi ảnh đều tốn đúng 1.568 token bất kể kích thước.
Đáp án B, D. Token ảnh tính theo patch 28×28: 36 × 36 = 1.296 (B). Mức High-res có trần 4.784 visual token và cạnh dài 2.576 px (D). A sai: tính theo patch, không theo pixel. C sai: FAQ nói Claude không đọc và không nhận metadata của ảnh. E sai: 1.568 là trần của mức Standard; ảnh nhỏ tốn ít hơn, ví dụ 200×200 chỉ tốn 64 token.
Một công ty SaaS phục vụ nhiều doanh nghiệp, cho khách hàng tải hợp đồng PDF lên để Claude tóm tắt. Đội dev dự định trả file_id cho frontend và để frontend gửi lại khi hỏi. Thiết kế nào an toàn hơn?
  1. Giữ nguyên thiết kế vì file_id là chuỗi ngẫu nhiên khó đoán.
  2. Mã hóa file_id bằng base64 trước khi gửi cho frontend.
  3. Dùng chung một workspace nhưng đặt tên file có tiền tố tên khách hàng.
  4. Tạo workspace riêng cho mỗi tenant với API key giới hạn theo workspace, và backend tự tra file_id từ người dùng đã xác thực thay vì nhận từ client.
Đáp án D. Trang Files API cảnh báo file có phạm vi theo workspace, không theo người dùng; không bao giờ nhận file_id từ nguồn không tin cậy, và nên tạo workspace riêng cho mỗi tenant. A sai: chuỗi khó đoán không thay cho kiểm soát truy cập (kiểu IDOR). B sai: base64 là mã hóa biểu diễn, không phải bảo mật. C sai: đặt tên file không tạo ranh giới phân quyền; key nào vào được workspace cũng đọc được mọi file.
Ứng dụng của bạn gọi Claude qua Amazon Bedrock. Bạn muốn Claude phân tích ảnh đang host trên CDN công khai bằng cách truyền {"type": "url", ...}. Điều gì xảy ra theo tài liệu?
  1. Hoạt động bình thường, vì nguồn URL được hỗ trợ trên mọi nền tảng.
  2. Không dùng được: trên Bedrock chỉ hỗ trợ nguồn base64 (mỗi ảnh tối đa 5 MB khi mã hóa base64), nên phải tải ảnh về và mã hóa base64.
  3. Phải đổi sang file_id của Files API vì Bedrock chỉ hỗ trợ Files API.
  4. Bedrock tự chuyển URL sang base64 nhưng giới hạn 20 MB mỗi ảnh.
Đáp án B. Trang Vision ghi rõ: trên Amazon Bedrock và Google Cloud (Google managed) chỉ có nguồn base64, giới hạn 5 MB/ảnh (base64) trên Bedrock và tổng request thấp hơn. A sai vì URL không có trên Bedrock. C sai: Files API không có trên Bedrock. D sai: không có cơ chế tự chuyển, và con số 20 MB không có trong tài liệu.
Những phát biểu nào đúng về PDF support? (Chọn 2)
  1. Hệ thống chuyển mỗi trang thành ảnh và trích văn bản của trang đó, nên Claude trả lời được cả câu hỏi về biểu đồ.
  2. Một request có thể chứa tối đa 1.000 trang PDF trên mọi model.
  3. Ảnh của mỗi trang PDF tốn tối đa 1.568 visual token trên mọi model, kể cả model mức High-resolution.
  4. PDF có mật khẩu được hỗ trợ nếu truyền mật khẩu trong trường password.
  5. File .docx có thể gửi trực tiếp trong document block giống PDF.
Đáp án A, C. A mô tả đúng quy trình 3 bước của tài liệu. C đúng: API đưa ảnh trang về giới hạn của mức Standard. B sai: tối đa 600 trang (100 khi context window của request dưới 1M token). D sai: chỉ hỗ trợ PDF chuẩn không mật khẩu/mã hóa; không có trường password. E sai: .docx, .xlsx không được hỗ trợ trong document block – cần chuyển sang văn bản hoặc PDF.
Bạn gửi ảnh chụp màn hình 1920×1080 cho Claude Haiku 4.5 (mức Standard) và hỏi tọa độ pixel của nút “Thanh toán”. Claude trả về [728, 410]. Để click đúng trên màn hình gốc 1920×1080, bạn nên làm gì?
  1. Dùng trực tiếp [728, 410] vì Claude luôn trả tọa độ theo ảnh gốc.
  2. Chia cho kích thước sau khi pad (bội số của 28) rồi nhân với 1920×1080.
  3. Ảnh đã bị thu về 1456×819, nên nhân x với 1920/1456 và y với 1080/819 (hoặc lần sau tự resize ảnh về 1456×819 trước khi gửi).
  4. Yêu cầu Claude trả tọa độ chuẩn hóa 0–1000 để khỏi phải quy đổi.
Đáp án C. Tọa độ Claude trả về là pixel trên ảnh sau resize; ở mức Standard, 1920×1080 được thu về 1456×819. Quy đổi tuyến tính theo kích thước sau resize, hoặc tự resize trước để tọa độ khớp 1:1. A sai vì ảnh đã bị resize. B sai: tài liệu nhấn mạnh phải quy đổi theo kích thước sau resize, không theo kích thước sau pad. D sai: tài liệu nói Claude làm kém với tọa độ chuẩn hóa; nên hỏi pixel tuyệt đối rồi tự chuẩn hóa trong code.
Đọc đoạn request sau, gửi tới một model mức Standard, với ảnh có kích thước 1920×1080: 
{"type": "image",
 "source": {"type": "base64", "media_type": "image/png", "data": "..."},
 "transformations": {"oversized_image": "error"}}
Kết quả là gì?
  1. Ảnh được thu nhỏ âm thầm về 1456×819 như bình thường.
  2. Ảnh được cắt (crop) phần thừa để vừa 1568×1568.
  3. Request thành công nhưng Claude bỏ qua ảnh này.
  4. Request bị từ chối với lỗi 400 invalid_request_error, thông báo nêu kích thước ảnh và kích thước tối đa phù hợp (1456×819).
Đáp án D. "oversized_image": "error" biến việc resize thành lỗi 400, nêu kích thước ảnh và kích thước lớn nhất phù hợp – tài liệu dùng chính ví dụ 1920×1080 → 1456×819. A là hành vi của giá trị mặc định "downsize". B sai: Claude không bao giờ crop; resize luôn giữ tỉ lệ khung hình. C sai: API không bỏ qua ảnh âm thầm; ảnh đánh dấu “error” không bao giờ tới model ở dạng đã resize.
Một bệnh viện xây dựng hệ thống tóm tắt hồ sơ bệnh án dạng PDF và cần tuân thủ HIPAA. Theo tài liệu PDF support, cách gửi PDF nào phù hợp?
  1. Tải PDF lên Files API rồi tham chiếu bằng file_id để giảm kích thước request.
  2. Gửi PDF inline (ví dụ base64) trực tiếp trong Messages API request.
  3. Chuyển PDF thành ảnh PNG rồi gửi qua Files API.
  4. Gửi qua URL công khai để Anthropic tự tải về.
Đáp án B. Bảng Data handling của PDF support ghi: điều kiện HIPAA áp dụng cho PDF gửi inline qua Messages API, không qua Files API. A và C sai vì dùng Files API (Files API cũng không đủ điều kiện HIPAA/ZDR). D sai: đặt hồ sơ bệnh án lên URL công khai là rò rỉ dữ liệu nghiêm trọng.
Bạn cần ước tính chi phí phân tích 1.000 ảnh sản phẩm kích thước 1000×1000 bằng Claude Opus 5.5 (giá input $4 / triệu token theo Models overview, kiểm tra 2026-11-20), chỉ tính token ảnh. Ước tính nào đúng?
  1. Khoảng $5,18 (1.296 token × 1.000 ảnh × $4 / 1.000.000).
  2. Khoảng $4,00 vì mỗi ảnh tính đúng 1.000 token.
  3. Khoảng $19,14 vì mọi ảnh trên model High-res đều tốn 4.784 token.
  4. Miễn phí vì token ảnh không bị tính tiền, chỉ token văn bản bị tính.
Đáp án A. 1000×1000 = 36 × 36 = 1.296 token, không bị resize ở cả hai mức; 1.296.000 token × $4/MTok ≈ $5,18 – đúng ví dụ trong tài liệu. B sai cách tính token. C sai: 4.784 là trần, chỉ ảnh lớn (ví dụ 4K) mới chạm; $19,14 là chi phí cho 1.000 ảnh 4K. D sai: token ảnh được tính như input token theo giá của model.
