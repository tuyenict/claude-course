Sau bài này bạn sẽ

  • Phân biệt ba loại thông điệp JSON-RPC của MCP và ba message pattern trong đặc tả 2026-07-28: request/response, Multi Round-Trip Requests (MRTR), subscribe/notify.
  • Đọc và viết được một InputRequiredResult chứa elicitation/create, sampling/createMessage hoặc roots/list, và biết cách bảo vệ requestState.
  • Giải thích sampling, elicitation (form mode / URL mode), roots — và biết cái nào đã deprecated, nên chuyển sang gì.
  • Dùng đúng notifications/progress, notifications/message (logging) và cơ chế hủy request trên từng transport.
  • Chọn transport phù hợp: stdio hay Streamable HTTP; nắm các header bắt buộc, cách xử lý "state" khi server không còn session.
  • Mô tả luồng authorization OAuth 2.1 của MCP: Protected Resource Metadata, PKCE S256, tham số resource, kiểm tra audience và cấm token passthrough.

📨JSON message types và ba mẫu tương tác

Khóa Academy có riêng một bài "JSON message types". Ở bản 2026-07-28, quy tắc rất gọn: mọi tương tác đều bắt đầu từ client.

📤

Request

Yêu cầu

Có id và method; chỉ client gửi. Bên kia phải trả lời đúng một response.

📥

Response

Phản hồi

Cùng id với request; chứa result hoặc error. Chỉ server gửi.

🔔

Notification

Thông báo

Có method, không có id, không được trả lời. Server gửi (progress, log, list_changed); client gửi notifications/cancelled trên stdio.

Trang Transports nói rõ: binding phải chuyển request và notification của client tới server, và response và notification của server tới client — "không có hướng nào khác". Trang Message patterns nhấn mạnh: Servers MUST NOT initiate JSON-RPC requests, và client không gửi JSON-RPC response.

Metadata đi kèm mọi request

Vì không còn bắt tay, mỗi request phải tự mang theo phiên bản giao thức và capabilities trong _meta. Ví dụ một tools/call đầy đủ (rút từ trang Streamable HTTP):

{
  "jsonrpc": "2.0",
  "id": 1,                                   // có id ⇒ đây là request
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "location": "Seattle, WA" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",   // bắt buộc trên mọi request
      "io.modelcontextprotocol/clientInfo": { "name": "ExampleClient", "version": "1.0.0" },
      "io.modelcontextprotocol/clientCapabilities": {}         // khai báo elicitation, sampling, roots… ở đây
    }
  }
}

Nếu server không hỗ trợ phiên bản được yêu cầu, nó phải trả UnsupportedProtocolVersionError (mã -32022) kèm danh sách phiên bản hỗ trợ; client chọn một phiên bản chung rồi gửi lại. Server cũng bắt buộc cài server/discover để client có thể hỏi trước phiên bản/capabilities nếu muốn.

Mã lỗi dành riêng cho MCP

Changelog định nghĩa chính sách phân bổ mã lỗi: dải -32000 đến -32019 do implementation tự định nghĩa; dải -32020 đến -32099 dành cho đặc tả MCP. Ba mã mới: HeaderMismatch = -32020, MissingRequiredClientCapability = -32021, UnsupportedProtocolVersion = -32022. Lỗi "resource not found" đổi từ -32002 sang -32602 (Invalid params).

Lỗi thường gặp

Viết server "đời mới" nhưng vẫn để server tự gửi một JSON-RPC request {"id": 7, "method": "sampling/createMessage"} lên stdout hoặc SSE stream. Ở 2026-07-28, hành vi này không còn được hỗ trợ (trang stdio: "The server MUST NOT write JSON-RPC requests to stdout"). Phải đóng gói yêu cầu đó trong InputRequiredResult.inputRequests.

🔁Multi Round-Trip Requests: server xin thêm thông tin thế nào?

Multi Round-Trip Requests (MRTR) được giới thiệu ở phiên bản này để thay cho việc server tự gửi request. Đây là thay đổi phá vỡ tương thích (breaking change).

Luồng cấp cao theo tài liệu:

  1. Bước 1 – Client gửi request ban đầu với các tham số cần cho thao tác.
  2. Bước 2 – Server thấy cần thêm thông tin, trả về một InputRequiredResult (thay vì kết quả cuối).
  3. Bước 3 – Client thu thập thông tin (từ người dùng hoặc nguồn khác) rồi gửi lại request gốc kèm thông tin đã xin.
  4. Bước 4 – Server đã đủ thông tin, trả kết quả cuối cùng (resultType: "complete").

Các kiểu dữ liệu cốt lõi

KiểuÝ nghĩa
InputRequestsMap: khóa là chuỗi do server đặt (duy nhất trong phạm vi request), giá trị là một request object: ElicitRequest, CreateMessageRequest hoặc ListRootsRequest.
InputResponsesMap trả lời: khóa trùng với khóa trong InputRequests; giá trị là ElicitResult, CreateMessageResult hoặc ListRootsResult.
InputRequiredResultMột loại Result với resultType: "input_required"; có inputRequests (tùy chọn) và requestState (tùy chọn) — nhưng phải có ít nhất một trong hai.
requestStateChuỗi mờ (opaque), chỉ server hiểu. Client không được đọc, phân tích, sửa hay suy đoán nội dung; chỉ gửi trả nguyên văn.

Ví dụ InputRequiredResult gộp hai yêu cầu cùng lúc — một elicitation và một sampling (trích từ trang MRTR):

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "input_required",          // không phải kết quả cuối
    "inputRequests": {
      "github_login": {                          // khóa do server tự đặt
        "method": "elicitation/create",
        "params": {
          "mode": "form",
          "message": "Please provide your GitHub username",
          "requestedSchema": {
            "type": "object",
            "properties": { "name": { "type": "string" } },
            "required": ["name"]
          }
        }
      },
      "capital_of_france": {
        "method": "sampling/createMessage",
        "params": {
          "messages": [{ "role": "user", "content": { "type": "text", "text": "What is the capital of France?" } }],
          "modelPreferences": { "hints": [{ "name": "claude-3-sonnet" }], "intelligencePriority": 0.8, "speedPriority": 0.5 },
          "systemPrompt": "You are a helpful assistant.",
          "maxTokens": 100
        }
      }
    },
    "requestState": "AEAD-protected blob"      // client gửi trả nguyên văn
  }
}

Client gửi lại request gốc với id khác, kèm inputResponses và requestState:

{
  "github_login":      { "action": "accept", "content": { "name": "octocat" } },
  "capital_of_france": { "role": "assistant",
                          "content": { "type": "text", "text": "The capital of France is Paris." },
                          "model": "claude-3-sonnet-20240307", "stopReason": "endTurn" }
}

Ghi chú: claude-3-sonnet trong ví dụ là chuỗi minh họa có sẵn trong đặc tả (một hint dạng chuỗi con), không phải model ID bạn nên dùng khi gọi Claude API.

Request nào được phép trả InputRequiredResult?

Chỉ ba: prompts/get, resources/read, tools/call. Server không được trả InputRequiredResult cho bất kỳ request nào khác (ví dụ tools/list).

Quy tắc cho server và client

🖥️Server phải / nên

  • Không gửi loại input request mà client chưa khai báo trong capabilities (không có elicitation ⇒ không được gửi elicitation/create).
  • Coi requestState gửi về là dữ liệu do kẻ tấn công kiểm soát; nếu nó ảnh hưởng tới phân quyền, truy cập tài nguyên hay logic nghiệp vụ thì phải bảo vệ toàn vẹn (HMAC hoặc AEAD) và từ chối state sai.
  • Chống replay: nên nhúng danh tính người dùng đã xác thực, thời hạn ngắn (TTL), định danh request gốc (tên method + digest tham số) vào payload được bảo vệ.
  • Không giả định client sẽ đáp ứng hay gửi lại; nếu thiếu thông tin, trả một InputRequiredResult mới thay vì báo lỗi.

💻Client phải

  • Nếu có inputRequests: thu thập đủ input rồi mới gửi lại. Nếu không có: có thể gửi lại ngay.
  • Gửi lại nguyên văn requestState; nếu server không gửi requestState thì không được tự thêm.
  • Dùng JSON-RPC id khác cho lần gửi lại — đó là hai request độc lập.
  • Không dùng inputRequests / requestState cho request khác chạy song song.
Lỗi thường gặp – tin tưởng requestState

Server mã hóa {"user":"alice","approved":true} thành base64 rồi đặt vào requestState, lần sau đọc ra và tin luôn. Một client độc hại chỉ cần sửa thành "approved":true cho người khác. Đặc tả yêu cầu: khi state ảnh hưởng phân quyền/nghiệp vụ, phải ký HMAC hoặc mã hóa AEAD và từ chối khi xác minh thất bại. Ngay cả khi đã ký, các biện pháp này chỉ thu hẹp cửa sổ replay; thao tác "chỉ dùng một lần" (ví dụ đổi mã khuyến mãi) phải được kiểm soát ở phía server.

Mẹo thực chiến (Pro Tip)

Tình huống: "Server MCP chạy sau load balancer, nhiều instance, không có Redis dùng chung, nhưng tool cần hỏi người dùng xác nhận giữa chừng" ⇒ dùng MRTR và mã hóa ngữ cảnh vào requestState (có HMAC/AEAD + TTL + principal). Instance nào nhận lần gửi lại cũng xử lý được — đúng mục tiêu tài liệu nêu: không cần shared storage hay stateful load balancing.

🎲Sampling: server "mượn" LLM của client (deprecated)

Sampling cho phép server yêu cầu client sinh văn bản (hoặc ảnh, âm thanh) bằng LLM mà client đang dùng. Client giữ quyền kiểm soát việc truy cập model, chọn model và cấp quyền — còn server không cần API key riêng.

Deprecated từ 2026-07-28

Theo SEP-2577, Sampling vẫn hoạt động đầy đủ trong cửa sổ deprecation (ít nhất 12 tháng), nhưng triển khai mới không nên dùng. Hướng chuyển đổi tài liệu đề xuất: tích hợp trực tiếp với API của nhà cung cấp LLM (ví dụ server tự gọi Claude API — xem Bài tập 2). Khóa Academy vẫn dạy sampling vì nhiều server đang chạy dùng nó; bạn cần hiểu để đọc và bảo trì.

Vì sao từng cần sampling?

Hình dung một MCP server "tóm tắt tài liệu nội bộ". Server cần LLM để tóm tắt, nhưng nếu server tự giữ API key thì: ai trả tiền, ai chọn model, dữ liệu đi đâu? Sampling chuyển việc gọi LLM về phía client — nơi người dùng đã có model và hạn mức của mình. Đặc tả nói sampling cho phép "LLM calls to occur nested inside other MCP server features", tức là server xây được hành vi agentic lồng trong tool.

Model hints và các mức ưu tiên

Server và client có thể dùng nhà cung cấp AI khác nhau, nên server không thể đòi đúng một model theo tên. Đặc tả dùng hệ thống ưu tiên:

  • hints được hiểu là chuỗi con để khớp tên model một cách linh hoạt, xét theo thứ tự; client có thể ánh xạ sang model tương đương của nhà cung cấp khác. Hint chỉ mang tính tư vấn.
  • costPriority cao ⇒ ưu tiên model rẻ; speedPriority cao ⇒ ưu tiên model nhanh; intelligencePriority cao ⇒ ưu tiên model mạnh.

Kết quả trả về

CreateMessageResult gồm role, content (một block hoặc mảng block), model (tên model thực sự đã sinh) và stopReason. Các giá trị stopReason đặc tả nêu (không đầy đủ): "endTurn", "stopSequence", "maxTokens", "toolUse".

Sampling có tool

Server có thể gửi kèm tools để LLM phía client gọi tool trong lúc sampling. Khi LLM trả stopReason: "toolUse", server thực thi tool, rồi gửi một InputRequiredResult mới với lịch sử + tool_result. Hai ràng buộc quan trọng:

  • Message user chứa tool_result thì chỉ được chứa tool_result, không trộn text/ảnh.
  • Mỗi tool_use (có id) phải được đáp bằng một tool_result có toolUseId tương ứng trước bất kỳ message nào khác. Hai bên nên đặt giới hạn số vòng lặp; vòng cuối có thể đặt toolChoice: {mode: "none"} để buộc trả lời cuối.
Human-in-the-loop là yêu cầu an toàn

Đặc tả: vì an toàn và bảo mật, luôn nên có con người có quyền từ chối request sampling. Ứng dụng nên có UI để xem request, cho sửa prompt trước khi gửi và xem câu trả lời trước khi giao cho server. Client nên giới hạn tần suất (rate limiting); cả hai bên phải xử lý dữ liệu nhạy cảm đúng cách. Nếu người dùng từ chối, client không cần gửi lại request gốc kèm lỗi — server không "chờ" gì cả.

Mẹo thực chiến (Pro Tip)

Tình huống: "Bạn viết MCP server mới cần tóm tắt văn bản bằng LLM" ⇒ theo hướng chuyển đổi của SEP-2577, gọi thẳng Claude API trong server (API key đọc từ biến môi trường ANTHROPIC_API_KEY), thay vì dựa vào sampling đã deprecated. Chỉ cài sampling khi phải tương thích với server/host cũ.

📝Elicitation: hỏi người dùng giữa chừng

Elicitation là tính năng client duy nhất trong đặc tả 2026-07-28 không bị deprecated. Nó cho phép server xin thông tin bổ sung từ người dùng thông qua client, trong lúc xử lý một request.

🧾Form mode

  • Thu thập dữ liệu có cấu trúc ngay trong client, theo requestedSchema.
  • Dữ liệu đi qua client (client nhìn thấy).
  • Schema chỉ là object phẳng với thuộc tính kiểu nguyên thủy: string (format email, uri, date, date-time), number/integer, boolean, enum (chọn một hoặc nhiều).
  • Cấm dùng để xin mật khẩu, API key, access token, thông tin thanh toán.

🔗URL mode

  • Đưa người dùng tới một URL bên ngoài để tương tác ngoài băng (out-of-band).
  • Dữ liệu (trừ chính URL) không lộ cho client.
  • Bắt buộc dùng khi liên quan thông tin nhạy cảm: nhập API key, OAuth với dịch vụ bên thứ ba, thanh toán.
  • Ra đời ở bản 2025-11-25; thiết kế có thể còn thay đổi.

URL mode – ví dụ và lưu ý

{ "method": "elicitation/create",
  "params": { "mode": "url",
              "url": "https://mcp.example.com/ui/set_api_key",
              "message": "Please provide your API key to continue." } }
// Client trả { "action": "accept" } = người dùng ĐỒNG Ý mở URL, KHÔNG có nghĩa là đã xong.
// Khi client gửi lại request gốc, server dựa vào requestState (hoặc state của nó) để biết đã xong chưa.
  • URL mode không dùng để ủy quyền client truy cập chính MCP server (việc đó là của MCP authorization). Nó dùng khi server cần thông tin nhạy cảm hoặc ủy quyền với bên thứ ba thay mặt người dùng.
  • Credential bên thứ ba không được đi qua client; server không được dùng token của client cho dịch vụ bên thứ ba (token passthrough).
  • Client: không tự động tải trước URL, không mở URL khi chưa có đồng ý, phải hiện đầy đủ URL, mở bằng cách mà client/LLM không đọc được nội dung (ví dụ iOS dùng SFSafariViewController thay vì WKWebView), nên làm nổi bật domain và cảnh báo URL đáng ngờ (Punycode).
  • Server: không nhét thông tin cá nhân/credential vào URL, không đưa URL đã xác thực sẵn, và phải xác minh người mở URL chính là người khởi tạo elicitation (chống phishing chiếm tài khoản).
Lỗi thường gặp

Dùng form mode với schema {"password": {"type": "string"}} để "tiện" lấy mật khẩu Jira của người dùng. Đặc tả cấm rõ: server MUST NOT dùng form mode để xin password, API key, access token, payment credentials — phải dùng URL mode. Cũng đừng để form chứa URL bấm được (đặc tả khuyến nghị không làm).

Mẹo thực chiến (Pro Tip)

Tình huống ⇒ chọn mode: "Tool đặt phòng cần người dùng chọn ngày và số khách" ⇒ form (schema có format: "date" + integer). "Tool cần quyền đọc Google Calendar của người dùng" ⇒ URL mode dẫn tới trang "connect" của server, server làm OAuth với Google và tự lưu token gắn với danh tính người dùng.

🔔Progress, logging và cancellation

Khóa Academy gọi nhóm này là "Log and progress notifications". Đây là những notification server gửi trong khi một request đang chạy, trước response cuối.

Progress notifications

Client muốn nhận tiến độ thì đặt progressToken (chuỗi hoặc số nguyên, duy nhất trong các request đang hoạt động) vào _meta. Server có thể gửi:

// Client → request có progressToken
{ "jsonrpc": "2.0", "id": 1, "method": "some_method",
  "params": { "_meta": { "progressToken": "abc123" } } }

// Server → notification (không có id)
{ "jsonrpc": "2.0", "method": "notifications/progress",
  "params": { "progressToken": "abc123", "progress": 50, "total": 100,
              "message": "Reticulating splines..." } }
  • progress phải tăng sau mỗi notification, kể cả khi không biết total. progress và total có thể là số thực.
  • total và message là tùy chọn; message nên là thông tin dễ đọc cho người.
  • Server có quyền không gửi gì, hoặc gửi với tần suất tùy ý. Hai bên nên giới hạn tần suất để tránh "lụt" thông báo; notification phải dừng khi thao tác hoàn tất.

Logging (deprecated)

Server gửi log có cấu trúc qua notifications/message với level, logger (tùy chọn) và data. Các mức theo syslog (RFC 5424): debug, info, notice, warning, error, critical, alert, emergency.

  • Ở 2026-07-28, logging/setLevel đã bị bỏ. Client đặt io.modelcontextprotocol/logLevel trong _meta của từng request. Thiếu trường này ⇒ server không được gửi notifications/message cho request đó.
  • Mức log không hợp lệ ⇒ server nên trả lỗi -32602 (Invalid params).
  • Log không được chứa credential/secret, thông tin định danh cá nhân, chi tiết nội bộ giúp kẻ tấn công.
  • Hướng chuyển đổi (SEP-2577): log ra stderr với stdio; dùng OpenTelemetry cho observability có cấu trúc.
{ "jsonrpc": "2.0", "method": "notifications/message",
  "params": { "level": "error", "logger": "database",
              "data": { "error": "Connection failed", "details": { "host": "localhost", "port": 5432 } } } }

Trong cả hai trường hợp, server nên dừng việc sớm nhất có thể và không được gửi thêm thông điệp nào cho request đã hủy.

🌳Roots: thư mục làm việc của client (deprecated)

Roots là cách client cho server biết những thư mục/file mà client coi là liên quan (ví dụ thư mục dự án đang mở trong IDE), để server tập trung thao tác vào đó.

  • Mỗi root có uri — trong đặc tả hiện tại phải là URI file:// — và name (tùy chọn, để hiển thị).
  • Roots chỉ là hướng dẫn mang tính thông tin, không phải cơ chế kiểm soát truy cập: giao thức không ép server phải ở trong roots.
  • Client khai báo capability roots; server lấy danh sách bằng roots/list đặt trong InputRequiredResult. notifications/roots/list_changed đã bị bỏ ở bản này.
// Server → inputRequests
{ "method": "roots/list" }
// Client → inputResponses
{ "roots": [ { "uri": "file:///home/user/repos/frontend", "name": "Frontend Repository" },
             { "uri": "file:///home/user/repos/backend",  "name": "Backend Repository" } ] }
Hướng chuyển đổi

Roots bị deprecated theo SEP-2577. Triển khai mới nên truyền thư mục/file qua tham số tool, URI của resource, hoặc cấu hình server (ví dụ đối số dòng lệnh khi khởi động server stdio). Nếu vẫn dùng roots: client phải chỉ lộ roots có quyền phù hợp và kiểm tra URI chống path traversal; server nên kiểm tra mọi đường dẫn so với roots được cung cấp.

Ví dụ đời thường

Roots giống tờ giấy ghi "hôm nay chỉ dọn phòng khách và bếp" bạn để lại cho người giúp việc: hữu ích để họ tập trung, nhưng không khóa các phòng khác. Muốn thật sự chặn, bạn phải khóa cửa — tức là kiểm soát quyền ở server/hệ điều hành (least privilege), không dựa vào roots.

🚚Transports chuyên sâu: stdio và Streamable HTTP

Một transport là một binding: nó quy định cách đóng khung và chuyển thông điệp, cách mang metadata, cách báo hủy và kết thúc — nhưng không quy định ý nghĩa thông điệp. Ngữ nghĩa giao thức giống hệt nhau trên mọi transport. Mọi thông điệp JSON-RPC phải mã hóa UTF-8.

stdio

  • Client khởi chạy MCP server như một tiến trình con. Server đọc JSON-RPC từ stdin, ghi ra stdout.
  • Thông điệp phân tách bằng ký tự xuống dòng và không được chứa xuống dòng bên trong.
  • Server không được ghi ra stdout bất cứ thứ gì không phải thông điệp MCP hợp lệ; có thể ghi chuỗi UTF-8 ra stderr để log. Client không nên coi output stderr là lỗi.
  • Không có header: phiên bản, capabilities, danh tính client nằm trong _meta của body.
  • Shutdown: client đóng stdin → chờ server thoát → quá lâu thì buộc dừng (POSIX: SIGTERM rồi SIGKILL; Windows: TerminateProcess hoặc Job Objects). Server nên thoát ngay khi stdin đóng (EOF).
  • Server chết bất ngờ ⇒ client nên khởi động lại; vì giao thức stateless, request đang bay chỉ cần gửi lại; các stream subscriptions/listen phải mở lại.
  • Authorization: transport stdio không nên theo đặc tả OAuth, mà lấy credential từ môi trường (biến môi trường).

Streamable HTTP

  • Ra đời ở bản 2025-03-26, thay cho transport HTTP+SSE của 2024-11-05 (nay deprecated theo SEP-2596).
  • Server cung cấp một đường dẫn duy nhất hỗ trợ POST (ví dụ https://example.com/mcp). Mỗi thông điệp client gửi là một HTTP POST mới.
  • Header Accept phải liệt kê cả application/json và text/event-stream.
  • Nếu body là notification và server chấp nhận ⇒ 202 Accepted không body.
  • Nếu body là request ⇒ server trả Content-Type: application/json (một object) hoặc text/event-stream (SSE stream gắn với request đó); client phải hỗ trợ cả hai. Trên SSE, server có thể gửi notification liên quan (progress, message) trước response cuối; response cuối nên kết thúc stream.
  • Server không được gửi JSON-RPC request độc lập trên stream — đây là khác biệt so với 2025-03-26 đến 2025-11-25.
  • Khi mở SSE stream, server nên gửi header X-Accel-Buffering: no để reverse proxy (như nginx) không đệm; stream sống lâu nên gửi dòng comment : định kỳ làm keep-alive.

"State" khi không còn session

Bài cuối của phần transport trong khóa Academy là "State and the StreamableHTTP transport". Ở bản 2026-07-28 câu trả lời đã thay đổi căn bản:

  • Không còn Mcp-Session-Id, không còn GET stream, không còn nối lại stream bằng Last-Event-ID. Server chỉ hỗ trợ bản mới nên bỏ qua Mcp-Session-Id và Last-Event-ID nếu nhận được, trả 405 cho GET/DELETE.
  • Stream phản hồi bị đứt ⇒ request đang bay bị mất; client phải gửi lại như request mới với ID mới.
  • Cần trạng thái giữa các lời gọi ⇒ server cấp handle tường minh (ví dụ cart_id) và client truyền lại như tham số tool thông thường (SEP-2567).
  • Cần trạng thái trong một thao tác nhiều lượt ⇒ dùng requestState của MRTR.
  • Thông báo thay đổi lâu dài ⇒ subscriptions/listen (client chọn loại: toolsListChanged, promptsListChanged, resourcesListChanged, resourceSubscriptions).

🖥️Chọn stdio khi

  • Server chạy trên máy người dùng (công cụ dòng lệnh, đọc file cục bộ).
  • Chỉ một client dùng server đó.
  • Credential lấy từ biến môi trường là đủ.

🌐Chọn Streamable HTTP khi

  • Server từ xa, phục vụ nhiều client/người dùng.
  • Cần scale ngang sau load balancer (hợp với mô hình stateless).
  • Cần OAuth 2.1 để bảo vệ tài nguyên của từng người dùng.
Lỗi thường gặp – server cục bộ mở toang

Chạy Streamable HTTP server trên máy dev với 0.0.0.0 và không kiểm tra Origin. Một trang web độc hại có thể dùng DNS rebinding để gọi server cục bộ của bạn. Đặc tả: server phải kiểm tra header Origin (sai ⇒ 403), khi chạy local nên chỉ bind 127.0.0.1, và nên xác thực mọi kết nối.

Mẹo thực chiến (Pro Tip)

Tình huống: "Server stdio của tôi thỉnh thoảng làm client báo lỗi parse JSON" ⇒ gần như chắc chắn có lệnh print() hoặc thư viện ghi log ra stdout. Chuyển mọi log sang stderr — vừa đúng quy tắc stdio, vừa đúng hướng chuyển đổi khỏi logging deprecated.

🔐Authorization: bảo vệ MCP server từ xa bằng OAuth 2.1

Authorization trong MCP là tùy chọn. Khi hỗ trợ: transport HTTP nên tuân theo đặc tả này; stdio không nên (lấy credential từ môi trường); transport khác phải theo best practice bảo mật của giao thức đó.

Tương tác với người dùng, cấp access token. Có thể chung hoặc tách khỏi resource server.

Các chuẩn được dùng

OAuth 2.1 (draft-ietf-oauth-v2-1-13), Bearer Token Usage (RFC 6750), Authorization Server Metadata (RFC 8414), Dynamic Client Registration (RFC 7591 — nay deprecated), Resource Indicators (RFC 8707), Protected Resource Metadata (RFC 9728), Issuer Identification (RFC 9207), OAuth Client ID Metadata Documents (draft), OpenID Connect Discovery 1.0.

Các bước và yêu cầu then chốt

  1. Khám phá Protected Resource Metadata (RFC 9728) – MCP server phải cài RFC 9728 và chỉ ra authorization_servers. Client lấy URL metadata từ resource_metadata trong header WWW-Authenticate của phản hồi 401; nếu không có, thử well-known URI: trước tiên theo đường dẫn endpoint (/.well-known/oauth-protected-resource/mcp), sau đó ở gốc (/.well-known/oauth-protected-resource).
  2. Khám phá Authorization Server Metadata – client phải hỗ trợ cả RFC 8414 (/.well-known/oauth-authorization-server) và OpenID Connect Discovery (/.well-known/openid-configuration), thử theo thứ tự ưu tiên. issuer trong tài liệu phải trùng với issuer dùng để dựng URL, nếu không phải bỏ.
  3. Đăng ký client – thứ tự ưu tiên: (1) thông tin pre-registered nếu có; (2) Client ID Metadata Documents nếu AS báo client_id_metadata_document_supported — client_id là một URL HTTPS có path trỏ tới JSON chứa ít nhất client_id, client_name, redirect_uris; (3) Dynamic Client Registration (deprecated) nếu AS có registration_endpoint; (4) hỏi người dùng nhập.
  4. PKCE – client phải dùng PKCE, dùng phương thức S256 khi có thể, và phải kiểm tra code_challenge_methods_supported trong metadata; nếu thiếu trường này, client phải từ chối tiếp tục.
  5. Tham số resource (RFC 8707) – phải có trong cả authorization request và token request, là canonical URI của MCP server (ví dụ https://mcp.example.com/mcp; không có fragment, nên không có dấu / cuối), gửi kể cả khi AS không hỗ trợ.
  6. Kiểm tra iss (RFC 9207) – trước khi đổi code lấy token, client so iss trong phản hồi với issuer đã ghi nhận bằng so sánh chuỗi đơn giản.
  7. Dùng token – gửi Authorization: Bearer <access-token> trên mọi HTTP request; không bao giờ đặt token trong query string.

Scope và step-up authorization

  • Server nên đưa scope vào WWW-Authenticate. Client ưu tiên dùng scope trong challenge; nếu không có thì dùng scopes_supported trong Protected Resource Metadata — theo nguyên tắc least privilege.
  • Đang chạy mà thiếu quyền ⇒ server nên trả 403 Forbidden với error="insufficient_scope", scope cần thiết, resource_metadata. Client tính hợp của scope đã xin và scope mới, xin ủy quyền lại, rồi thử lại vài lần là tối đa.

Lỗi thường gặp – token passthrough

Server MCP nhận token của người dùng rồi "tiện tay" gửi nguyên token đó tới GitHub API. Đây là token passthrough — bị cấm rõ ràng. Nó phá vỡ kiểm tra audience, làm mất dấu vết kiểm toán và mở đường cho confused deputy. Cách đúng: server tự làm OAuth với GitHub (ví dụ qua elicitation URL mode) và dùng token GitHub riêng, gắn với danh tính người dùng.

Viết hai hàm bằng thư viện chuẩn Python: make_state(principal, method, args, ttl_s) trả về chuỗi base64url gồm payload JSON + chữ ký HMAC-SHA256; verify_state(state, principal, method, args) từ chối khi chữ ký sai, hết hạn, khác principal hoặc khác request. 
    import base64, hashlib, hmac, json, os, time

KEY = os.environ["MCP_STATE_KEY"].encode()   # bí mật lấy từ môi trường

def _digest(method, args):
    return hashlib.sha256((method + json.dumps(args, sort_keys=True)).encode()).hexdigest()

def make_state(principal, method, args, ttl_s=300, extra=None):
    body = json.dumps({"sub": principal, "req": _digest(method, args),
                       "exp": int(time.time()) + ttl_s, "x": extra or {}}).encode()
    sig = hmac.new(KEY, body, hashlib.sha256).digest()
    return base64.urlsafe_b64encode(body).decode() + "." + base64.urlsafe_b64encode(sig).decode()

def verify_state(state, principal, method, args):
    b64body, b64sig = state.split(".", 1)
    body = base64.urlsafe_b64decode(b64body)
    if not hmac.compare_digest(hmac.new(KEY, body, hashlib.sha256).digest(),
                               base64.urlsafe_b64decode(b64sig)):
        raise ValueError("bad signature")
    p = json.loads(body)
    if p["exp"] < time.time():              raise ValueError("expired")
    if p["sub"] != principal:               raise ValueError("wrong principal")
    if p["req"] != _digest(method, args):   raise ValueError("wrong request")
    return p["x"]
    Kết quả mong đợi: sửa một ký tự của state ⇒ bad signature; dùng state của Alice cho Bob ⇒ wrong principal; dùng cho tool khác ⇒ wrong request. Lưu ý: HMAC chỉ bảo vệ toàn vẹn, không che giấu nội dung — nếu payload chứa dữ liệu nhạy cảm, hãy dùng AEAD. Thao tác chỉ-một-lần vẫn phải được chặn ở phía server.

Với một MCP server từ xa bạn được phép kiểm thử (hoặc server tự dựng), dùng curl -i gửi POST không token tới MCP endpoint với đủ header (Accept, MCP-Protocol-Version, Mcp-Method). Ghi lại: mã trạng thái, giá trị resource_metadata và scope trong WWW-Authenticate; tải Protected Resource Metadata và đọc authorization_servers; tải metadata của AS và kiểm tra có code_challenge_methods_supported chứa S256 và client_id_metadata_document_supported hay không.
    Kết quả mong đợi: một bảng ghi lại từng bước như Hình 5, kèm kết luận "client có được phép tiếp tục không" (thiếu code_challenge_methods_supported ⇒ phải dừng). Không dán access token thật vào tài liệu hay log.

Tóm tắt ghi nhớ

Key takeaways
  • Đặc tả hiện hành 2026-07-28 (kiểm tra ngày 2026-11-20): stateless, không bắt tay initialize, không session; mọi request mang protocolVersion + clientCapabilities trong _meta.
  • Chỉ client gửi request; server trả response và notification. Ba mẫu: request/response, MRTR, subscribe/notify (subscriptions/listen).
  • MRTR: server trả InputRequiredResult (resultType: "input_required", inputRequests, requestState) chỉ cho tools/call, resources/read, prompts/get; client gửi lại với ID mới + inputResponses + requestState nguyên văn. Server coi requestState là input của kẻ tấn công ⇒ HMAC/AEAD, TTL, principal.
  • Sampling, Roots, Logging deprecated (SEP-2577): chuyển sang gọi thẳng API LLM; truyền thư mục qua tham số tool/URI/cấu hình; log ra stderr hoặc OpenTelemetry. Elicitation vẫn hiệu lực.
  • Elicitation: form cho dữ liệu thường (schema phẳng, kiểu nguyên thủy), URL cho thông tin nhạy cảm/OAuth bên thứ ba; trả lời accept / decline / cancel.
  • Progress: progressToken trong _meta, progress luôn tăng. Hủy: stdio gửi notifications/cancelled; HTTP đóng SSE stream.
  • stdio: stdout chỉ chứa thông điệp MCP, log ra stderr, credential từ môi trường. Streamable HTTP: một endpoint POST, header MCP-Protocol-Version/Mcp-Method/Mcp-Name phải khớp body (-32020), kiểm tra Origin, bind localhost khi chạy local.
  • Authorization: RFC 9728 → RFC 8414/OIDC → đăng ký client (pre-registered, CIMD, DCR deprecated) → PKCE S256 → resource (RFC 8707) → kiểm tra iss → Authorization: Bearer. Server kiểm tra audience, cấm token passthrough.

Thuật ngữ (Glossary)

Message pattern
Mẫu tương tác – cách ghép request/response/notification thành tương tác: request–response, multi round-trip, subscribe–notify.
Multi Round-Trip Requests (MRTR)
Yêu cầu nhiều lượt – server trả InputRequiredResult, client gửi lại request gốc kèm inputResponses; thay cho server tự gửi request (SEP-2322).
InputRequiredResult
Kết quả "cần thêm input" – result có resultType: "input_required", chứa inputRequests và/hoặc requestState.
requestState
Trạng thái request mờ – chuỗi chỉ server hiểu, client gửi trả nguyên văn; server phải coi là dữ liệu không tin cậy.
Sampling
Lấy mẫu LLM qua client – server nhờ client gọi LLM (sampling/createMessage); deprecated từ 2026-07-28.
Model preferences / hints
Ưu tiên chọn model / gợi ý tên model – costPriority, speedPriority, intelligencePriority (0–1) và hint dạng chuỗi con; client quyết định cuối cùng.
Elicitation
Hỏi thêm thông tin người dùng – elicitation/create, form mode hoặc URL mode; kết quả accept/decline/cancel.
Form mode / URL mode
Chế độ biểu mẫu / chế độ URL – thu dữ liệu có cấu trúc qua client / dẫn người dùng tới URL ngoài cho tương tác nhạy cảm.
Roots
Thư mục gốc – danh sách URI file:// client coi là liên quan; chỉ mang tính thông tin; deprecated.
Progress notification
Thông báo tiến độ – notifications/progress với progressToken, progress, total, message.
Logging
Ghi log có cấu trúc – notifications/message theo 8 mức syslog; mức đặt qua io.modelcontextprotocol/logLevel; deprecated.
Cancellation
Hủy request – stdio: notifications/cancelled; Streamable HTTP: đóng SSE response stream.
Deprecated
Không còn khuyến nghị, sẽ bị gỡ – còn trong đặc tả ít nhất 12 tháng; triển khai mới không nên dùng.
stdio transport
Transport luồng chuẩn – client chạy server làm tiến trình con, JSON-RPC phân tách bằng xuống dòng qua stdin/stdout.
Streamable HTTP
Transport HTTP có thể stream – một MCP endpoint nhận POST, trả JSON hoặc SSE theo từng request.
Server-Sent Events (SSE)
Sự kiện do server đẩy – định dạng text/event-stream để server gửi nhiều thông điệp trên một phản hồi HTTP.
subscriptions/listen
Đăng ký lắng nghe thay đổi – stream sống lâu nhận notification thay đổi danh sách/resource đã chọn.
DNS rebinding
Tấn công gán lại DNS – trang web độc hại gọi server cục bộ; phòng bằng kiểm tra Origin, bind 127.0.0.1.
Protected Resource Metadata (RFC 9728)
Siêu dữ liệu tài nguyên được bảo vệ – tài liệu MCP server công bố, chỉ ra authorization_servers.
PKCE
Proof Key for Code Exchange – cặp verifier/challenge chống đánh cắp authorization code; MCP yêu cầu S256 khi có thể.
Resource indicator (RFC 8707)
Chỉ định tài nguyên đích – tham số resource gắn token với đúng MCP server (audience).
Client ID Metadata Document (CIMD)
Tài liệu metadata định danh client – client_id là URL HTTPS trỏ tới JSON metadata của client; thay cho DCR.
Token passthrough
Chuyển tiếp token – server dùng/chuyển tiếp token không cấp cho nó; bị cấm.
Confused deputy
Kẻ ủy quyền bị lừa – proxy có quyền bị lợi dụng để hành động thay kẻ tấn công.
Step-up authorization
Nâng cấp ủy quyền – xin thêm scope khi nhận 403 insufficient_scope.

Câu hỏi luyện tập

Một nhóm đang nâng cấp MCP server lên đặc tả 2026-07-28. Trong tool deploy, server cần người dùng xác nhận tên môi trường trước khi chạy. Code cũ ghi một JSON-RPC request elicitation/create (có id riêng) lên SSE stream rồi chờ client trả lời. Cách làm đúng ở phiên bản mới là gì?
  1. Giữ nguyên, nhưng mở thêm GET stream để gửi request elicitation/create.
  2. Trả về InputRequiredResult chứa elicitation/create trong inputRequests (kèm requestState nếu cần); client gửi lại tools/call với inputResponses.
  3. Gửi notification notifications/elicitation và chờ client gửi notification trả lời.
  4. Dùng Mcp-Session-Id để lưu trạng thái và gửi request khi client gọi lại.
Đáp án B. Từ 2026-07-28, server không được tự khởi tạo JSON-RPC request; mọi yêu cầu sampling/elicitation/roots đi qua MRTR với InputRequiredResult. A sai: GET stream endpoint đã bị bỏ, và server vẫn không được gửi request. C sai: không có notification như vậy, và notification không mang câu trả lời. D sai: session ở mức giao thức và header Mcp-Session-Id đã bị bỏ.
Một MCP server cần API key của dịch vụ thanh toán bên thứ ba thuộc về từng người dùng để thực hiện tool create_invoice. Cách nào tuân thủ đặc tả elicitation?
  1. Elicitation form mode với trường api_key kiểu string và format: "password".
  2. Yêu cầu người dùng dán API key vào chat để LLM chuyển cho tool.
  3. Dùng chính access token MCP của người dùng để gọi dịch vụ thanh toán.
  4. Elicitation URL mode dẫn tới trang HTTPS của server; người dùng nhập key trực tiếp ở đó, server lưu key gắn với danh tính người dùng.
Đáp án D. Đặc tả bắt buộc dùng URL mode cho thông tin nhạy cảm (password, API key, token, thanh toán) để dữ liệu không đi qua client hay ngữ cảnh LLM. A sai: form mode bị cấm dùng cho secret (và password không nằm trong danh sách format được hỗ trợ). B sai: key lọt vào ngữ cảnh LLM và log client — đúng điều URL mode nhằm tránh. C sai: đó là token passthrough, bị cấm; token MCP chỉ dùng cho MCP server.

  "requestState":"eyJ0Ijo..."}}

  2. Báo lỗi vì InputRequiredResult bắt buộc phải có inputRequests.
  3. Giải mã requestState (base64) để biết server cần gì rồi hỏi người dùng.

C sai: client không được đọc, phân tích hay suy đoán nội dung requestState. D sai: lần gửi lại là request độc lập nên id phải khác.

  2. Không hợp lệ vì notification phải có id để client trả lời.
  3. Thông báo thứ hai vi phạm đặc tả vì progress phải tăng sau mỗi notification.
  4. Không hợp lệ vì progressToken chỉ được là số nguyên.

Server xử lý body phải phản hồi thế nào?
  1. Thực thi read_file vì header được ưu tiên hơn body.
  2. Từ chối với 400 Bad Request và lỗi JSON-RPC HeaderMismatch (-32020).
  3. Thực thi delete_file vì body là nguồn sự thật, header bỏ qua.
  4. Trả 404 Not Found với lỗi -32601.
Đáp án B. Mcp-Name phải khớp params.name; khi không khớp, server MUST trả 400 + -32020 — để tránh lỗ hổng khi load balancer định tuyến theo header còn server thực thi theo body. A sai: body mới là nguồn sự thật. C sai: body là nguồn sự thật nhưng sự không khớp vẫn phải bị từ chối, không được lặng lẽ bỏ qua. D sai: 404/-32601 dành cho method không được cài đặt.
Client MCP gửi request không có token và nhận 401 với WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource", scope="files:read". Metadata của authorization server tìm được không có trường code_challenge_methods_supported. Client phải làm gì?
  1. Tiếp tục authorization code flow mà không dùng PKCE.
  2. Dùng PKCE phương thức plain cho chắc.
  3. Chuyển sang gửi token trong query string để tránh PKCE.
  4. Từ chối tiếp tục, vì không xác minh được authorization server hỗ trợ PKCE.
Đáp án D. Đặc tả: client MUST kiểm tra hỗ trợ PKCE qua metadata; nếu code_challenge_methods_supported vắng mặt, client MUST refuse to proceed. A sai: PKCE là bắt buộc. B sai: vẫn không xác minh được hỗ trợ và đặc tả yêu cầu S256 khi có thể. C sai: token MUST NOT nằm trong query string, và điều đó không liên quan tới PKCE.
Công ty bạn chạy một MCP server Streamable HTTP từ xa, phía trước là load balancer với nhiều instance. Những phát biểu nào đúng với đặc tả 2026-07-28? (Chọn 2)
  1. Server nên cấp Mcp-Session-Id để load balancer gắn client với một instance.
  2. Khi cần trạng thái giữa các lời gọi (ví dụ giỏ hàng), server cấp một handle tường minh và client truyền lại như tham số tool.
  3. Khi SSE stream bị đứt, client gửi Last-Event-ID để nhận tiếp các sự kiện.
  4. Server dùng GET stream để đẩy request sampling tới client.
  5. Server phải kiểm tra audience của access token, chỉ nhận token được cấp cho chính nó.
Đáp án B, E. B: changelog (SEP-2567) nêu server cần trạng thái thì dùng handle do server cấp, truyền như tham số tool thông thường. E: server MUST xác minh token được cấp cho mình (RFC 8707). A sai: session và Mcp-Session-Id đã bị bỏ; server bỏ qua header này. C sai: resumability qua Last-Event-ID đã bị bỏ — client gửi lại request với ID mới. D sai: GET stream đã bị bỏ và server không được gửi request; sampling đi qua MRTR (và đã deprecated).
Một MCP server cũ dùng sampling gửi modelPreferences: {"hints":[{"name":"claude"}], "costPriority": 0.9, "intelligencePriority": 0.2}. Host của người dùng chỉ cấu hình model của một nhà cung cấp khác. Điều nào mô tả đúng hành vi theo đặc tả?
  1. Hint chỉ mang tính tư vấn; client có thể ánh xạ sang model tương đương và ưu tiên model rẻ do costPriority cao — client quyết định cuối cùng.
  2. Client phải từ chối request vì không có model chứa chuỗi "claude".
  3. Client phải dùng đúng model có điểm thông minh thấp nhất vì intelligencePriority là 0.2.
  4. Server được quyền ép client dùng model Claude bằng cách đặt systemPrompt.
Đáp án A. Hints là chuỗi con khớp linh hoạt, mang tính tư vấn; client MAY ánh xạ sang model tương đương của nhà cung cấp khác; các priority 0–1 chỉ thể hiện mức quan trọng. B sai: không có quy định bắt từ chối. C sai: priority không ép một lựa chọn cụ thể. D sai: client MAY sửa hoặc bỏ qua systemPrompt, và nó không điều khiển việc chọn model.
