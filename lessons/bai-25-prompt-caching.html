Sau bài này bạn sẽ

  • Giải thích được prompt caching hoạt động thế nào: cache theo tiền tố (prefix), khớp chính xác 100%, theo thứ tự tools → system → messages.
  • Bật caching bằng automatic caching (một trường cache_control ở cấp cao nhất) hoặc explicit cache breakpoints (gắn cache_control lên từng block), và biết giới hạn 4 breakpoint.
  • Chọn đúng TTL 5 phút hay 1 giờ, tính được chi phí ghi/đọc cache và điểm hòa vốn.
  • Đọc các trường cache_creation_input_tokens, cache_read_input_tokens, input_tokens trong usage để kiểm tra cache có “trúng” hay không.
  • Nhận diện các thay đổi làm mất cache (tool definitions, hình ảnh, thinking, tool_choice…), dùng cache diagnostics để tìm nguyên nhân, và biết cách pre-warm cache.

🗃️Prompt caching là gì?

Theo tài liệu của Anthropic, prompt caching giúp tối ưu việc dùng API bằng cách cho phép tiếp tục xử lý từ một tiền tố (prefix) cụ thể trong prompt. Kết quả: giảm đáng kể thời gian xử lý và chi phí cho các tác vụ lặp đi lặp lại hoặc các prompt có phần nội dung không đổi.

Hãy hình dung một chatbot hỏi đáp về bộ hợp đồng 50 trang. Mỗi câu hỏi của người dùng đều phải gửi kèm toàn bộ hợp đồng trong system. Không có cache, Claude phải “đọc lại” toàn bộ hợp đồng ở mỗi request — bạn trả tiền đầy đủ cho từng token đầu vào, và phải chờ xử lý lại từ đầu. Với prompt caching, phần hợp đồng được xử lý một lần, lưu lại, và các request sau chỉ việc đọc từ cache với giá rẻ hơn nhiều.

Cơ chế 3 bước

  1. Kiểm tra – Hệ thống xem phần prompt prefix tính đến một cache breakpoint đã được cache từ một request gần đây chưa.
  2. Trúng cache (cache hit) – Nếu có, dùng bản đã cache ⇒ giảm thời gian xử lý và chi phí.
  3. Trượt cache (cache miss) – Nếu không, xử lý toàn bộ prompt rồi ghi prefix vào cache ngay khi response bắt đầu.

Ví dụ đời thường

Prompt caching giống một giáo viên đã đọc và ghi chú sẵn giáo trình từ sáng. Mỗi khi học sinh hỏi, cô không phải đọc lại cả cuốn sách mà chỉ mở phần ghi chú ra. Lưu ý

📍Bật caching: automatic hay explicit breakpoints

Có hai cách bật prompt caching trong Messages API, đều dùng trường cache_control:

🪄Automatic caching

  • Thêm một trường cache_control ở cấp cao nhất của request body.
  • Hệ thống tự đặt breakpoint lên block cuối cùng có thể cache và tự dời nó về sau khi hội thoại dài ra.
  • Phù hợp nhất cho hội thoại nhiều lượt.
  • Không có trên Amazon Bedrock (bedrock-runtime) — trả lỗi 400.

🎯Explicit cache breakpoints

  • Gắn cache_control lên từng content block (tool, system block, message block).
  • Kiểm soát chi tiết: cache riêng từng phần thay đổi với tần suất khác nhau.
  • Tối đa 4 breakpoint mỗi request.
  • Bắt buộc dùng khi pre-warm cache hoặc trên Bedrock.

Automatic caching – cách đơn giản nhất

# Python SDK – automatic caching: chỉ thêm 1 dòng cache_control ở cấp cao nhất
import anthropic

client = anthropic.Anthropic()  # đọc ANTHROPIC_API_KEY từ biến môi trường, không hard-code

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    cache_control={"type": "ephemeral"},   # ← bật automatic caching
    system="You are an AI assistant tasked with analyzing literary works. ...",
    messages=[
        {"role": "user", "content": "Analyze the major themes in 'Pride and Prejudice'."}
    ],
)
print(response.usage.model_dump_json())   # xem cache_creation / cache_read

Với automatic caching, mỗi request cache mọi thứ tới block cuối cùng có thể cache; nội dung phía trước được đọc từ cache. Bạn không cần tự dời marker khi hội thoại dài thêm.

Explicit breakpoint – cache một tài liệu lớn trong system

# Python SDK – cache tài liệu dài bằng breakpoint explicit trên system block
import anthropic

client = anthropic.Anthropic()
CONTRACT = open("contract.txt", encoding="utf-8").read()   # tài liệu ~50 trang, không đổi

def ask(question: str):
    return client.messages.create(
        model="claude-opus-5-5",
        max_tokens=1024,
        system=[
            {"type": "text",
             "text": "You are an AI assistant tasked with analyzing legal documents."},
            {"type": "text",
             "text": "Here is the full text of a complex legal agreement: " + CONTRACT,
             "cache_control": {"type": "ephemeral"}},   # ← breakpoint ở cuối phần tĩnh
        ],
        messages=[{"role": "user", "content": question}],   # phần thay đổi nằm SAU breakpoint
    )

r1 = ask("What are the key terms and conditions?")
r2 = ask("Who are the parties to this agreement?")
print(r1.usage.cache_creation_input_tokens, r1.usage.cache_read_input_tokens)  # lần 1: ghi cache, đọc 0
print(r2.usage.cache_creation_input_tokens, r2.usage.cache_read_input_tokens)  # lần 2: ghi 0, đọc = cả system
Mẹo thực chiến (Pro Tip)

Chatbot hội thoại nhiều lượt, không muốn tự quản lý vị trí marker ⇒ bắt đầu bằng automatic caching (cache_control ở cấp cao nhất). Khi prompt có nhiều phần thay đổi với tần suất khác nhau (tools hiếm đổi, tài liệu RAG đổi hằng ngày, hội thoại đổi liên tục) ⇒ chuyển sang explicit breakpoints.

Lỗi thường gặp

Code cũ gọi client.beta.prompt_caching.messages.create(...) (Python) hoặc client.beta.promptCaching.messages.create(...) (TypeScript) sẽ báo lỗi kiểu AttributeError: 'Beta' object has no attribute 'prompt_caching'. Prompt caching nay nằm ngay trên client.messages, không cần tiền tố beta.

🧭Cache breakpoints, thứ tự prefix và lookback

Để đặt cache breakpoint đúng chỗ, bạn cần nắm 4 quy tắc cốt lõi sau.

  1. Thứ tự prefix cố định: tools → system → messages. Prefix được cache bao gồm mọi thứ theo thứ tự đó, tính tới và bao gồm block có cache_control.
  2. Chỉ ghi tại breakpoint: đánh dấu một block sẽ ghi một entry — là hash tích lũy của prefix kết thúc tại block đó. Không có entry nào được ghi cho các vị trí phía trước.
  3. Đọc thì nhìn lùi: hệ thống kiểm tra hash prefix tại breakpoint; nếu không khớp, nó lùi từng block một để tìm một lần ghi trước đó.
  4. Lookback window = 20 block: mỗi breakpoint kiểm tra tối đa 20 vị trí (kể cả chính nó). Một chuỗi tool_use liên tiếp tính là một vị trí; một chuỗi tool_result liên tiếp cũng vậy.

Với bố cục ở Hình 2, tài liệu Anthropic mô tả:

  • Thêm một lượt hội thoại mới mà không sửa nội dung cũ ⇒ cả 4 đoạn cache được tái sử dụng.
  • Cập nhật tài liệu RAG nhưng giữ nguyên tools và hướng dẫn ⇒ 2 đoạn đầu vẫn được dùng lại.
  • Thay đổi hội thoại nhưng giữ tools, hướng dẫn, tài liệu ⇒ 3 đoạn đầu vẫn được dùng lại.

Lookback window hoạt động thế nào

Mẹo thực chiến (Pro Tip)

Trong đa số trường hợp, một breakpoint ở cuối phần nội dung tĩnh là đủ. Chỉ cần nhiều breakpoint khi: hội thoại dài đẩy breakpoint quá 20 block so với lần ghi trước; muốn cache độc lập các phần thay đổi với tần suất khác nhau; hoặc cần kiểm soát chính xác phần nào được cache để tối ưu chi phí. Bản thân breakpoint không tốn tiền — bạn chỉ trả cho token ghi cache, đọc cache và token đầu vào không cache.

Lỗi thường gặp

Đặt breakpoint lên block thay đổi mỗi request (ví dụ: chèn timestamp + câu hỏi của người dùng). Kết quả là request nào cũng ghi một entry mới và không bao giờ đọc được. Hãy đặt breakpoint lên block cuối cùng có prefix giống hệt giữa các request cần chia sẻ cache; phần thay đổi để sau breakpoint.

Cache tool definitions

Đặt cache_control lên tool cuối cùng trong mảng tools: mọi tool tính tới tool đó được cache thành một prefix.

// JSON request – breakpoint trên tool cuối cùng
{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "tools": [
    { "name": "get_weather",
      "description": "Get the current weather in a given location",
      "input_schema": { "type": "object",
        "properties": { "location": { "type": "string" } },
        "required": ["location"] } },
    { "name": "get_time",
      "description": "Get the current time in a given time zone",
      "input_schema": { "type": "object",
        "properties": { "timezone": { "type": "string" } },
        "required": ["timezone"] },
      "cache_control": { "type": "ephemeral" } }   // ← cache cả get_weather và get_time
  ],
  "messages": [{ "role": "user", "content": "What is the weather and time in New York?" }]
}

⏳Cache TTL: 5 phút hay 1 giờ

TTL (time to live) là thời gian tối thiểu một entry tồn tại trong cache. Mặc định là 5 phút và được làm mới miễn phí mỗi lần entry được đọc.

// TTL 5 phút (mặc định)
"cache_control": { "type": "ephemeral" }

// TTL 1 giờ
"cache_control": { "type": "ephemeral", "ttl": "1h" }
Thời điểm bắt đầu tính TTL

TTL được tính từ lúc bắt đầu request ghi hoặc đọc entry, không phải lúc response kết thúc. Ví dụ trong tài liệu: nếu response mất 4 phút để stream xong, request tiếp theo muốn dùng lại prefix (TTL 5 phút) phải bắt đầu trong khoảng 1 phút sau khi response đó hoàn tất.

Một lợi ích khác của TTL 1 giờ theo tài liệu: cải thiện việc tận dụng rate limit, vì cache hit không bị trừ vào rate limit.

Trộn hai loại TTL trong một request

Có thể dùng cả hai TTL trong cùng request, nhưng entry 1 giờ phải đứng trước entry 5 phút. Khi đó API tính tiền theo 3 vị trí:

  • A – số token tại lần cache hit cuối (0 nếu không có hit).
  • B – số token tại block cache_control 1 giờ cuối cùng sau A (bằng A nếu không có).
  • C – số token tại block cache_control cuối cùng.

Bạn trả: đọc cache cho A, ghi 1 giờ cho (B − A), ghi 5 phút cho (C − B).

Mẹo thực chiến (Pro Tip)

Agent xử lý tác vụ dài, mỗi bước có thể cách nhau vài phút (chờ tool chạy, chờ người duyệt) ⇒ dùng TTL 1 giờ cho phần prefix ổn định (system prompt, tools) để không bị trượt cache giữa chừng. Chatbot đông người dùng gửi liên tục ⇒ TTL 5 phút là đủ và rẻ hơn khi ghi.

Ví dụ tính chi phí và điểm hòa vốn

Giả sử ứng dụng dùng claude-opus-5-5, mỗi request gửi kèm một tài liệu 100.000 token (không đổi) và một câu hỏi ngắn. Bỏ qua token câu hỏi và output, chỉ tính phần tài liệu, cho 10 request trong vòng TTL 5 phút:

Cách làmPhép tính (giá Opus 5.5)Tổng
Không cache10 × 0,1 MTok × $4$4,00
Cache TTL 5 phút1 lần ghi: 0,1 × $5 = $0,50 + 9 lần đọc: 9 × 0,1 × $0,20 = $0,18$0,68

Về điểm hòa vốn (tính theo bội số của giá input cơ bản): với TTL 5 phút trên Opus 5.5, 2 request có cache tốn 1,25 + 0,05 = 1,30 so với 2,0 khi không cache ⇒ có lời ngay từ lần đọc đầu tiên. Với TTL 1 giờ, 2 request tốn 2 + 0,05 = 2,05 (lỗ nhẹ), nhưng từ request thứ 3 trở đi đã có lời (2,10 so với 3,0).

Mẹo thực chiến (Pro Tip)

Đã gắn cache_control nhưng cả cache_creation_input_tokens lẫn cache_read_input_tokens đều bằng 0 ⇒ nhiều khả năng prompt chưa đạt độ dài tối thiểu. Nếu chỉ thiếu một chút, mở rộng phần nội dung được cache (thêm ví dụ, hướng dẫn chi tiết) cho đủ ngưỡng thường đáng làm.

Có thể và không thể cache

✅Có thể cache

  • Tools – tool definitions trong mảng tools.
  • System messages – các block trong mảng system.
  • Text messages – block trong messages.content, cả lượt user và assistant.
  • Images & documents – block trong messages.content ở lượt user.
  • Tool use & tool results – block trong messages.content, lượt user hoặc assistant.

⛔Không cache trực tiếp được

  • Thinking blocks – không gắn cache_control trực tiếp được; nhưng được cache kèm nội dung khác trong lượt assistant trước đó, và khi đọc từ cache thì tính là input token.
  • Sub-content blocks (như citations) – hãy cache block cấp cao nhất; với citations thì cache block tài liệu nguồn.
  • Empty text blocks – block văn bản rỗng.

Thinking blocks và caching

  • Thinking blocks được cache như một phần nội dung request khi bạn gửi lại chúng cùng tool_result (thường gặp trong tool use).
  • Cache vẫn hợp lệ khi chỉ thêm tool_result vào lượt user.
  • Trên Claude Opus 4.5 trở về sau (dòng Opus), Sonnet 4.6 trở về sau (dòng Sonnet), Haiku 5.5 và mọi model Fable/Mythos, thinking blocks được giữ lại mặc định ngay cả khi thêm nội dung user không phải tool result ⇒ cache vẫn hợp lệ.
  • Trên các model khác, thêm nội dung user không phải tool result sẽ làm mất cache và loại bỏ mọi thinking block trước đó khỏi ngữ cảnh.

💥Điều gì làm mất cache?

Cache hit đòi hỏi các đoạn giống hệt 100%, gồm mọi văn bản và hình ảnh tính tới block có cache_control. Vì prefix theo thứ tự tools → system → messages, thay đổi ở một cấp sẽ làm mất cache của cấp đó và mọi cấp phía sau.

Lưu ý – thêm hướng dẫn giữa hội thoại

Theo tài liệu, trên một số model mới (Fable 5.2, Mythos 5.2, Fable 5.1, Mythos 5.1, Fable 5, Mythos 5, Opus 5.5, Opus 5, Opus 4.8, Sonnet 5.5, Haiku 5.5), có thể nối thêm một message {"role": "system"} vào messages để bổ sung hướng dẫn mà không làm mất cache system hay messages (không có trên Sonnet 5). Ngoài ra có tính năng inline tools (beta) với header inline-tools-2026-09-15 cho phép thêm tool giữa hội thoại mà không đổi mảng tools.

Checklist khắc phục sự cố

  1. Phần được cache giống hệt nhau giữa các lần gọi; marker explicit nằm cùng vị trí.
  2. Các lần gọi nằm trong TTL (mặc định 5 phút).
  3. tool_choice, việc dùng hình ảnh, cấu hình thinking và output_config.effort nhất quán.
  4. Nội dung được cache đạt độ dài tối thiểu của model và nền tảng.
  5. Breakpoint nằm trên block không đổi giữa các request.
  6. Key trong input của tool_use có thứ tự ổn định — một số ngôn ngữ (ví dụ Swift, Go) xáo trộn thứ tự key khi chuyển JSON, làm vỡ cache.

Cache diagnostics

Không có công cụ này, tín hiệu duy nhất là usage.cache_read_input_tokens tụt về 0 mà không biết vì sao. Cache diagnostics cho API so sánh hai request liên tiếp và báo chỗ prefix bắt đầu khác nhau. Bạn gửi đối tượng diagnostics trong mọi lượt: lượt đầu dùng "previous_message_id": null, các lượt sau truyền id của response trước.

# Python – cache diagnostics (theo ví dụ trong tài liệu, dùng client.beta.messages)
SYSTEM = "You are an AI assistant analyzing a large document. ..."

r1 = client.beta.messages.create(
    model="claude-opus-5-5", max_tokens=1024,
    cache_control={"type": "ephemeral"}, system=SYSTEM,
    messages=[{"role": "user", "content": "Summarize section 1."}],
    diagnostics={"previous_message_id": None},        # opt-in, chưa có gì để so
)
r2 = client.beta.messages.create(
    model="claude-opus-5-5", max_tokens=1024,
    cache_control={"type": "ephemeral"}, system=SYSTEM,
    messages=[
        {"role": "user", "content": "Summarize section 1."},
        {"role": "assistant", "content": r1.content},
        {"role": "user", "content": "Now summarize section 2."},
    ],
    diagnostics={"previous_message_id": r1.id},       # so với request trước
)
d = r2.diagnostics
if d is None:
    print("Không phát hiện khác biệt.")
elif d.cache_miss_reason is None:
    print("Đang so sánh, chưa có kết quả.")
else:
    print(d.cache_miss_reason.type)   # vd "system_changed"
cache_miss_reason.typeÝ nghĩa
model_changedModel khác request trước (router, A/B test, fallback). Cache gắn theo từng model.
system_changedsystem khác — thường do chèn timestamp, request ID vào system prompt.
tools_changedMảng tools khác: thêm, bớt, đổi thứ tự, hoặc input_schema serialize không ổn định.
messages_changedModel, system, tools khớp nhưng một message cũ bị sửa/xóa/đổi thứ tự thay vì chỉ nối thêm.
previous_message_not_foundKhông tìm thấy fingerprint cho previous_message_id (request trước không bật diagnostics, khác workspace, hoặc quá lâu). Không phải bằng chứng request đã đổi.
unavailableKhông có thông tin chẩn đoán cho request này.

Bốn loại *_changed còn kèm cache_missed_input_tokens — ước lượng số token nằm sau điểm phân kỳ, chỉ nên xem như độ lớn. Diagnostics là best-effort: không bao giờ chặn hay làm request thất bại, và fingerprint chỉ chứa hash và ước lượng số token, không chứa nội dung prompt.

🔥Pre-warming, Batch, đồng thời và bảo mật

Pre-warm cache với max_tokens: 0

Muốn người dùng đầu tiên cũng được hưởng cache hit? Gửi trước một request với max_tokens: 0. API ghi cache tại breakpoint rồi trả về ngay với content rỗng, stop_reason: "max_tokens" và usage đầy đủ. Không tính token output, chỉ tính phí ghi cache nếu prefix chưa có trong cache.

# Python – pre-warm system prompt dùng chung trước giờ cao điểm
prewarm = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=0,                                 # chỉ ghi cache, không sinh output
    system=[{
        "type": "text",
        "text": "You are an expert software engineer with deep knowledge of distributed systems...",
        "cache_control": {"type": "ephemeral"},     # breakpoint EXPLICIT trên phần dùng chung
    }],
    messages=[{"role": "user", "content": "warmup"}],  # placeholder, chuỗi bất kỳ không rỗng
)
print(prewarm.stop_reason)   # "max_tokens"
print(prewarm.content)       # []
  • Đặt breakpoint lên block cuối dùng chung với request thật (thường là system hoặc tools), không đặt lên message placeholder; dùng breakpoint explicit, không dùng automatic caching.
  • Dùng cùng cấu hình thinking và output_config.effort với các request sau.
  • Bị từ chối (invalid_request_error) khi có stream: true, extended thinking (thinking.type: "enabled"), structured outputs (output_config.format), tool_choice loại tool hoặc any, hoặc khi nằm trong Message Batches.
  • Với TTL 5 phút phải pre-warm lại ít nhất mỗi 5 phút; khoảng trống dài hơn thì dùng TTL 1 giờ.
  • Nên dùng max_tokens: 0 thay cho mẹo cũ max_tokens: 1: không có output phải bỏ đi và không tính token output.

Request song song và Message Batches

Prompt caching dùng được với Message Batches API, nhưng vì các request trong batch có thể chạy đồng thời và theo thứ tự bất kỳ, cache hit chỉ ở mức best-effort. Cách hiệu quả theo tài liệu: gom các request có chung prefix; gửi trước một batch chỉ gồm một request có prefix đó với block cache 1 giờ; khi job hoàn tất thì gửi phần còn lại. TTL 1 giờ thường tốt hơn 5 phút vì batch hay mất từ 5 phút đến 1 giờ để chạy xong.

Mẹo thực chiến (Pro Tip)

Hệ thống fan-out gửi 50 request song song cùng một tài liệu dài ⇒ gửi một request trước (hoặc pre-warm với max_tokens: 0), chờ response bắt đầu, rồi mới gửi 49 request còn lại. Nếu không, cả 50 request đều trượt cache và đều trả phí ghi cache.

Bảo mật, quyền riêng tư và cô lập dữ liệu

  • Cô lập theo organization: các organization không bao giờ dùng chung cache, kể cả khi prompt giống hệt.
  • Cô lập theo workspace: trên Claude API, Claude Platform on AWS và Microsoft Foundry, mỗi workspace có cache riêng; trên Google Cloud (Google managed) và Amazon Bedrock chỉ cô lập theo organization.
  • Cache key là hash mật mã của prompt tới điểm cache_control ⇒ chỉ request có prompt giống hệt mới truy cập được entry đó.
  • ZDR: prompt caching đủ điều kiện zero data retention; Anthropic không lưu văn bản thô của prompt hay response. Biểu diễn KV cache và hash chỉ nằm trong bộ nhớ, bị xóa sau khi hết TTL.
  • Không xóa cache thủ công được: entry tự hết hạn sau tối thiểu 5 phút không dùng.
Lỗi thường gặp – an toàn ứng dụng

Cache không thay thế cơ chế phân quyền của bạn. Nếu ứng dụng phục vụ nhiều khách hàng (multi-tenant) chung một workspace, đừng gộp dữ liệu của nhiều khách vào cùng một system prompt được cache rồi “dặn” Claude chỉ trả lời phần của từng người — đó vẫn là rủi ro rò rỉ dữ liệu và prompt injection. Tách ngữ cảnh theo từng khách hàng, áp dụng nguyên tắc least privilege, và luôn đọc API key từ biến môi trường ANTHROPIC_API_KEY, không hard-code vào mã nguồn (theo IPA「安全なウェブサイトの作り方」/「セキュア・プログラミング講座」).

Best practices tổng hợp

  1. Bắt đầu bằng automatic caching cho hội thoại nhiều lượt.
  2. Dùng breakpoint explicit cho các phần thay đổi với tần suất khác nhau.
  3. Cache nội dung ổn định: system instructions, thông tin nền, ngữ cảnh lớn, tool definitions dùng thường xuyên.
  4. Đặt nội dung được cache ở đầu prompt.
  5. Đặt breakpoint lên block cuối cùng giữ nguyên giữa các request.
  6. Theo dõi tỉ lệ cache hit qua các trường usage; dùng cache diagnostics khi tỉ lệ tụt bất thường.

🧪Thực hành

Chuẩn bị: pip install anthropic, đặt biến môi trường ANTHROPIC_API_KEY (không ghi key vào code hay commit lên Git). Chuẩn bị một file văn bản dài (ví dụ tài liệu nội bộ, điều khoản dịch vụ) có ít nhất vài nghìn token — đủ vượt ngưỡng 512 token của claude-opus-5-5.

  1. Bài tập 1 – Đo cache hit. Viết hàm ask(question) gửi file tài liệu trong system với breakpoint explicit ở cuối block tài liệu (như ví dụ ở phần “Bật caching”). Gọi 3 câu hỏi khác nhau liên tiếp, in cache_creation_input_tokens, cache_read_input_tokens, input_tokens mỗi lần.
    Kết quả mong đợi: lần 1 có cache_creation_input_tokens ≈ độ dài system, cache_read_input_tokens = 0; lần 2 và 3 ngược lại (ghi 0, đọc ≈ độ dài system), input_tokens chỉ còn vài chục token của câu hỏi.
  2. Bài tập 2 – Cố tình làm vỡ cache. Sửa hàm ở bài 1 để chèn datetime.now().isoformat() vào đầu system prompt. Gọi lại 2 lần và quan sát usage. Sau đó bật cache diagnostics (truyền diagnostics={"previous_message_id": ...} với client.beta.messages.create) và in cache_miss_reason.type. Cuối cùng chuyển timestamp vào tin nhắn user (sau breakpoint).
    Kết quả mong đợi: khi timestamp ở đầu system, lần nào cũng ghi cache mới, đọc = 0; diagnostics báo system_changed. Khi dời timestamp ra sau breakpoint, cache hit trở lại.
  3. Bài tập 3 – Chatbot nhiều lượt với automatic caching. Viết vòng lặp hội thoại 5 lượt, mỗi lượt nối câu trả lời của Claude và câu hỏi mới vào messages, request dùng cache_control={"type": "ephemeral"} ở cấp cao nhất. Ghi lại tổng token đầu vào (công thức 3 trường) và tỉ lệ cache_read_input_tokens / total mỗi lượt.
    Kết quả mong đợi: tỉ lệ đọc từ cache tăng dần qua các lượt; tự tính chi phí theo bảng giá Opus 5.5 và so với trường hợp không cache.
  4. Bài tập 4 (tùy chọn) – Pre-warm. Gửi request max_tokens=0 với system dùng chung, sau đó gửi request thật. Kiểm tra stop_reason, content của request pre-warm và cache_read_input_tokens của request thật.
    Kết quả mong đợi: pre-warm trả stop_reason: "max_tokens", content: [], có cache_creation_input_tokens; request thật có cache_read_input_tokens > 0 ngay từ lần đầu.
# Khung code gợi ý cho bài tập 3 – automatic caching nhiều lượt
import anthropic

client = anthropic.Anthropic()          # ANTHROPIC_API_KEY từ biến môi trường
SYSTEM = open("handbook.txt", encoding="utf-8").read()
history = []

for q in ["Chính sách nghỉ phép?", "Còn làm việc từ xa?", "Tóm tắt 2 ý trên"]:
    history.append({"role": "user", "content": q})
    r = client.messages.create(
        model="claude-opus-5-5",
        max_tokens=1024,
        cache_control={"type": "ephemeral"},   # breakpoint tự dời theo hội thoại
        system=SYSTEM,
        messages=history,
    )
    history.append({"role": "assistant", "content": r.content})
    u = r.usage
    total = u.cache_read_input_tokens + u.cache_creation_input_tokens + u.input_tokens
    print(f"read={u.cache_read_input_tokens} write={u.cache_creation_input_tokens} "
          f"uncached={u.input_tokens} hit_ratio={u.cache_read_input_tokens/total:.0%}")

Tóm tắt ghi nhớ

Key takeaways
  • Prompt caching cache theo prefix, thứ tự tools → system → messages, khớp chính xác 100%; caching không làm thay đổi output.
  • Hai cách bật: automatic (cache_control ở cấp cao nhất, hợp với multi-turn) và explicit breakpoints (gắn trên block, tối đa 4).
  • Breakpoint chỉ ghi tại vị trí đánh dấu; khi đọc thì nhìn lùi tối đa 20 block. Breakpoint đặt trên block cuối không đổi; phần thay đổi để sau.
  • TTL mặc định 5 phút (làm mới miễn phí), tùy chọn 1 giờ ("ttl": "1h"); TTL tính từ lúc request bắt đầu.
  • Giá: ghi 5 phút 1,25×, ghi 1 giờ 2×, đọc 0,1× giá input (Opus 5.5/Sonnet 5.5: 0,05×) — theo tài liệu, kiểm tra 2026-11-20. Breakpoint không tốn phí.
  • total = cache_read_input_tokens + cache_creation_input_tokens + input_tokens; input_tokens chỉ là phần sau breakpoint cuối.
  • Dưới ngưỡng tối thiểu (512 token với các model mới nhất) thì không cache và không báo lỗi — cả hai trường cache đều bằng 0.
  • Đổi tool definitions làm mất toàn bộ cache; đổi tool_choice hay hình ảnh chỉ mất cache messages. Dùng cache diagnostics để biết chỗ phân kỳ.
  • Pre-warm với max_tokens: 0; request song song phải chờ response đầu tiên bắt đầu; Batch chỉ cache best-effort (nên dùng 1 giờ).

Thuật ngữ (Glossary)

Prompt caching
Bộ nhớ đệm prompt – tính năng lưu lại phần prefix đã xử lý của prompt để các request sau đọc lại, giảm chi phí và độ trễ.
cache_control
Trường điều khiển cache – đặt ở cấp cao nhất (automatic) hoặc trên từng block (explicit); giá trị {"type": "ephemeral"}, tùy chọn "ttl": "1h".
Cache breakpoint
Điểm ngắt cache – block được gắn cache_control; prefix tính tới block này được ghi thành một entry. Tối đa 4 mỗi request.
Automatic caching
Cache tự động – hệ thống tự đặt breakpoint lên block cuối có thể cache và tự dời theo hội thoại.
Explicit cache breakpoint
Điểm ngắt cache tường minh – lập trình viên tự gắn cache_control lên từng block.
Prompt prefix
Tiền tố prompt – phần đầu prompt theo thứ tự tools → system → messages, tính tới breakpoint.
Cache hit / cache miss
Trúng / trượt cache – tìm thấy hoặc không tìm thấy entry khớp với prefix.
Cache write
Ghi cache – tạo entry mới; tính phí 1,25× (5 phút) hoặc 2× (1 giờ) giá input.
Cache read / refresh
Đọc / làm mới cache – dùng entry có sẵn; tính phí theo hệ số thấp (0,1× ở đa số model) và làm mới TTL.
TTL (time to live)
Thời gian sống của cache – mặc định 5 phút, tùy chọn 1 giờ; tính từ lúc request bắt đầu.
Lookback window
Cửa sổ nhìn lùi – mỗi breakpoint kiểm tra tối đa 20 vị trí block phía trước để tìm entry đã ghi.
cache_creation_input_tokens
Token ghi vào cache ở request hiện tại.
cache_read_input_tokens
Token đọc từ cache ở request hiện tại.
input_tokens (khi có cache)
Token không được cache – chỉ phần sau breakpoint cuối cùng.
Minimum cacheable prompt length
Độ dài tối thiểu để cache – ngưỡng token theo model (512 / 1.024 / 2.048 / 4.096); dưới ngưỡng thì không cache, không báo lỗi.
Cache invalidation
Làm mất hiệu lực cache – thay đổi ở một cấp prefix khiến cache cấp đó và các cấp sau không dùng được.
Cache diagnostics
Chẩn đoán cache – so sánh request với request trước (diagnostics.previous_message_id) và trả cache_miss_reason.
Pre-warming
Làm nóng cache trước – gửi request max_tokens: 0 để ghi cache trước khi người dùng thật tới.
Workspace isolation
Cô lập theo workspace – mỗi workspace có cache riêng (trên Claude API, Claude Platform on AWS, Microsoft Foundry).

Câu hỏi luyện tập

Một công ty xây chatbot hỏi đáp trên bộ quy chế nội bộ 80.000 token. System prompt bắt đầu bằng dòng "Hôm nay là {ngày giờ hiện tại}", tiếp theo là toàn bộ quy chế, block cuối có cache_control. Dù người dùng hỏi liên tục, cache_read_input_tokens luôn bằng 0. Cách khắc phục đúng nhất là gì?
  1. Đổi TTL sang "1h" để entry tồn tại lâu hơn.
  2. Thêm breakpoint thứ hai ngay sau dòng ngày giờ.
  3. Đưa thông tin ngày giờ ra khỏi phần prefix được cache (ví dụ chuyển vào tin nhắn user, sau breakpoint), giữ quy chế ở đầu prompt.
  4. Chuyển sang automatic caching để hệ thống tự xử lý.
Đáp án C. Cache khớp theo prefix chính xác 100%; ngày giờ ở đầu system khiến prefix khác nhau mỗi request nên lần nào cũng ghi mới, không bao giờ đọc được. Phải đặt phần thay đổi sau breakpoint. A sai: TTL dài hơn không giúp gì khi prefix đã khác. B sai: breakpoint ngay sau dòng ngày giờ vẫn bao gồm dòng đó trong prefix nên vẫn trượt. D sai: automatic caching vẫn cache theo prefix, timestamp ở đầu vẫn làm vỡ cache.
Những phát biểu nào đúng về các trường trong usage khi dùng prompt caching? (Chọn 2)
  1. Tổng token đầu vào = cache_read_input_tokens + cache_creation_input_tokens + input_tokens.
  2. input_tokens luôn là tổng số token đầu vào của request.
  3. Token trong cache_read_input_tokens tính phí 1,25× giá input cơ bản.
  4. Nếu đã gắn cache_control mà cả cache_creation_input_tokens và cache_read_input_tokens đều bằng 0, nhiều khả năng prompt chưa đạt độ dài tối thiểu.
  5. cache_creation_input_tokens bao gồm cả số token output của response.
Đáp án A, D. A là công thức trong tài liệu. D đúng: dưới ngưỡng tối thiểu thì không cache và không báo lỗi. B sai: khi có cache, input_tokens chỉ là phần sau breakpoint cuối. C sai: 1,25× là giá ghi cache 5 phút; đọc cache rẻ hơn nhiều (0,1× ở đa số model). E sai: đây là token đầu vào được ghi vào cache, không liên quan output.
Đọc request sau (rút gọn). Request này có 4 block (1 tool, 2 system block, 1 message block) đều gắn "cache_control": {"type": "ephemeral"}, đồng thời có thêm trường cấp cao nhất: 
{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "cache_control": {"type": "ephemeral"},
  "tools": [ ..., {"name": "get_document", ..., "cache_control": {"type": "ephemeral"}} ],
  "system": [ {..., "cache_control": {"type": "ephemeral"}},
              {..., "cache_control": {"type": "ephemeral"}} ],
  "messages": [ {"role": "user", "content": [ {..., "cache_control": {"type": "ephemeral"}} ]} ]
}
Điều gì xảy ra?
  1. API bỏ qua trường cấp cao nhất và dùng 4 breakpoint explicit.
  2. API trả lỗi 400 vì đã có 4 breakpoint explicit, không còn slot cho automatic caching.
  3. API tạo 5 entry cache, mỗi breakpoint một entry.
  4. API chỉ giữ breakpoint cuối cùng và bỏ các breakpoint còn lại.
Đáp án B. Tối đa 4 breakpoint mỗi request, và automatic caching chiếm 1 slot. Tài liệu nêu rõ: nếu đã có 4 breakpoint explicit ở cấp block thì API trả lỗi 400. A sai: API không âm thầm bỏ qua trong trường hợp này. C sai: không thể có 5 breakpoint. D sai: không có cơ chế tự cắt bớt breakpoint. (Lưu ý: nếu block cuối đã có breakpoint explicit cùng TTL và còn slot thì automatic là no-op — nhưng ở đây hết slot.)
Một agent nghiên cứu chạy nhiều bước, mỗi bước chờ tool bên ngoài từ 10 đến 20 phút rồi mới gọi lại Claude với cùng system prompt và tool definitions dài. Đội phát triển thấy phần lớn request bị trượt cache. Lựa chọn phù hợp nhất?
  1. Giữ TTL 5 phút và tăng số breakpoint lên 4.
  2. Gọi API xóa cache thủ công trước mỗi bước để ghi lại từ đầu.
  3. Bỏ caching vì khoảng cách giữa các bước quá dài.
  4. Dùng "ttl": "1h" cho breakpoint trên phần system prompt và tools.
Đáp án D. Tài liệu khuyên dùng TTL 1 giờ khi prompt được dùng thưa hơn 5 phút nhưng dày hơn 1 giờ, ví dụ agent có bước chạy lâu. A sai: thêm breakpoint không kéo dài thời gian sống; sau 5 phút entry đã hết hạn. B sai: không có cách xóa cache thủ công. C sai: vẫn có lợi đáng kể với TTL 1 giờ (từ request thứ 3 đã hòa vốn trên Opus 5.5).
Một lập trình viên gửi request tới claude-opus-5-5 với system prompt ngắn có cache_control. Response trả về: 
"usage": {
  "input_tokens": 300,
  "cache_creation_input_tokens": 0,
  "cache_read_input_tokens": 0,
  "output_tokens": 120
}
Gửi lại y hệt vẫn ra kết quả như vậy. Giải thích hợp lý nhất?
  1. Prompt chỉ khoảng 300 token, dưới ngưỡng tối thiểu 512 token của Claude Opus 5.5, nên không được cache (và không báo lỗi).
  2. Claude Opus 5.5 không hỗ trợ prompt caching.
  3. Cache đã được ghi nhưng API ẩn số token đọc ở request thứ hai.
  4. Phải thêm header beta prompt caching thì mới hoạt động.
Đáp án A. Ngưỡng tối thiểu của Opus 5.5 là 512 token; dưới ngưỡng thì xử lý không cache và cả hai trường cache bằng 0. B sai: prompt caching hỗ trợ mọi model đang hoạt động. C sai: cache_read_input_tokens luôn phản ánh số token đọc từ cache. D sai: prompt caching nằm trên client.messages, không cần tiền tố/header beta.
Ứng dụng dùng breakpoint ở cả tools, system và tin nhắn cuối. Thay đổi nào sau đây làm mất cache của cả ba cấp tools, system và messages?
  1. Nối thêm một lượt user mới vào cuối messages.
  2. Đổi tool_choice từ auto sang any.
  3. Sửa phần description của một tool trong mảng tools.
  4. Bật web search tool.
Đáp án C. Theo bảng invalidation, thay đổi tool definitions (tên, mô tả, tham số) làm mất toàn bộ cache vì tools đứng đầu prefix. A sai: nối thêm lượt mới không làm đổi prefix cũ; cache vẫn được đọc. B sai: tool_choice chỉ làm mất cache messages. D sai: bật web search làm đổi system prompt nên mất cache system và messages, nhưng cache tools vẫn còn.
Một đội muốn pre-warm cache system prompt dùng chung trước giờ cao điểm. Những phát biểu nào đúng? (Chọn 2)
  1. Có thể pre-warm bằng request stream: true để nhận phản hồi nhanh hơn.
  2. Request max_tokens: 0 trả về content rỗng và stop_reason: "max_tokens", không tính token output.
  3. Nên dùng automatic caching cho request pre-warm để breakpoint tự đặt đúng chỗ.
  4. Request pre-warm bị tính phí như một request bình thường có output 1 token.
  5. Breakpoint explicit phải nằm trên block cuối dùng chung với request thật (thường là system hoặc tools), không đặt trên message placeholder.
Đáp án B, E. Đây là hai yêu cầu/đặc tính nêu trong tài liệu. A sai: stream: true bị từ chối với invalid_request_error. C sai: tài liệu yêu cầu breakpoint explicit, không dùng automatic (automatic sẽ đặt breakpoint lên message placeholder “warmup” vốn không dùng chung). D sai: max_tokens: 0 không tính token output; đó là ưu điểm so với mẹo cũ max_tokens: 1.
Hệ thống phân tích hồ sơ gửi đồng thời 30 request dùng chung một tài liệu 60.000 token có breakpoint. Log cho thấy cả 30 request đều có cache_creation_input_tokens lớn và cache_read_input_tokens = 0. Nguyên nhân chính?
  1. Mỗi request được gửi tới một organization khác nhau.
  2. Tài liệu vượt quá kích thước tối đa có thể cache.
  3. Prompt caching không hoạt động khi có nhiều request trong cùng một phút.
  4. Entry cache chỉ khả dụng sau khi response đầu tiên bắt đầu; các request gửi cùng lúc đều chưa thấy entry nên đều ghi mới.
Đáp án D. Tài liệu nêu: muốn cache hit cho request song song, hãy chờ response đầu tiên bắt đầu rồi mới gửi các request khác (hoặc pre-warm trước). A sai: cùng một hệ thống dùng cùng organization; tình huống không gợi ý điều này. B sai: tài liệu không nêu giới hạn như vậy; tài liệu dài chính là trường hợp nên cache. C sai: không có giới hạn kiểu này; vấn đề là thời điểm entry sẵn sàng.
Dùng claude-opus-5-5 (theo tài liệu kiểm tra 2026-11-20: input $4/MTok, ghi cache 5 phút $5/MTok, đọc cache $0.20/MTok). Mỗi request kèm cùng tài liệu 100.000 token. Chỉ tính phần tài liệu, chi phí cho 10 request liên tiếp trong vòng TTL 5 phút, có dùng cache, là bao nhiêu?
  1. $0,68
  2. $4,00
  3. $0,50
  4. $5,00
Đáp án A. Request 1 ghi cache: 0,1 MTok × $5 = $0,50; 9 request sau đọc cache: 9 × 0,1 × $0,20 = $0,18; tổng $0,68. B sai: $4,00 là chi phí khi không cache (10 × 0,1 × $4). C sai: chỉ tính lần ghi, quên 9 lần đọc. D sai: tính cả 10 lần đều là ghi cache.
Sau khi bật cache diagnostics, một response có: 
"usage": { "input_tokens": 42, "cache_read_input_tokens": 0,
           "cache_creation_input_tokens": 41850, "output_tokens": 210 },
"diagnostics": { "cache_miss_reason": {
    "type": "system_changed", "cache_missed_input_tokens": 41850 } }
Nguyên nhân có khả năng cao nhất và hướng xử lý?
  1. Entry cache đã hết TTL; chuyển sang TTL 1 giờ.
  2. Có giá trị thay đổi theo từng request (timestamp, request ID…) được chèn vào system; cần loại bỏ hoặc dời nó ra sau breakpoint.
  3. Router đã chọn model khác; cần cố định model.
  4. Prompt dưới ngưỡng tối thiểu; cần thêm nội dung.
Đáp án B. system_changed nghĩa là tham số system khác request trước, thường do chèn timestamp/request ID. A sai: hết TTL thì diagnostics trả null (request không đổi) kèm số đọc cache thấp, không phải system_changed. C sai: đổi model sẽ báo model_changed. D sai: 41.850 token vượt xa ngưỡng tối thiểu, và lý do được báo là thay đổi system.
