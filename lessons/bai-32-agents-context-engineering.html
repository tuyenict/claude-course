Sau bài này bạn sẽ

  • Mô tả được agent loop: Claude dùng tool, nhận phản hồi từ môi trường, rồi quyết định bước tiếp theo.
  • Giải thích vì sao agent phải lấy ground truth từ môi trường ở mỗi bước (environment inspection).
  • Phân biệt context engineering với prompt engineering, và hiểu hiện tượng context rot.
  • Chọn đúng kỹ thuật cho tác vụ dài: compaction, structured note-taking hay sub-agents.
  • Cấu hình context editing (clear_tool_uses_20250919) và memory tool (memory_20250818) trên Claude API.

🤖Agent là gì: LLM dùng tool trong một vòng lặp

Bài trước (bài 31) so sánh workflow với agent. Bài này đi sâu vào bên trong một agent: nó vận hành ra sao, nhìn thấy gì về môi trường, và làm thế nào để giữ "trí nhớ làm việc" của nó gọn gàng khi tác vụ kéo dài hàng giờ.

Trong bài Building effective agents, Anthropic phân biệt hai loại hệ thống agentic:

  • Workflow: LLM và tool được điều phối qua các nhánh code định sẵn ("predefined code paths").
  • Agent: LLM tự điều khiển quy trình và việc dùng tool của mình, tự quyết cách hoàn thành nhiệm vụ.

Bài Effective context engineering for AI agents (Anthropic, 29/09/2025) đưa ra định nghĩa ngắn gọn hơn nữa: agent là "LLMs autonomously using tools in a loop" – các LLM tự chủ sử dụng tool trong một vòng lặp. Còn theo Building effective agents, agent "thường chỉ là LLM dùng tool dựa trên phản hồi từ môi trường, trong một vòng lặp".

Ví dụ đời thường

Hãy hình dung một thợ sửa ống nước đến nhà bạn. Anh không có kịch bản cố định. Anh nhìn chỗ rò (quan sát), vặn thử một van (hành động), xem nước còn chảy không (phản hồi), rồi quyết định bước kế tiếp. Anh mang theo hộp đồ nghề (tools), và ghi chú vào sổ nếu phải quay lại hôm sau (memory). Agent làm việc y như vậy.

Vòng đời của một agent

  1. Khởi động – Agent bắt đầu từ một lệnh hoặc cuộc trao đổi với người dùng. Khi nhiệm vụ đã rõ, agent tự lập kế hoạch và làm việc độc lập.
  2. Hành động – Claude trả về khối tool_use (với stop_reason: "tool_use"); ứng dụng thực thi tool.
  3. Quan sát – Kết quả tool (tool_result) hoặc kết quả chạy code được đưa lại cho Claude: đây là "ground truth" từ môi trường.
  4. Đánh giá tiến độ – Claude so kết quả với mục tiêu, quyết định gọi tool tiếp, đổi hướng, hay dừng lại hỏi người dùng tại các checkpoint.
  5. Kết thúc – Thường là khi hoàn thành nhiệm vụ; nhưng nên có stopping condition như số vòng lặp tối đa để giữ quyền kiểm soát.

Khi nào nên dùng agent?

Anthropic khuyên luôn bắt đầu bằng giải pháp đơn giản nhất và chỉ thêm độ phức tạp khi thật cần. Agent phù hợp với bài toán mở, khi không thể đoán trước số bước và không thể hard-code một lộ trình cố định. Đổi lại, tính tự chủ kéo theo chi phí cao hơn và nguy cơ lỗi cộng dồn (compounding errors). Vì vậy tài liệu khuyến nghị kiểm thử kỹ trong sandboxed environment, kèm guardrails phù hợp.

👀Environment inspection: lấy ground truth từ môi trường

Một agent đáng tin không "đoán" trạng thái thế giới. Ở mỗi bước, nó cần lấy ground truth từ môi trường, tức là kết quả thực của tool call hoặc của việc chạy code, để đánh giá mình đang tiến gần hay xa mục tiêu. Đây là ý nghĩa của environment inspection.

userSửa giúp tôi test test_invoice_total đang fail.
assistant[tool_use: bash {"command": "pytest tests/test_invoice.py -x -q"}]
tool_resultFAILED tests/test_invoice.py::test_invoice_total – AssertionError: 109.0 != 110.0
assistantKết quả lệch 1.0. Tôi sẽ xem hàm tính thuế trước khi sửa. [tool_use: text_editor {"command": "view", "path": "/repo/src/invoice.py"}]
tool_result(nội dung file…) round(subtotal * 0.09)
assistantLỗi làm tròn sớm. Đã sửa; chạy lại test để xác nhận. [tool_use: bash {"command": "pytest tests/test_invoice.py -q"}]
tool_result3 passed

Để ý cách agent hành xử: nó không tuyên bố "đã sửa xong" ngay sau khi chỉnh code. Nó chạy lại test để lấy bằng chứng từ môi trường. Bài Building effective agents nêu rõ coding agent hiệu quả chính vì "lời giải code kiểm chứng được bằng test tự động".

Metadata cũng là tín hiệu

Theo Anthropic, agent tận dụng cả metadata của môi trường: cấu trúc thư mục, quy ước đặt tên, timestamp. Ví dụ: một file tên test_utils.py nằm trong thư mục tests ngụ ý mục đích khác hẳn file cùng tên nằm trong src/core_logic/. Agent "đọc" được cấu trúc này mà không cần mở từng file.

Thiết kế tool để agent quan sát tốt: ACI

Anthropic gọi giao diện giữa agent và tool là agent-computer interface (ACI), và khuyên đầu tư vào ACI nhiều như đầu tư vào giao diện người dùng (HCI). Một số nguyên tắc:

  • Đặt mình vào vị trí model: đọc description và tham số, việc dùng tool có hiển nhiên không? Mô tả tốt gồm ví dụ sử dụng, edge case, yêu cầu định dạng đầu vào và ranh giới với các tool khác.
  • Viết như docstring cho một lập trình viên junior trong nhóm.
  • Thử với nhiều input mẫu để xem model hay mắc lỗi gì, rồi cải tiến.
  • Poka-yoke: đổi tham số sao cho khó dùng sai.
Case study: SWE-bench

Khi xây agent cho SWE-bench, Anthropic thấy model hay dùng sai đường dẫn tương đối sau khi agent đã cd ra khỏi thư mục gốc. Cách sửa không phải là thêm chỉ dẫn vào prompt, mà là đổi tool để luôn yêu cầu đường dẫn tuyệt đối. Sau thay đổi, model dùng tool "hoàn hảo". Nhóm cho biết họ dành nhiều thời gian tối ưu tool hơn là tối ưu prompt tổng thể.

Mẹo thực chiến (Pro Tip)

Agent cứ lặp lại một lỗi khi dùng tool (sai định dạng ngày, sai đường dẫn…) ⇒ trước khi viết thêm cảnh báo vào system prompt, hãy sửa chính tool (poka-yoke): ép kiểu tham số, đổi sang đường dẫn tuyệt đối, trả thông báo lỗi rõ ràng có hướng dẫn sửa.

Lỗi thường gặp

Tin vào "lời kể" của model thay vì môi trường: agent nói "đã deploy thành công" nhưng không có tool call nào kiểm tra trạng thái deploy. Hãy thiết kế để agent xác minh bằng tool (chạy test, đọc lại bản ghi) và để ứng dụng của bạn kiểm tra độc lập các bước quan trọng.

🧠Context engineering: bước tiến tiếp theo của prompt engineering

Context, theo Anthropic, là tập hợp các token được đưa vào khi lấy mẫu (sampling) từ một LLM. Nó gồm system prompt, định nghĩa tool, ví dụ, lịch sử hội thoại, kết quả tool, dữ liệu ngoài, MCP…

Anthropic coi context engineering là "sự tiến hóa tự nhiên của prompt engineering":

✍️Prompt engineering

  • Viết và tổ chức chỉ dẫn (instructions) cho LLM.
  • Trọng tâm: system prompt tối ưu.
  • Thường là việc làm một lần cho một tác vụ (phân loại, sinh văn bản một lượt).

🧠Context engineering

  • Tuyển chọn và duy trì toàn bộ thông tin đi vào model lúc suy luận.
  • Gồm: system prompt, tools, examples, message history, dữ liệu ngoài, MCP.
  • Mang tính lặp: mỗi lượt đều phải quyết định đưa gì vào ngữ cảnh.

Một agent chạy trong vòng lặp liên tục sinh ra dữ liệu mới: kết quả tool, file đã đọc, ghi chú. Những dữ liệu đó có thể liên quan đến lượt kế tiếp. Context engineering là nghệ thuật chọn ra cái gì thực sự được vào cửa sổ ngữ cảnh hữu hạn ở mỗi lượt.

Nguyên tắc dẫn đường

Tìm "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome": tập token nhỏ nhất, giàu tín hiệu nhất, giúp tối đa khả năng đạt kết quả mong muốn.

📉Context rot và attention budget

Vì sao không cứ nhét hết vào context window, nhất là khi các model hiện hành có context window 1M token (theo trang Models overview, kiểm tra ngày 2026-11-20)? Vì có hiện tượng context rot: khi số token trong ngữ cảnh tăng, khả năng nhớ lại chính xác thông tin trong ngữ cảnh đó giảm đi.

  • Suy giảm diễn ra theo dốc thoai thoải (gradient), không phải rơi xuống vực. Model vẫn hoạt động tốt ở ngữ cảnh dài, nhưng độ chính xác khi truy hồi thông tin và suy luận dài hạn có thể kém hơn so với ngữ cảnh ngắn.
  • Hiện tượng xuất hiện ở mọi model, dù mức độ khác nhau.

Attention budget: "ngân sách chú ý"

Anthropic so sánh LLM với con người có working memory giới hạn: LLM có một attention budget khi xử lý lượng lớn ngữ cảnh. Mỗi token mới đều tiêu hao một phần ngân sách đó, nên cần tuyển chọn token cẩn thận.

n²số cặp quan hệ giữa n token mà kiến trúc transformer phải xử lý (mỗi token "chú ý" tới mọi token khác)
1Mtoken – context window của Opus 5.5 / Sonnet 5.5 / Haiku 5.5 (Models overview, kiểm tra 2026-11-20)
1.000–2.000token – độ dài tóm tắt thường thấy mà một sub-agent trả về cho agent chính

Nguồn gốc kỹ thuật của giới hạn này:

  1. Kiến trúc transformer cho phép mỗi token chú ý tới mọi token khác, tạo ra n² cặp quan hệ với n token. Ngữ cảnh càng dài, khả năng nắm các quan hệ này càng bị "kéo mỏng".
  2. Dữ liệu huấn luyện: chuỗi ngắn phổ biến hơn chuỗi dài, nên model có ít kinh nghiệm hơn với phụ thuộc trải dài trên toàn ngữ cảnh.
Ví dụ đời thường

Bàn làm việc càng chất nhiều giấy tờ, bạn càng khó tìm đúng tờ cần thiết, dù bàn rộng đến đâu. Một chiếc bàn rộng (context window lớn) không thay được thói quen dọn bàn (context engineering).

Lỗi thường gặp

"Model có 1M token nên cứ đưa cả repo vào cho chắc." Anthropic nhấn mạnh rằng context window lớn hơn không tự giải quyết vấn đề ô nhiễm ngữ cảnh (context pollution) và độ liên quan. Ngữ cảnh ở mọi kích thước đều bị context rot; hãy coi ngữ cảnh là "precious, finite resource" (tài nguyên quý và hữu hạn).

System prompt ở "đúng độ cao" (right altitude)

Examples: "bức tranh đáng giá ngàn lời"

Anthropic vẫn khuyến nghị mạnh dùng few-shot examples, nhưng không nên nhồi một danh sách dài các edge case để cố liệt kê mọi quy tắc. Hãy tuyển chọn một bộ ví dụ đa dạng, tiêu biểu (canonical) mô tả hành vi mong muốn. Với LLM, "examples are the pictures worth a thousand words".

Mẹo thực chiến (Pro Tip)

System prompt phình lên vì liên tục thêm "nếu A thì làm B" cho từng bug ⇒ đó là dấu hiệu prompt đang ở độ cao quá thấp. Hãy gom lại thành nguyên tắc chung kèm 2–3 ví dụ tiêu biểu, rồi đo lại bằng eval (bài 15).

🔎Truy xuất ngữ cảnh: up-front, just-in-time và hybrid

Nhiều ứng dụng AI truyền thống dùng truy xuất dựa trên embedding (RAG, bài 20) trước khi suy luận để đưa ngữ cảnh quan trọng vào. Khi chuyển sang agent, ngày càng nhiều đội bổ sung chiến lược just-in-time context.

Just-in-time: giữ "con trỏ", không giữ dữ liệu

Thay vì nạp sẵn mọi dữ liệu, agent giữ các định danh nhẹ (lightweight identifiers): đường dẫn file, câu truy vấn đã lưu, link web… rồi dùng tool để nạp dữ liệu vào ngữ cảnh khi cần, lúc runtime.

Ví dụ của Anthropic: Claude Code phân tích dữ liệu phức tạp trên database lớn bằng cách viết truy vấn có mục tiêu, lưu kết quả, và dùng lệnh Bash như head, tail để xem dữ liệu, không bao giờ nạp nguyên đối tượng dữ liệu vào ngữ cảnh. Cách này giống con người: ta không học thuộc cả kho dữ liệu mà dùng hệ thống file, hộp thư, bookmark để tra cứu khi cần.

Progressive disclosure

Cho phép agent tự điều hướng và truy xuất dẫn tới progressive disclosure: agent khám phá ngữ cảnh từng bước. Kích thước file gợi ý độ phức tạp, tên file gợi ý mục đích, timestamp gợi ý mức độ liên quan. Agent chỉ giữ trong working memory những gì cần thiết.

📥Up-front (nạp trước)

  • Nhanh: dữ liệu đã sẵn trong ngữ cảnh.
  • Dễ dữ liệu cũ (stale), index phức tạp.
  • Tốn ngữ cảnh cho thông tin có thể không dùng tới.

🔎Just-in-time (truy xuất khi cần)

  • Ngữ cảnh gọn, dữ liệu luôn mới.
  • Chậm hơn tính toán trước.
  • Cần tool và heuristic tốt; nếu không agent dễ lãng phí ngữ cảnh vào ngõ cụt, dùng sai tool.

Chiến lược hybrid

Trong thực tế, cách hiệu quả nhất thường là kết hợp: nạp sẵn một số dữ liệu để có tốc độ, rồi để agent tự khám phá thêm. Claude Code là ví dụ: file CLAUDE.md được đưa vào ngữ cảnh ngay từ đầu, còn các công cụ như glob và grep cho phép điều hướng môi trường và truy xuất file just-in-time, tránh vấn đề index cũ và cây cú pháp phức tạp.

Theo Anthropic, hybrid có thể phù hợp với lĩnh vực ít biến động như pháp lý hay tài chính. Và khi model ngày càng giỏi, thiết kế agent sẽ để model tự hành động thông minh hơn, ít cần con người tuyển chọn sẵn. Lời khuyên chung: "do the simplest thing that works".

Mẹo thực chiến (Pro Tip)

Agent cần làm việc với một bảng log hàng triệu dòng ⇒ đừng trả cả bảng trong tool_result. Hãy cung cấp tool truy vấn có lọc/phân trang, hoặc lưu kết quả ra file và cho agent dùng head/grep trên file đó. Trong tool_result chỉ cần đường dẫn và số dòng.

⏳Ba kỹ thuật cho tác vụ dài hạn: compaction, note-taking, sub-agents

Tác vụ long-horizon (kéo dài hàng chục phút đến hàng giờ, như di chuyển một codebase lớn hay dự án nghiên cứu) đòi hỏi agent giữ được mạch lạc và hướng tới mục tiêu qua chuỗi hành động có tổng số token vượt context window. Anthropic không chờ context window lớn hơn mà đề xuất ba kỹ thuật.

1. Compaction – tóm tắt rồi bắt đầu lại

Compaction là lấy một cuộc hội thoại sắp chạm giới hạn context window, tóm tắt nội dung, rồi khởi tạo cửa sổ ngữ cảnh mới với bản tóm tắt đó. Đây thường là "đòn bẩy" đầu tiên để cải thiện mạch lạc dài hạn.

  • Trong Claude Code: lịch sử tin nhắn được đưa cho model để tóm tắt và nén các chi tiết quan trọng nhất. Model giữ lại quyết định kiến trúc, bug chưa giải quyết, chi tiết triển khai; bỏ đi output tool trùng lặp. Agent tiếp tục với bản tóm tắt cộng 5 file được truy cập gần nhất.
  • Nghệ thuật nằm ở việc chọn giữ gì, bỏ gì: nén quá tay sẽ làm mất chi tiết tinh tế mà tầm quan trọng chỉ lộ ra về sau.
  • Cách tinh chỉnh prompt tóm tắt: trước hết tối đa hóa recall (nắm đủ mọi thông tin liên quan) trên các trace agent phức tạp, sau đó lặp để tăng precision (loại bỏ phần thừa).
  • Tool result clearing: dạng compaction "nhẹ" và an toàn nhất. Một tool đã được gọi sâu trong lịch sử thì agent hiếm khi cần lại kết quả thô của nó.

2. Structured note-taking – agentic memory

Structured note-taking (còn gọi là agentic memory): agent thường xuyên viết ghi chú lưu bên ngoài context window, và đọc lại vào ngữ cảnh khi cần. Chi phí ngữ cảnh rất nhỏ mà vẫn có trí nhớ bền vững.

  • Ví dụ đơn giản: to-do list của Claude Code, hoặc agent tự duy trì file NOTES.md.
  • Claude chơi Pokémon: agent theo dõi chính xác số liệu qua hàng nghìn bước, ví dụ "trong 1.234 bước vừa qua tôi đã luyện Pokémon ở Route 1…". Không cần được nhắc về cấu trúc bộ nhớ, nó tự vẽ bản đồ các vùng đã khám phá, nhớ các thành tựu đã mở khóa, ghi lại chiến lược chiến đấu. Sau mỗi lần ngữ cảnh bị reset, nó đọc lại ghi chú và tiếp tục chuỗi chơi kéo dài nhiều giờ.
  • Memory tool: Anthropic phát hành ở dạng public beta cùng đợt ra mắt Sonnet 4.5 trên Claude Developer Platform; trang tài liệu hiện hành ghi trạng thái stable (kiểm tra ngày 2026-11-20). Chi tiết ở phần tiếp theo.

3. Sub-agent architectures – chia để trị

Thay vì một agent giữ trạng thái của cả dự án, các sub-agent chuyên biệt xử lý các tác vụ tập trung với context window sạch. Agent chính (lead agent) điều phối với kế hoạch cấp cao; mỗi sub-agent có thể khám phá sâu, dùng "hàng chục nghìn token hoặc hơn", nhưng chỉ trả về bản tóm tắt cô đọng, thường 1.000–2.000 token.

Lợi ích: tách bạch mối quan tâm. Ngữ cảnh tìm kiếm chi tiết nằm cô lập trong sub-agent, agent chính chỉ tập trung tổng hợp và phân tích. Anthropic cho biết mô hình này cải thiện đáng kể so với hệ thống một agent trên các tác vụ nghiên cứu phức tạp.

Lỗi thường gặp: quên tác động tới prompt caching

Tool result clearing làm mất hiệu lực phần prefix đã cache khi nội dung bị xóa. Nếu mỗi lần chỉ xóa vài trăm token, bạn trả phí ghi cache liên tục mà lợi chẳng bao nhiêu. Dùng clear_at_least để mỗi lần xóa đủ nhiều, xứng đáng với chi phí ghi cache mới (xem bài 25 về Prompt caching).

Memory tool: thư mục /memories do bạn kiểm soát

Memory tool hỗ trợ đúng tinh thần just-in-time: thay vì nạp mọi thứ từ đầu, agent ghi lại điều đã học vào file memory và đọc lại khi cần. Đây là client tool: Claude chỉ yêu cầu thao tác; ứng dụng của bạn thực thi trên kho lưu trữ của bạn (file, database, cloud storage…). Khi tool có mặt, API tự thêm vào system prompt chỉ dẫn yêu cầu Claude xem thư mục memory trước khi làm bất cứ điều gì và giả định ngữ cảnh có thể bị reset bất cứ lúc nào.

# Kiểm tra đường dẫn trong memory handler – chống path traversal
from pathlib import Path
from urllib.parse import unquote

BASE = Path("./memory_store").resolve()     # thư mục thật ánh xạ cho /memories

def resolve_memory_path(virtual_path: str) -> Path:
    p = unquote(virtual_path)                  # chặn cả dạng mã hóa %2e%2e%2f
    if p != "/memories" and not p.startswith("/memories/"):
        raise ValueError("Đường dẫn phải nằm trong /memories")
    rel = p[len("/memories"):].lstrip("/")
    real = (BASE / rel).resolve()              # chuẩn hóa về dạng canonical
    real.relative_to(BASE)                     # ném ValueError nếu thoát khỏi BASE
    return real

# resolve_memory_path("/memories/notes.md")          -> OK
# resolve_memory_path("/memories/../../secrets.env") -> ValueError
Bảo mật (IPA – Secure Programming)

Tài liệu Anthropic cảnh báo: đường dẫn độc hại như /memories/../../secrets.env có thể truy cập file ngoài thư mục memory. Mọi lệnh đều phải kiểm tra đường dẫn (bắt đầu bằng /memories, chuẩn hóa canonical, chặn ../ và dạng URL-encoded). Thêm vào đó: giới hạn kích thước file, xóa memory lâu không dùng, lọc thông tin nhạy cảm trước khi ghi. Điều này khớp với khuyến nghị chống directory traversal trong tài liệu IPA「安全なウェブサイトの作り方」. Lưu ý thêm: nội dung đọc từ file, web hay memory có thể chứa prompt injection; hãy coi đó là dữ liệu, không phải mệnh lệnh, và cấp cho agent quyền tối thiểu (least privilege).

Vòng lặp agent có điều kiện dừng

# Agent loop tối giản với stopping condition (Python)
import anthropic

client = anthropic.Anthropic()
MAX_TURNS = 20                         # điều kiện dừng: số vòng tối đa

def run_agent(task: str, tools: list, execute_tool) -> str:
    messages = [{"role": "user", "content": task}]
    for turn in range(MAX_TURNS):
        resp = client.messages.create(
            model="claude-sonnet-5-5", max_tokens=4096,
            tools=tools, messages=messages,
        )
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":      # Claude không gọi tool nữa => xong
            return "".join(b.text for b in resp.content if b.type == "text")
        results = []
        for block in resp.content:
            if block.type == "tool_use":
                out = execute_tool(block.name, block.input)   # ground truth từ môi trường
                results.append({"type": "tool_result",
                                "tool_use_id": block.id, "content": out})
        messages.append({"role": "user", "content": results})
    return "Dừng: đã chạm MAX_TURNS, cần con người xem xét"

🧪Thực hành

  1. Bài tập 1 – Agent có điều kiện dừng và kiểm chứng. Dùng đoạn code "Agent loop tối giản" ở trên, viết hai client tool: run_tests (chạy pytest -q trong một thư mục sandbox, trả về 30 dòng cuối) và read_file (chỉ đọc file trong thư mục sandbox, bắt buộc đường dẫn tuyệt đối). Giao nhiệm vụ "làm cho toàn bộ test pass".
    Kết quả mong đợi: Claude gọi run_tests trước, đọc file liên quan, đề xuất sửa, rồi gọi lại run_tests để xác nhận. Nếu vượt MAX_TURNS, hàm trả về thông báo cần con người xem xét. Không có lệnh nào chạy ngoài sandbox.
  2. Bài tập 2 – Đo tác dụng của tool result clearing. Tạo một hội thoại agent có khoảng 10 lần gọi tool trả về văn bản dài. Gọi endpoint đếm token (count_tokens) với cùng cấu hình context_management (trigger thấp, keep = 3) và beta header context-management-2025-06-27.
    Kết quả mong đợi: Phản hồi có cả input_tokens (sau khi chỉnh) và context_management.original_input_tokens (trước khi chỉnh); chênh lệch tương ứng với các kết quả tool cũ đã bị xóa. Khi gọi thật, đọc applied_edits để thấy cleared_tool_uses và cleared_input_tokens.
  3. Bài tập 3 – Memory tool đa phiên. Dùng BetaLocalFilesystemMemoryTool (Python SDK: from anthropic.tools import BetaLocalFilesystemMemoryTool) với client.beta.messages.tool_runner(...) và runner.until_done(). Phiên 1: "Hãy ghi nhớ rằng khách hàng Acme Corp thích nhận follow-up qua email". Kết thúc chương trình. Phiên 2 (chạy lại script, hội thoại mới): "Tôi nên liên hệ Acme Corp bằng kênh nào?".
    Kết quả mong đợi: Ở phiên 2, Claude gọi view /memories trước, đọc file đã tạo ở phiên 1 và trả lời "email". Sau đó viết hàm resolve_memory_path như trên và thử đường dẫn /memories/../x để xác nhận bị từ chối.
  4. Bài tập 4 – Viết lại system prompt ở "đúng độ cao". Lấy một system prompt có hơn 15 quy tắc "nếu… thì…" của chatbot nội bộ. Gom thành 3–4 phần có XML tag (<background_information>, <instructions>, <tool_guidance>), thay các quy tắc lẻ bằng nguyên tắc chung và 2–3 ví dụ tiêu biểu.
    Kết quả mong đợi: Prompt gọn hơn nhưng chạy bộ eval cũ (bài 15) cho điểm bằng hoặc cao hơn; ghi lại các ca thất bại để bổ sung chỉ dẫn có mục tiêu.

Key takeaways
  • Agent = LLM tự chủ dùng tool trong vòng lặp; mỗi bước phải lấy ground truth từ môi trường (kết quả tool, test, code execution) và có stopping condition.
  • Đầu tư vào ACI: tool rõ ràng, ít chồng chéo, chống sai (poka-yoke), ví dụ bắt buộc đường dẫn tuyệt đối.
  • Context engineering = tuyển chọn toàn bộ token vào model ở mỗi lượt; mục tiêu là tập token nhỏ nhất, giàu tín hiệu nhất.
  • Context rot: ngữ cảnh càng dài, khả năng nhớ lại chính xác càng giảm (n² quan hệ, attention budget hữu hạn). Context window lớn không thay thế được việc tuyển chọn.
  • System prompt ở "đúng độ cao"; tool tối thiểu và rõ ràng; vài ví dụ tiêu biểu thay vì danh sách edge case.
  • Just-in-time: giữ định danh nhẹ (đường dẫn, truy vấn) và nạp dữ liệu khi cần; hybrid như Claude Code (CLAUDE.md nạp sẵn + glob/grep).
  • Tác vụ dài: compaction (nhiều trao đổi qua lại), structured note-taking (mốc rõ ràng), sub-agents (nghiên cứu song song; trả về tóm tắt thường 1.000–2.000 token).
  • Trên API: context editing (clear_tool_uses_20250919, beta header context-management-2025-06-27), memory tool (memory_20250818, client-side, phải chống path traversal), server-side compaction (beta).

Thuật ngữ (Glossary)

Agent
Tác tử – hệ thống trong đó LLM tự điều khiển quy trình và việc dùng tool; theo Anthropic: "LLMs autonomously using tools in a loop".
Agent loop
Vòng lặp agent – chu trình chọn hành động → thực thi tool → nhận kết quả → quyết định tiếp.
Ground truth
Sự thật nền – thông tin thực từ môi trường (kết quả tool, test, code execution) để agent đánh giá tiến độ.
Environment inspection
Quan sát môi trường – việc agent chủ động kiểm tra trạng thái thực của môi trường thay vì suy đoán.
Stopping condition
Điều kiện dừng – vd số vòng lặp tối đa, giúp giữ quyền kiểm soát agent.
Agent-computer interface (ACI)
Giao diện agent – máy tính – cách tool được định nghĩa và trình bày cho agent; cần đầu tư như HCI.
Poka-yoke
Chống sai sót từ thiết kế – thiết kế tham số tool sao cho khó dùng sai.
Context engineering
Kỹ thuật quản lý ngữ cảnh – tuyển chọn và duy trì bộ token tối ưu đưa vào model lúc suy luận.
Context rot
Suy giảm chất lượng ngữ cảnh – khả năng nhớ lại chính xác giảm khi số token trong ngữ cảnh tăng.
Attention budget
Ngân sách chú ý – năng lực chú ý hữu hạn của LLM; mỗi token mới tiêu hao một phần.
Right altitude
Đúng độ cao – mức cụ thể vừa phải của system prompt, giữa hard-code if-else và chỉ dẫn mơ hồ.
Just-in-time context
Truy xuất ngữ cảnh đúng lúc – giữ định danh nhẹ và nạp dữ liệu bằng tool khi cần.
Progressive disclosure
Tiết lộ dần dần – agent khám phá ngữ cảnh từng bước, mỗi bước định hướng bước sau.
Compaction
Nén ngữ cảnh – tóm tắt hội thoại sắp chạm giới hạn và bắt đầu cửa sổ mới với bản tóm tắt.
Tool result clearing
Xóa kết quả tool – dạng compaction nhẹ nhất: thay kết quả tool cũ bằng placeholder.
Context editing
Chỉnh sửa ngữ cảnh – tính năng beta của Claude API tự xóa tool result / thinking block cũ phía server.
Structured note-taking / agentic memory
Ghi chú có cấu trúc / trí nhớ tác tử – agent ghi chú bền vững ngoài context window và đọc lại khi cần.
Memory tool
Công cụ bộ nhớ – client tool memory_20250818 thao tác file trong /memories.
Sub-agent
Agent con – agent chuyên biệt có context window sạch, trả về tóm tắt cô đọng cho lead agent.
Path traversal
Tấn công duyệt thư mục – dùng ../ để truy cập file ngoài thư mục cho phép.

Câu hỏi luyện tập

Một coding agent thường xuyên báo "đã sửa xong lỗi" nhưng khi kiểm tra thì test vẫn fail. Thay đổi nào giải quyết gốc rễ vấn đề tốt nhất?
  1. Thêm vào system prompt câu "Hãy chắc chắn trước khi báo xong" bằng chữ in hoa.
  2. Cung cấp tool chạy test và thiết kế để agent chạy lại test sau mỗi lần sửa, lấy kết quả làm ground truth trước khi kết luận.
  3. Chuyển sang model có context window lớn hơn.
  4. Giảm max_tokens để agent trả lời ngắn hơn.
Đáp án B. Anthropic nhấn mạnh agent phải lấy "ground truth" từ môi trường ở mỗi bước; coding agent hiệu quả vì lời giải kiểm chứng được bằng test tự động. A chỉ là lời nhắc, không cho agent bằng chứng thực. C không liên quan: vấn đề là thiếu xác minh, không phải thiếu ngữ cảnh. D chỉ cắt ngắn đầu ra, thậm chí có thể làm phản hồi bị dừng giữa chừng.
Agent dùng tool edit_file(path) và hay sửa nhầm file sau khi đã cd sang thư mục con. Theo kinh nghiệm SWE-bench của Anthropic, cách khắc phục nào nên ưu tiên?
  1. Thêm 10 ví dụ về đường dẫn tương đối vào system prompt.
  2. Cấm agent dùng lệnh cd bằng một câu trong prompt.
  3. Tăng số vòng lặp tối đa để agent có thời gian tự sửa.
  4. Đổi tool để bắt buộc đường dẫn tuyệt đối (poka-yoke).
Đáp án D. Trong SWE-bench, Anthropic đổi tool sang luôn yêu cầu đường dẫn tuyệt đối và model dùng "hoàn hảo"; đây là poka-yoke: làm cho lỗi khó xảy ra ngay từ thiết kế. A thêm token mà không loại bỏ nguyên nhân. B dựa vào việc model tuân thủ lời dặn, không chắc chắn. C chỉ cho phép lỗi lặp lại nhiều hơn, tốn chi phí.
Đồng nghiệp nói: "Model mới có context window 1M token, nên ta cứ nạp toàn bộ tài liệu nội bộ vào mọi request, khỏi cần RAG hay tuyển chọn." Theo bài viết context engineering của Anthropic, nhận xét nào đúng nhất?
  1. Không ổn: context rot khiến khả năng nhớ lại chính xác giảm khi ngữ cảnh dài ra; cần tìm tập token nhỏ nhất, giàu tín hiệu nhất.
  2. Ổn: chỉ cần ngữ cảnh chưa vượt context window thì chất lượng không đổi.
  3. Không ổn chỉ vì chi phí; về chất lượng thì ngữ cảnh dài luôn tốt hơn.
  4. Ổn, miễn là đặt tài liệu ở cuối prompt.
Đáp án A. Anthropic mô tả context rot: khi số token tăng, khả năng nhớ lại chính xác giảm, theo dạng gradient và ở mọi model. Ngữ cảnh là "tài nguyên quý và hữu hạn". B sai vì suy giảm xảy ra cả khi chưa chạm giới hạn. C sai vì ngữ cảnh dài không luôn tốt hơn về chất lượng. D: vị trí đặt tài liệu không loại bỏ context rot hay giới hạn attention budget.

Một nhóm đang viết memory handler cho memory tool. Những biện pháp nào là cần thiết theo tài liệu Anthropic? (Chọn 2)
  1. Kiểm tra mọi đường dẫn bắt đầu bằng /memories, chuẩn hóa về dạng canonical và đảm bảo vẫn nằm trong thư mục memory.
  2. Không cần kiểm tra vì Claude được huấn luyện để không gửi đường dẫn độc hại.
  3. Chặn chuỗi traversal như ../ và cả dạng URL-encoded như %2e%2e%2f.
  4. Gửi kèm API key trong tool_result để Claude tự xác thực thao tác.
  5. Cho phép delete trên chính thư mục /memories để dọn dẹp nhanh.
Đáp án A, C. Tài liệu memory tool yêu cầu ứng dụng kiểm tra mọi path để chống directory traversal: bắt đầu bằng /memories, resolve canonical, chặn ../ và dạng URL-encoded. B sai: đầu vào có thể bị ảnh hưởng bởi prompt injection; trách nhiệm kiểm tra thuộc về ứng dụng. D sai và nguy hiểm: không bao giờ đưa bí mật vào ngữ cảnh. E sai: tài liệu nói nên từ chối delete trên chính thư mục gốc memory.
Một agent nghiên cứu thị trường phải khảo sát 12 đối thủ, mỗi đối thủ cần đọc hàng chục trang web. Agent chính hay "lạc đề" vì ngữ cảnh đầy kết quả tìm kiếm thô. Kiến trúc nào phù hợp nhất?
  1. Một agent duy nhất, tăng max_tokens lên tối đa.
  2. Nạp sẵn toàn bộ 12 website vào system prompt.
  3. Chỉ dùng compaction sau mỗi lượt.
  4. Sub-agent architecture: mỗi sub-agent khảo sát một đối thủ trong context sạch, trả về tóm tắt cô đọng cho lead agent tổng hợp.
Đáp án D. Anthropic khuyến nghị sub-agent cho nghiên cứu phức tạp có lợi khi khám phá song song: sub-agent có thể dùng hàng chục nghìn token nhưng chỉ trả về tóm tắt thường 1.000–2.000 token. A: max_tokens giới hạn đầu ra, không giải quyết ô nhiễm ngữ cảnh đầu vào. B làm context rot trầm trọng hơn. C giúp phần nào nhưng compaction phù hợp nhất cho trao đổi qua lại nhiều; nén liên tục dễ mất chi tiết quan trọng.
Theo Anthropic, Claude Code dùng chiến lược truy xuất ngữ cảnh nào?
  1. Chỉ dùng vector database để nạp sẵn mọi file liên quan trước khi suy luận.
  2. Hybrid: file CLAUDE.md được nạp sẵn, còn glob và grep dùng để truy xuất file just-in-time.
  3. Nạp toàn bộ repository vào ngữ cảnh ở đầu mỗi phiên.
  4. Không bao giờ nạp gì trước; mọi thông tin đều hỏi lại người dùng.
Đáp án B. Bài viết mô tả Claude Code là ví dụ hybrid: CLAUDE.md được đưa vào ngữ cảnh ngay từ đầu, còn glob/grep cho phép điều hướng và truy xuất just-in-time, tránh index cũ. A sai: không dựa vào index embedding nạp sẵn. C trái nguyên tắc tập token nhỏ nhất. D sai vì có nạp sẵn CLAUDE.md, và agent tự khám phá bằng tool chứ không hỏi lại mọi thứ.
Những phát biểu nào đúng về compaction trong Claude Code theo bài viết context engineering? (Chọn 2)
  1. Compaction xóa toàn bộ lịch sử và bắt đầu lại hoàn toàn trống.
  2. Bản tóm tắt giữ lại quyết định kiến trúc, bug chưa giải quyết và chi tiết triển khai; bỏ đi output tool trùng lặp.
  3. Compaction chỉ chạy khi người dùng gõ lệnh thủ công, không bao giờ tự động.
  4. Nên tinh chỉnh prompt tóm tắt bằng cách tối đa precision trước, recall sau.
  5. Sau khi nén, agent tiếp tục với bản tóm tắt cộng 5 file được truy cập gần nhất.
Đáp án B, E. Bài viết nêu đúng hai điểm này. A sai: có bản tóm tắt và các file gần nhất đi kèm. C sai: bài viết mô tả việc tóm tắt khi hội thoại tiến gần giới hạn context window, không nói chỉ chạy thủ công. D ngược thứ tự: Anthropic khuyên tối đa recall trước, rồi mới cải thiện precision.
Nhóm của bạn bật tool result clearing và thấy hóa đơn tăng vì cache bị mất hiệu lực liên tục: mỗi lần server chỉ xóa vài trăm token. Nên điều chỉnh gì?
  1. Đặt clear_tool_inputs: true.
  2. Giảm trigger xuống thật thấp để xóa sớm hơn.
  3. Đặt clear_at_least để mỗi lần xóa phải loại bỏ đủ nhiều token, xứng đáng với chi phí ghi cache mới.
  4. Bỏ beta header context-management-2025-06-27 nhưng giữ tham số context_management.
Đáp án C. Tài liệu nói tool result clearing làm mất hiệu lực prefix đã cache, và khuyên dùng clear_at_least để mỗi lần xóa đủ token, đáng với chi phí ghi cache. A xóa thêm tham số tool call, không giải quyết tần suất mất cache. B làm việc xóa diễn ra thường hơn, tệ hơn. D: context editing là tính năng beta, cần header tương ứng.
Một agent lập trình làm việc qua nhiều phiên, mỗi phiên context window được làm mới. Mỗi phiên mới nó lại mất 20 phút đọc lại codebase để biết đã làm tới đâu. Giải pháp phù hợp nhất?
  1. Structured note-taking với memory tool: phiên đầu tạo progress log và checklist; phiên sau đọc log trước; cuối phiên cập nhật log.
  2. Tăng max_tokens để agent đọc nhanh hơn.
  3. Bật clear_thinking_20251015 để xóa thinking block cũ.
  4. Đưa toàn bộ lịch sử của mọi phiên trước vào system prompt.
Đáp án A. Tài liệu memory tool mô tả đúng mẫu "multisession software development": phiên khởi tạo tạo progress log và feature checklist; các phiên sau đọc chúng để khôi phục trạng thái; cuối phiên cập nhật. B: max_tokens giới hạn đầu ra, không làm việc đọc nhanh hơn. C quản lý thinking trong một hội thoại, không tạo trí nhớ giữa các phiên. D gây phình ngữ cảnh và context rot.
