📂Files API: upload một lần, dùng nhiều lần

Files API cung cấp cách tiếp cận "create-once, use-many-times": bạn upload tệp vào kho lưu trữ an toàn của Anthropic, nhận về một file_id duy nhất, rồi tham chiếu file_id đó trong các request tới /v1/messages. Tệp đặc biệt hữu ích khi làm việc với code execution tool: đưa dataset vào, rồi tải về biểu đồ mà Claude tạo ra.

Theo tài liệu hiện hành, Files API đã ra khỏi beta và không cần beta header nữa. Header cũ files-api-2025-04-14 vẫn hoạt động (trả về dạng response beta), nên việc migrate là tùy chọn.

500 MBkích thước tối đa mỗi tệp
1 TBtổng dung lượng mỗi organization
~500request/phút cho các API liên quan tới file
0 đupload, download, list, metadata, delete đều miễn phí

Bốn nhóm thao tác

  • Upload – POST /v1/files (multipart), nhận id dạng file_....
  • Reference – dùng file_id trong khối document, image hoặc container_upload.
  • Manage – list (GET /v1/files), lấy metadata (GET /v1/files/{file_id}), xóa (DELETE /v1/files/{file_id}).
  • Download – GET /v1/files/{file_id}/content, chỉ với tệp do skills hoặc code execution tool tạo ra.

Upload và tham chiếu tệp (Python SDK)

# Upload một PDF rồi hỏi Claude về nó – không cần beta header
import anthropic

client = anthropic.Anthropic()  # đọc ANTHROPIC_API_KEY từ biến môi trường, KHÔNG hard-code key

with open("report.pdf", "rb") as f:
    uploaded = client.files.upload(
        file=("report.pdf", f, "application/pdf"),
    )
file_id = uploaded.id          # ví dụ: "file_011CNha8iCJcU1wXNR6q4V8w"

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    messages=[{
        "role": "user",
        "content": [
            {"type": "text", "text": "Tóm tắt tài liệu này trong 5 gạch đầu dòng."},
            {"type": "document",
             "source": {"type": "file", "file_id": file_id}},
        ],
    }],
)
print(response.content[0].text)

Với .docx hoặc .xlsx (khối document không hỗ trợ), tài liệu khuyên chuyển sang văn bản thuần và đưa thẳng vào message; .docx có hình thì chuyển sang PDF để tận dụng khả năng đọc ảnh trong PDF. Vòng đời, hết hạn và phân trang

  • Tệp không sửa, không đổi tên được sau khi upload. Muốn đổi nội dung: upload tệp mới, xóa tệp cũ. Tệp đã xóa không khôi phục được.
  • Tệp tồn tại cho tới khi bạn gọi DELETE hoặc tới thời điểm expires_at. Đặt hạn bằng trường form expires_in_seconds khi upload: từ 3.600 (1 giờ) đến 7.776.000 (90 ngày); hạn chỉ đặt một lần, không đổi được.
  • Khi hết hạn: tải nội dung trả 404, request Messages tham chiếu tệp thất bại trước khi suy luận; metadata còn đọc được tối đa 30 ngày.
  • GET /v1/files phân trang: mặc định 20 tệp, tối đa 1.000 mỗi trang (limit), dùng con trỏ next_page → tham số page. Có thể kiểm tra tối đa 100 tệp cụ thể một lần bằng ids[].
  • Tên tệp dài 1–255 ký tự, không chứa < > : " | ? * \ / hoặc ký tự Unicode 0–31.

Lưu ý về dữ liệu

Files API không đủ điều kiện Zero Data Retention (ZDR): tệp được giữ cho tới khi bị xóa hoặc hết hạn. Nếu tổ chức bật Compliance API, các thao tác upload / download / delete được ghi vào Activity Feed (list và metadata thì không).

📦Message Batches API: xử lý hàng loạt, giảm 50% chi phí

Message Batches API cho phép gửi nhiều request Messages cùng lúc để xử lý asynchronous. Thay vì chờ từng response ngay lập tức, bạn nộp cả lô, rồi quay lại lấy kết quả. Tài liệu nêu: phần lớn batch xong trong dưới 1 giờ, chi phí giảm 50% và throughput tăng.

Phù hợp khi: dữ liệu lớn, không cần trả lời tức thì, muốn tối ưu chi phí – ví dụ đánh giá (eval) quy mô lớn, kiểm duyệt nội dung, phân tích/tóm tắt dataset, sinh mô tả sản phẩm hàng loạt.

100.000request tối đa / batch (hoặc 256 MB, cái nào tới trước)
24 giờquá hạn mà chưa xử lý xong thì request hết hạn (expired)
29 ngàykết quả còn tải được, tính từ created_at
50%giá chuẩn cho mọi usage (input, output, token đặc biệt)

Batch hoạt động thế nào

  1. Tạo batch – gửi danh sách requests, mỗi phần tử gồm custom_id duy nhất và params (đúng các tham số của Messages API).
  2. Xử lý bất đồng bộ – mỗi request được xử lý độc lập; processing_status ban đầu là in_progress.
  3. Polling – gọi retrieve định kỳ đến khi processing_status = ended (hoặc xem trong Console).
  4. Lấy kết quả – stream tệp .jsonl từ results_url, mỗi dòng một kết quả, ghép lại bằng custom_id.

Tạo batch (Python SDK)

# Phân loại cảm xúc 3 review sản phẩm trong một batch
import anthropic
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

client = anthropic.Anthropic()   # ANTHROPIC_API_KEY từ biến môi trường

reviews = {"review-001": "Giao hàng nhanh, đóng gói đẹp.",
           "review-002": "Sản phẩm lỗi, chưa được đổi trả.",
           "review-003": "Tạm ổn so với giá tiền."}

batch = client.messages.batches.create(
    requests=[
        Request(
            custom_id=rid,  # 1–64 ký tự: chữ, số, '-' và '_'
            params=MessageCreateParamsNonStreaming(
                model="claude-haiku-5-5",
                max_tokens=20,
                system="Chỉ trả lời một từ: positive, negative hoặc neutral.",
                messages=[{"role": "user", "content": text}],
            ),
        )
        for rid, text in reviews.items()
    ]
)
print(batch.id, batch.processing_status)   # msgbatch_..., in_progress

Polling và đọc kết quả

import time

while True:
    b = client.messages.batches.retrieve(batch.id)
    if b.processing_status == "ended":
        break
    time.sleep(60)   # poll mỗi phút là đủ – batch không phải API thời gian thực

# Stream tệp .jsonl, xử lý từng dòng để tiết kiệm bộ nhớ
for result in client.messages.batches.results(batch.id):
    outcome = result.result
    match outcome.type:
        case "succeeded":
            print(result.custom_id, outcome.message.content[0].text)
        case "errored":
            if outcome.error.error.type == "invalid_request_error":
                print("Sửa request rồi gửi lại:", result.custom_id)
            else:
                print("Lỗi server, có thể retry:", result.custom_id)
        case "expired" | "canceled":
            print("Chưa xử lý, gửi lại ở batch mới:", result.custom_id)
Result typeÝ nghĩaTính phí?
succeededThành công, kèm message kết quảCó (50% giá chuẩn)
erroredLỗi (request không hợp lệ hoặc lỗi server), không tạo messageKhông
canceledBạn hủy batch trước khi request được gửi tới modelKhông
expiredBatch chạm hạn 24 giờ trước khi request được xử lýKhông
Lỗi thường gặp – giả định thứ tự kết quả

Kết quả batch có thể trả về theo thứ tự bất kỳ, không khớp thứ tự lúc tạo. Luôn ghép kết quả với request bằng custom_id, không dùng chỉ số mảng. Ngoài ra, params của từng request chỉ được validate bất đồng bộ – lỗi chỉ lộ ra khi cả batch đã kết thúc. Hãy chạy thử một request bằng Messages API thường trước khi nộp batch lớn.

Giới hạn và những gì không batch được

  • Batch thuộc về một workspace; chỉ request trong cùng workspace (hoặc người có quyền trên Console) mới thấy batch và kết quả.
  • Rate limit áp dụng cho cả HTTP request tới Batches API lẫn số request đang chờ xử lý; dùng Batches API không ảnh hưởng rate limit của Messages API.
  • Do xử lý song song tốc độ cao, batch có thể vượt nhẹ spend limit đã cấu hình cho workspace.
  • Hầu hết tính năng đều batch được: vision, tool use (kể cả mọi server tool), system message, hội thoại nhiều lượt, extended thinking, đa số tính năng beta.
  • Không hỗ trợ trong batch (trả lỗi validation): stream: true, speed (Fast mode), fallbacks, và max_tokens: 0 (cache pre-warming). Mỗi request phải có max_tokens ≥ 1.
  • Batch đã nộp không sửa được; muốn thay đổi thì hủy (POST .../cancel, trạng thái chuyển canceling rồi ended, có thể có kết quả một phần) và nộp batch mới.
  • Xóa batch đã xử lý xong bằng DELETE /v1/messages/batches/{batch_id}; batch đang chạy phải hủy trước. Batch không đủ điều kiện ZDR (lưu tới 29 ngày).
  • Beta output-300k-2026-03-24 nâng trần max_tokens lên 300.000 cho batch với một số model (Opus 5.5, Sonnet 5.5, Haiku 5.5…) – chỉ có trên Batches API.

Kết hợp Batch với Prompt caching

Batches API hỗ trợ Prompt caching, và hai mức giảm giá cộng dồn. Tuy nhiên, vì request trong batch xử lý song song và không theo thứ tự, cache hit chỉ là best-effort: tài liệu ghi nhận tỉ lệ cache hit thường từ 30% đến 98% tùy mẫu traffic. Cache mặc định sống 5 phút, mà batch có thể chạy lâu hơn thế, nên tài liệu khuyên cân nhắc cache 1 giờ cho phần ngữ cảnh chung.

# Mọi request dùng chung một tài liệu dài → đánh dấu cache_control với TTL 1 giờ
shared_system = [
    {"type": "text", "text": "Bạn phân tích hợp đồng theo checklist pháp chế."},
    {"type": "text", "text": LONG_POLICY_TEXT,
     "cache_control": {"type": "ephemeral", "ttl": "1h"}},
]
requests = [
    Request(custom_id=f"contract-{i}",
            params=MessageCreateParamsNonStreaming(
                model="claude-sonnet-5-5", max_tokens=1024,
                system=shared_system,   # prefix giống hệt nhau giữa các request
                messages=[{"role": "user", "content": c}]))
    for i, c in enumerate(contracts)
]
batch = client.messages.batches.create(requests=requests)
Mẹo thực chiến (Pro Tip)

Chạy eval hàng nghìn test case mỗi đêm, kết quả cần trước 9 giờ sáng ⇒ Message Batches API (50%) + prompt caching 1 giờ cho system prompt chung. Nếu người dùng đang chờ trên giao diện chat ⇒ không dùng batch, vì batch có thể mất tới 24 giờ.

Mẹo thực chiến (Pro Tip)

Đặt custom_id có ý nghĩa (vd ticket-48213, eval-case-0042) và chia dataset rất lớn thành nhiều batch nhỏ hơn để dễ theo dõi, retry phần lỗi, và không bị kẹt toàn bộ khi một batch hết hạn.

Tài liệu hiện hành nói rõ: với đa số trường hợp, server-side compaction (phần sau) là chiến lược chính; context editing dành cho tình huống cần kiểm soát chi tiết thứ gì bị xóa.

Tham số của clear_thinking_20251015

  • keep mặc định {"type": "thinking_turns", "value": 1}: giữ thinking của N lượt gần nhất (N > 0); hoặc "all" để giữ toàn bộ (tối đa cache hit).
  • Nếu khai báo strategy mà không có keep ⇒ luôn là 1 lượt, kể cả với model mà mặc định (khi không khai báo strategy) là giữ hết thinking.
  • Một user message chỉ chứa tool_result vẫn thuộc lượt đang chạy; user message khác bắt đầu lượt mới.

Lỗi thường gặp – quên tác động tới prompt cache

Xóa tool result làm mất hiệu lực cache prefix từ điểm bị xóa: lần xóa đó phải trả phí cache write mới. Nếu ngưỡng quá thấp và mỗi lần chỉ xóa vài trăm token, bạn có thể tốn tiền hơn là tiết kiệm. Dùng clear_at_least để mỗi lần xóa đủ nhiều, bù lại chi phí phá cache.

Mẹo thực chiến (Pro Tip)

🗜️Compaction: tóm tắt hội thoại ngay trên server

Compaction thay các lượt cũ của hội thoại bằng một bản tóm tắt do Claude viết trên server, nên bạn không cần tự viết code tóm tắt. Nó giúp hội thoại dài hoặc agent chạy lâu nằm gọn trong context window, đồng thời giữ ngữ cảnh đang hoạt động nhỏ – vì chất lượng phản hồi giảm khi hội thoại phình to. Cả hai kiểu compaction đều đang beta.

Mẹo thực chiến (Pro Tip)

Chatbot hỗ trợ khách hàng có phiên rất dài, bạn không muốn tự viết logic tóm tắt ⇒ compaction. Đặt cache_control ở cuối system prompt để system prompt được cache riêng khỏi phần hội thoại, và có thể đặt cache_control lên chính khối compaction để cache bản tóm tắt.

Client-side compaction trong SDK (cũ)

SDK TypeScript và Ruby từng có compaction_control trong tool_runner (ngưỡng mặc định 100.000 token, tóm tắt bọc trong thẻ <summary>). Tùy chọn này đã deprecated; Anthropic khuyên dùng server-side compaction.

🧠Memory tool: ghi nhớ xuyên phiên

Memory tool cho phép Claude lưu và truy xuất thông tin qua nhiều cuộc hội thoại trong một thư mục tệp memory. Đây là cách làm just-in-time context retrieval: thay vì nạp mọi thứ từ đầu, agent ghi lại điều đã học và đọc lại khi cần, nhờ đó ngữ cảnh luôn tập trung vào việc hiện tại.

  • Là client tool: Claude chỉ yêu cầu thao tác tệp; ứng dụng của bạn thực thi trên kho lưu trữ bạn kiểm soát (thư mục theo user, database, cloud storage, tệp mã hóa…).
  • Khai báo: {"type": "memory_20250818", "name": "memory"} – name bắt buộc là memory, không cần input_schema, không cần beta header.
  • Lệnh: view, create, str_replace, insert, delete, rename – mọi đường dẫn bắt đầu bằng /memories.
  • Khi có memory tool, API tự thêm hướng dẫn vào system prompt: luôn xem thư mục memory trước khi làm việc và giả định có thể bị gián đoạn (context có thể bị reset bất cứ lúc nào).
  • SDK Python/TypeScript có sẵn BetaLocalFilesystemMemoryTool; Python/C# có lớp trừu tượng BetaAbstractMemoryTool để tự cài đặt backend.

Lỗi thường gặp – path traversal

Một đường dẫn độc hại như /memories/../../secrets.env có thể với tới tệp ngoài thư mục memory. Handler của bạn phải validate mọi đường dẫn trong mọi lệnh: bắt đầu bằng /memories, chuẩn hóa về dạng canonical rồi kiểm tra vẫn nằm trong thư mục (Python: pathlib.Path.resolve() + relative_to()), chặn ../, ..\ và dạng URL-encoded %2e%2e%2f. Đây chính là nhóm lỗi "Directory Traversal" trong IPA「安全なウェブサイトの作り方」. Ngoài ra: giới hạn kích thước tệp, xóa memory lâu không dùng, lọc dữ liệu nhạy cảm trước khi ghi, và từ chối delete/rename chính thư mục gốc /memories.

# Hàm kiểm tra đường dẫn an toàn cho memory handler tự viết
from pathlib import Path
from urllib.parse import unquote

BASE = Path("./memory_store/user_42").resolve()   # mỗi user một thư mục riêng

def safe_path(virtual: str) -> Path:
    virtual = unquote(virtual)                       # chặn %2e%2e%2f
    if not virtual.startswith("/memories"):
        raise ValueError("Path must start with /memories")
    rel = virtual[len("/memories"):].lstrip("/\\")
    real = (BASE / rel).resolve()
    real.relative_to(BASE)                           # ném ValueError nếu thoát khỏi BASE
    return real

🧮Tối ưu chi phí: ghép các mảnh lại với nhau

Ba nhóm tính năng trong bài đều tác động trực tiếp tới hóa đơn. Một cách tư duy đơn giản: chi phí ≈ số token × đơn giá. Files API và context management giảm số token (hoặc số lần gửi lại), Batch và caching giảm đơn giá.

  1. Không gửi lại nội dung thừa – upload tài liệu một lần bằng Files API (thao tác file miễn phí). Lưu ý: nội dung tệp vẫn tính là input token mỗi lần được tham chiếu trong Messages.
  2. Cache phần lặp lại – tài liệu/system prompt dùng chung ⇒ prompt caching.
  3. Gom việc không gấp – mọi tác vụ chấp nhận chờ ⇒ Batch (50%), cộng dồn với caching.
  4. Giữ context gọn – context editing/compaction giảm input token cho mỗi lượt của agent; nhớ cân nhắc chi phí phá cache (clear_at_least) và token của lượt compaction (usage.iterations).
  5. Chọn model phù hợp – tác vụ phân loại đơn giản trong batch ⇒ model nhỏ như Haiku.
Ví dụ tính nhanh

Theo bảng giá batch ở trên, 10.000 review × khoảng 200 input token = 2 triệu input token. Với Claude Haiku 5.5 (prompt ≤ 100.000 token) ở mức batch $0.05 / MTok, phần input khoảng $0.10; output 10.000 × 5 token = 50.000 token ≈ $0.0125. Cùng khối lượng gửi đồng bộ sẽ tốn gấp đôi. (Số token mỗi review là giả định minh họa; hãy dùng count_tokens để đo thực tế.)

📌Tóm tắt ghi nhớ

Key takeaways
  • Files API: upload một lần → file_id → dùng trong khối document / image / container_upload. 500 MB/tệp, 1 TB/organization, thao tác file miễn phí, nội dung tính như input token. Đã ra khỏi beta.
  • Tệp thuộc workspace, không thuộc user ⇒ không nhận file_id từ người dùng; multitenant ⇒ mỗi tenant một workspace. Chỉ tải về được tệp do skills/code execution tạo.
  • Message Batches API: ≤ 100.000 request hoặc 256 MB; đa số xong < 1 giờ, hết hạn sau 24 giờ; kết quả giữ 29 ngày; giảm 50%; kết quả không theo thứ tự ⇒ dùng custom_id.
  • Batch không hỗ trợ stream, speed, fallbacks, max_tokens: 0; errored/canceled/expired không tính phí; caching cộng dồn nhưng best-effort (30–98%), nên dùng cache 1 giờ.
  • Context editing (beta context-management-2025-06-27): clear_tool_uses_20250919 (mặc định trigger 100.000 token, keep 3) và clear_thinking_20251015 (đặt trước). Chạy phía server, xem applied_edits; dùng clear_at_least để bù chi phí phá cache.
  • Compaction (beta): on-demand compact-2026-09-04 + "compaction": {"type": "summarize"}; theo ngưỡng compact-2026-01-12 + compact_20260112 (trigger mặc định 150.000, tối thiểu 50.000). Tính phí = tổng usage.iterations.
  • Memory tool memory_20250818: client tool, thư mục /memories, 6 lệnh; giữ kiến thức qua phiên; bắt buộc chống path traversal.

📖Thuật ngữ (Glossary)

Files API
API quản lý tệp – upload, liệt kê, lấy metadata, xóa và tải tệp; tham chiếu tệp bằng file_id.
file_id
Mã định danh tệp – chuỗi dạng file_... trả về khi upload, dùng trong source.type: "file".
container_upload
Khối tải tệp vào container – đưa tệp vào môi trường của code execution tool để phân tích.
Workspace
Không gian làm việc – ranh giới cô lập tệp, batch và API key trong một organization.
expires_in_seconds
Thời hạn tự hết hạn – trường form khi upload, 3.600–7.776.000 giây.
Message Batches API
API xử lý theo lô – gửi nhiều request Messages để xử lý bất đồng bộ với giá 50%.
Asynchronous processing
Xử lý bất đồng bộ – nộp việc rồi quay lại lấy kết quả, không chờ trực tiếp.
custom_id
Mã tự đặt của request – 1–64 ký tự [a-zA-Z0-9_-], dùng ghép kết quả với request.
processing_status
Trạng thái xử lý batch – in_progress, canceling, ended.
request_counts
Bộ đếm request – số request processing, succeeded, errored, canceled, expired.
results_url
Đường dẫn kết quả – tệp .jsonl chứa kết quả, có giá trị khi batch ended.
Context editing
Chỉnh sửa ngữ cảnh – server tự xóa tool result / thinking cũ theo quy tắc trước khi prompt tới model (beta).
applied_edits
Các chỉnh sửa đã áp dụng – trường trong context_management của response, cho biết đã xóa bao nhiêu token.
Compaction
Nén ngữ cảnh bằng tóm tắt – Claude viết tóm tắt thay cho các lượt cũ trên server (beta).
Compaction block
Khối tóm tắt – khối type: "compaction" phải gửi lại trong request sau.
Memory tool
Công cụ bộ nhớ – client tool memory_20250818 cho Claude đọc/ghi tệp trong /memories qua nhiều phiên.
Path traversal
Tấn công vượt thư mục – dùng ../ để truy cập tệp ngoài thư mục cho phép.
Best-effort
Cố gắng tối đa, không bảo đảm – cách cache hit hoạt động trong batch.
Throughput
Thông lượng – lượng request xử lý được trong một đơn vị thời gian.

📝Câu hỏi luyện tập

Một startup legal-tech cho phép người dùng hỏi nhiều câu về cùng một hợp đồng PDF 40 trang trong suốt một tuần. Hiện mỗi câu hỏi đều gửi lại PDF dạng base64. Cách nào giảm băng thông và đơn giản hóa code nhất?
  1. Chuyển sang Message Batches API để giảm 50% giá.
  2. Dùng memory tool để Claude tự lưu toàn bộ PDF vào /memories.
  3. Upload PDF một lần qua Files API, lưu file_id phía server rồi tham chiếu trong khối document ở mỗi request.
  4. Bật context editing với clear_tool_uses_20250919.
Đáp án C. Files API được thiết kế đúng cho "upload một lần, dùng nhiều lần" – không phải gửi lại nội dung. A sai: batch là bất đồng bộ (tới 24 giờ), không hợp hỏi đáp tương tác, và vẫn phải gửi PDF. B sai: memory tool lưu ghi chú do Claude viết, không phải cơ chế lưu trữ tài liệu gốc. D sai: context editing xóa tool result cũ, không liên quan tới việc gửi lại PDF.
Một SaaS nhiều khách hàng (tenant) dùng chung một workspace. API endpoint /ask nhận file_id từ trình duyệt rồi chuyển thẳng cho Claude. Rủi ro chính và cách khắc phục là gì?
  1. Người dùng có thể gửi file_id của tenant khác để đọc tài liệu của họ; nên giữ mapping user ↔ file phía server và tách mỗi tenant một workspace.
  2. Không có rủi ro vì file_id được mã hóa và gắn với từng end user.
  3. file_id hết hạn sau 5 phút nên request sẽ lỗi; cần upload lại liên tục.
  4. Rủi ro duy nhất là vượt 500 MB; nên nén tệp trước khi upload.
Đáp án A. Tài liệu cảnh báo tệp có phạm vi toàn workspace, không gắn với end user; nhận file_id từ người dùng cho phép đọc tệp của người khác. Khuyến nghị: coi file_id là tham chiếu phía server và tạo workspace riêng cho mỗi tenant. B sai: tệp không scoped theo user. C sai: tệp tồn tại tới khi xóa hoặc tới expires_at bạn đặt (tối thiểu 1 giờ). D sai: giới hạn kích thước không phải vấn đề bảo mật được hỏi.
Đọc đoạn response sau của Message Batches API. Kết luận nào đúng? 
{ "processing_status": "ended",
  "request_counts": { "processing": 0, "succeeded": 9500,
                      "errored": 120, "canceled": 0, "expired": 380 } }
  1. Bạn bị tính phí cho cả 10.000 request vì batch đã ended.
  2. 380 request expired sẽ tự được Anthropic chạy lại trong batch kế tiếp.
  3. Kết quả sẽ có trong file theo đúng thứ tự request khi tạo batch.
  4. Chỉ 9.500 request succeeded bị tính phí; 380 request đã chạm hạn 24 giờ trước khi được xử lý và cần gửi lại ở batch mới.
Đáp án D. Request errored, canceled, expired không bị tính phí; expired nghĩa là batch chạm hạn 24 giờ trước khi request được gửi tới model, bạn phải tự gửi lại. A sai vì ba loại kết quả không thành công không tính phí. B sai: không có cơ chế tự chạy lại. C sai: kết quả có thể theo thứ tự bất kỳ, phải ghép bằng custom_id.
Đội data muốn chạy 50.000 prompt đánh giá chất lượng mỗi đêm bằng Message Batches API. Những tham số/cấu hình nào sẽ khiến request trong batch bị lỗi validation? (Chọn 2)
  1. Bật extended thinking trong params.
  2. "stream": true.
  3. Dùng system prompt và hội thoại nhiều lượt.
  4. Thêm cache_control với "ttl": "1h".
  5. "max_tokens": 0 để pre-warm cache.
Đáp án B, E. Tài liệu liệt kê các tham số không hỗ trợ trong batch: stream: true, speed, fallbacks và max_tokens: 0. A sai: extended thinking batch được. C sai: system message và multi-turn đều được hỗ trợ. D sai: prompt caching được hỗ trợ và tài liệu còn khuyên dùng cache 1 giờ cho batch.
Một nền tảng thương mại điện tử cần sinh mô tả cho 80.000 sản phẩm mới, hạn chót sáng mai, ngân sách hạn chế. Mọi request dùng chung một system prompt dài về giọng văn thương hiệu. Giải pháp tối ưu chi phí nhất?
  1. Gọi Messages API đồng bộ với stream: true để nhanh hơn.
  2. Message Batches API, đặt cache_control (TTL 1 giờ) ở cuối system prompt chung; mỗi request một custom_id theo mã sản phẩm.
  3. Upload system prompt lên Files API rồi tham chiếu bằng file_id để không bị tính token.
  4. Bật compaction để giảm số token của system prompt.
Đáp án B. 80.000 request vừa trong giới hạn 100.000/batch; batch giảm 50%, cộng dồn với caching cho prefix chung; tài liệu khuyên cache 1 giờ vì batch có thể chạy lâu hơn 5 phút. A sai: giá chuẩn, không tiết kiệm. C sai: nội dung tệp vẫn tính như input token (và khối document không thay được system prompt). D sai: compaction tóm tắt hội thoại dài, không áp dụng cho request một lượt.
Đọc cấu hình sau. Điều gì xảy ra khi prompt của agent đạt 45.000 input token và đã có 10 lần gọi tool (trong đó 4 lần là web_search)? 
"context_management": { "edits": [ {
  "type": "clear_tool_uses_20250919",
  "trigger": {"type": "input_tokens", "value": 30000},
  "keep": {"type": "tool_uses", "value": 3},
  "exclude_tools": ["web_search"] } ] }
  1. Không có gì xảy ra vì ngưỡng mặc định là 100.000 token.
  2. Toàn bộ lịch sử hội thoại được thay bằng một bản tóm tắt.
  3. Các tool result cũ nhất (không phải web_search) bị thay bằng placeholder, giữ lại 3 tool use gần nhất; lịch sử phía client không đổi.
  4. Client phải tự xóa các tool_result cũ trong mảng messages trước khi gửi.
Đáp án C. trigger đặt 30.000 nên đã vượt; strategy xóa tool result cũ nhất trước, giữ keep = 3, không đụng tới tool trong exclude_tools; việc xóa áp dụng phía server. A sai: 100.000 chỉ là mặc định khi không đặt trigger. B sai: đó là compaction. D sai: context editing chạy server-side, client giữ nguyên lịch sử.
Sau khi bật compaction theo ngưỡng, kỹ sư FinOps thấy usage.input_tokens = 23.000 nhưng hóa đơn cao hơn dự kiến. Giải thích nào đúng?

  2. Compaction luôn tính giá gấp đôi so với Messages API.
  3. Hóa đơn sai; compaction là miễn phí giống Files API.
  4. Do compaction tự bật Message Batches API.
Đáp án A. Tài liệu nêu rõ top-level usage chỉ phản ánh các iteration không phải compaction; lượt tạo tóm tắt (vd 180.000 input) nằm trong usage.iterations. B sai: không có quy định "gấp đôi". C sai: lượt compaction tiêu thụ token thực sự; chỉ các thao tác của Files API là miễn phí. D sai: hai tính năng độc lập.
