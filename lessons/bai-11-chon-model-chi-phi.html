Sau bài này bạn sẽ

  • Chọn được model Claude phù hợp dựa trên ba tiêu chí năng lực – tốc độ – chi phí (cộng thêm tham số effort), và biết khi nào nên đi theo hướng "efficiency-first" hay "capability-first".
  • Hiểu cách tính tiền theo input / output tokens, các hệ số của prompt caching, Batch API, data residency, và tự ước tính được chi phí một ứng dụng.
  • Dùng endpoint /v1/messages/count_tokens để đếm token trước khi gửi request, và đọc được trường usage trong response.
  • Nắm cơ chế rate limits (RPM, ITPM, OTPM, token bucket, ramp limits), usage tiers, spend limits và cách xử lý lỗi 429.
  • Gọi Claude qua Amazon Bedrock và Google Cloud (Vertex AI / Agent Platform), biết khác biệt về model ID, xác thực, endpoint và tính năng.
Lưu ý về số liệu

Toàn bộ model ID, giá, giới hạn trong bài lấy từ tài liệu Anthropic (trang Models overview, Pricing, Rate limits, Token counting), theo tài liệu, kiểm tra ngày 2026-11-20. Những con số này thay đổi thường xuyên — trước khi lập ngân sách thật, hãy mở lại trang Pricing và Rate limits.

⚖️Ba tiêu chí khi chọn model

Theo hướng dẫn Choosing the right model của Anthropic, chọn model Claude là việc cân bằng giữa capabilities (năng lực), speed (tốc độ) và cost (chi phí). Không có model "tốt nhất cho mọi việc" — chỉ có model phù hợp nhất với bài toán và ngân sách của bạn.

  • Capabilities – năng lực: ứng dụng cần model làm được gì? Suy luận nhiều bước, viết code dài, agent chạy hàng giờ, hay chỉ phân loại một câu ngắn?
  • Speed – tốc độ: người dùng chờ được bao lâu? Chatbot thời gian thực cần độ trễ thấp; job chạy đêm thì không. Tài liệu nhắc thêm fast mode: tốc độ sinh output cao hơn tới 2.5 lần, với mức giá cao hơn (premium), trên các model được hỗ trợ.
  • Cost – chi phí: ngân sách cho cả giai đoạn phát triển lẫn vận hành production.
  • Effort: nhiều model hỗ trợ tham số effort để đổi giữa "độ thông minh" với độ trễ và chi phí ngay trong một model. Tài liệu nhấn mạnh: chỉnh effort thường là đòn bẩy tốt hơn đổi model.

Kết hợp nhiều model (multimodel)

Chiến lược đa model ghép một model rẻ với một model frontier để phần lớn token được tính theo giá thấp. Hai mẫu phổ biến được tài liệu nêu:

  • Executor + advisor: model rẻ làm việc chính, chỉ "hỏi ý kiến" model mạnh ở các quyết định khó.
  • Orchestrator + workers: model mạnh điều phối, giao phần việc khối lượng lớn cho các worker rẻ hơn (ví dụ Haiku 5.5 làm subagent).
Lỗi thường gặp
  • Chọn model theo cảm tính hay theo bảng xếp hạng chung, không có eval riêng ⇒ không biết đổi model có làm chất lượng giảm hay không.
  • Đổi model nhưng giữ nguyên ước tính token cũ. Từ Claude Opus 4.7, tokenizer mới sinh ra khoảng 30% token nhiều hơn cho cùng một đoạn văn bản ⇒ phải đếm lại.
  • Chuyển sang Opus 5.5 / Fable 5.2 mà không đọc mục Breaking changes — ví dụ khi code ép tool_choice kiểu any/tool, tắt thinking, hoặc dùng tool computer_20251124.

🔢Token: đơn vị tính tiền và tính giới hạn

Token là những mẩu văn bản mà model xử lý. Theo FAQ của trang Pricing, số token của cùng một đoạn văn bản phụ thuộc vào tokenizer của model, ngôn ngữ và loại nội dung. Mọi thứ — giá, context window, rate limit — đều đo bằng token.

  • Input tokens: tất cả những gì bạn gửi đi — system, lịch sử messages, định nghĩa tools, hình ảnh, PDF, các khối tool_result.
  • Output tokens: những gì Claude sinh ra — văn bản, khối tool_use, và thinking. Output luôn đắt hơn input (ở các model hiện hành, giá output gấp 5 lần input).

Đọc trường usage trong response

Mỗi response của Messages API có object usage. Khi dùng prompt caching, tổng input được chia làm ba phần — đây là kiến thức quan trọng cho cả tính tiền lẫn rate limit:

// Ví dụ usage của một request có dùng prompt caching
{
  "usage": {
    "input_tokens": 50,                  // token SAU breakpoint cache cuối cùng (chưa cache)
    "cache_creation_input_tokens": 0,     // token đang được GHI vào cache
    "cache_read_input_tokens": 200000,   // token ĐỌC từ cache (rẻ hơn nhiều)
    "output_tokens": 812
  }
}
// total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens
//                    = 200000 + 0 + 50 = 200050

Ví dụ trên lấy đúng tình huống trong tài liệu Rate limits: một tài liệu 200k token đã cache cộng câu hỏi 50 token ⇒ input_tokens chỉ là 50 dù tổng input là 200,050.

Các hệ số điều chỉnh giá

♻️

Prompt caching

Bộ nhớ đệm prompt

Ghi cache 5 phút = 1.25x giá input; ghi cache 1 giờ = 2x; đọc cache = 0.1x ở đa số model (0.05x với Opus 5.5 & Sonnet 5.5; 0.025x với Fable 5.2/5.1). Hòa vốn sau 1 lần đọc (5 phút) hoặc 2 lần đọc (1 giờ).

📦

Batch API

Xử lý theo lô, bất đồng bộ

Giảm 50% cả input lẫn output. Ví dụ Opus 5.5 batch: $2 / $10 MTok; Sonnet 5.5: $1 / $5; Haiku 5.5 (≤100k): $0.05 / $0.25.

🗺️

Data residency

Lưu trú dữ liệu

inference_geo: "us" ⇒ hệ số 1.1x trên mọi loại token (model từ Claude 4.6). "global" (mặc định) giữ giá chuẩn.

📏

Long context

Ngữ cảnh dài

Model từ Claude 4.6 (trừ Haiku 5.5) dùng trọn 1M token context ở giá chuẩn. Riêng Haiku 5.5: prompt > 100,000 token trả mức giá cao hơn.

🏎️

Fast mode

Chế độ nhanh

Tới 2.5x output token/giây, giá premium. Có trên Fable 5.2, Opus 5.5, Opus 5, Opus 4.8. Không dùng được với Batch API.

🌐

Server tools

Công cụ phía server

Tính thêm theo lượt dùng. Ví dụ web search: $10 / 1,000 lượt tìm + token của kết quả tìm kiếm. Lượt tìm lỗi không bị tính.

Các hệ số cộng dồn (stack) với nhau

Theo trang Pricing, hệ số prompt caching cộng dồn với chiết khấu Batch API và hệ số data residency; giá fast mode cũng nhân thêm hệ số caching và data residency. Riêng với Haiku 5.5, độ dài prompt (để xét ngưỡng 100,000 token) tính toàn bộ input, kể cả cache read và cache write — một request vượt ngưỡng sẽ trả giá cao dù một phần là cache hit.

# Hàm ước tính chi phí từ trường usage (Python) – bảng giá lấy từ trang Pricing, kiểm tra 2026-11-20
PRICE = {  # USD / MTok: (input, output, cache_write_5m, cache_read)
    "claude-opus-5-5":   (4.00, 20.00, 5.00, 0.20),
    "claude-sonnet-5-5": (2.00, 10.00, 2.50, 0.10),
    "claude-haiku-5-5":  (0.10, 0.50, 0.125, 0.01),  # chỉ đúng khi prompt ≤ 100,000 token
}

def estimate_cost(model: str, usage) -> float:
    p_in, p_out, p_cw, p_cr = PRICE[model]
    cost = (usage.input_tokens * p_in
            + (usage.cache_creation_input_tokens or 0) * p_cw
            + (usage.cache_read_input_tokens or 0) * p_cr
            + usage.output_tokens * p_out)
    return cost / 1_000_000
Lỗi thường gặp
  • Ước tính chi phí chỉ dựa vào giá input, quên rằng output đắt gấp 5 lần và thinking cũng tính là output.
  • Quên token của định nghĩa tools và tool use system prompt — với agent có hàng chục tool, phần này lặp lại ở mọi request.
  • Dùng Haiku 5.5 với prompt dài hơn 100,000 token mà vẫn tính theo giá $0.10/$0.50 ⇒ ngân sách sai tới 5 lần.
  • Hard-code bảng giá trong code mà không ghi ngày kiểm tra ⇒ báo cáo chi phí sai khi Anthropic đổi giá.

🧮Token counting API

Token counting cho phép biết số token của một message trước khi gửi cho Claude. Theo tài liệu, bạn dùng nó để: chủ động quản lý rate limit và chi phí; ra quyết định routing model; và tối ưu prompt về đúng độ dài mong muốn.

  • Endpoint: POST /v1/messages/count_tokens, nhận cùng cấu trúc input với Messages API: system, messages, tools, hình ảnh, PDF, thinking.
  • Response: chỉ một trường input_tokens.
  • Miễn phí, nhưng có giới hạn requests per minute theo usage tier, tách biệt với rate limit của việc tạo message.
  • Kết quả là ước tính; số thật khi tạo message có thể lệch một chút. Số đếm có thể gồm token Anthropic tự thêm để tối ưu hệ thống — bạn không bị tính tiền cho các token này.
  • Không dùng prompt caching: bạn có thể gửi cache_control nhưng caching chỉ xảy ra khi tạo message thật.
# Đếm token trước khi gửi (Python SDK)
import anthropic

client = anthropic.Anthropic()  # đọc ANTHROPIC_API_KEY từ biến môi trường, không hard-code key

response = client.messages.count_tokens(
    model="claude-opus-5-5",
    system="You are a scientist",
    messages=[{"role": "user", "content": "Hello, Claude"}],
)
print(response.json())   # { "input_tokens": 14 }

Với tool, tài liệu cho ví dụ một tool get_weather và câu hỏi về thời tiết San Francisco: kết quả là { "input_tokens": 403 } — lớn hơn nhiều so với bản thân câu hỏi, vì gồm cả schema của tool và tool use system prompt. Ví dụ có ảnh cho 1028 token, ví dụ PDF cho 2188 token.

🚦Rate limits, spend limits & usage tiers

Để chống lạm dụng và quản lý năng lực phục vụ, Claude API có hai loại giới hạn ở cấp organization:

  1. Spend limits – mức chi tối đa mỗi tháng cho API.
  2. Rate limits – số request (và token) tối đa trong một khoảng thời gian.

Giới hạn được định nghĩa theo usage tier. Tổ chức được xếp tier tự động dựa trên lịch sử sử dụng và tình trạng tài khoản, rồi lên tier cao hơn theo thời gian. Tổ chức mới có thể bắt đầu ở Evaluation tier với giới hạn thấp hơn mức chuẩn; giới hạn này tự tăng khi có thêm lịch sử. Xem tier hiện tại tại trang Rate limits trong Claude Console.

Token bucket – giới hạn được "rót lại" liên tục

API dùng thuật toán token bucket: năng lực được bổ sung liên tục tới mức tối đa, chứ không reset theo mốc cố định mỗi phút. Hệ quả: một đợt burst ngắn có thể vượt giới hạn và gây lỗi dù trung bình cả phút vẫn dưới mức.

Cache-aware ITPM: caching = tăng throughput

Ví dụ trong tài liệu: với giới hạn 2,000,000 ITPM và tỉ lệ cache hit 80%, bạn xử lý được thực tế 10,000,000 input token mỗi phút (2M chưa cache + 8M đọc từ cache), vì token đọc từ cache không tính vào ITPM. Theo dõi tỉ lệ cache hit trên trang Usage của Claude Console.

Ramp limits

Ramp limit giới hạn tốc độ tăng lượng token của tổ chức trên một model. Sau một cú tăng đột ngột (kể cả burst trong vài giây), request có thể bị 429 dù vẫn dưới ITPM/OTPM. Mỗi phút bạn được vượt đỉnh gần đây thêm một "step"; giới hạn dừng tăng khi chạm rate limit. Mã lỗi: error.details.error_code = ramp_limit_exceeded. Message Batches API không chịu ramp limit; token đọc từ cache không tính vào ramp limit.

  • Chờ ít nhất số giây trong header retry-after.
  • Giữ lưu lượng ở mức thành công, rồi tăng tối đa một step mỗi phút.
  • Job theo lịch/khối lượng lớn: khởi động chậm, rải đều request thay vì bắn tất cả cùng lúc.

# Đọc header rate limit và xử lý 429 (Python SDK)
import anthropic

client = anthropic.Anthropic(max_retries=5)  # SDK tự retry các lỗi có thể thử lại, ví dụ 429

try:
    raw = client.messages.with_raw_response.create(
        model="claude-sonnet-5-5",
        max_tokens=512,
        messages=[{"role": "user", "content": "Tóm tắt báo cáo tuần này"}],
    )
    print(raw.headers.get("anthropic-ratelimit-input-tokens-remaining"))
    msg = raw.parse()            # object Message bình thường
    print(msg.usage)
except anthropic.RateLimitError as e:
    body = e.body if isinstance(e.body, dict) else {}
    code = body.get("error", {}).get("details", {}).get("error_code")
    if code == "enforced_spend_limit_reached":
        # Hết spend cap của tier: retry vô ích – báo người vận hành / xin nâng tier
        alert_ops("Spend cap reached")
    else:
        # Rate limit hoặc ramp limit: chờ theo retry-after rồi giảm tốc
        wait = e.response.headers.get("retry-after")
        schedule_retry(seconds=float(wait) if wait else 30)

alert_ops và schedule_retry là hàm giả định của ứng dụng bạn.

Giới hạn theo workspace & xin nâng giới hạn

  • Có thể đặt spend limit và rate limit thấp hơn cho từng workspace để một dự án không "ăn" hết quota của cả tổ chức. Ví dụ trong tài liệu: tổ chức có 40,000 ITPM, giới hạn một workspace ở 30,000 ITPM.
  • Giới hạn toàn tổ chức luôn áp dụng, kể cả khi tổng giới hạn các workspace lớn hơn. Nếu không đặt, giới hạn workspace bằng giới hạn tổ chức.
  • Rate limit dùng chung cho mọi giá trị inference_geo ("us" và "global" cùng một pool).
  • Cần cao hơn: dùng nút Request tier increase trên trang Rate limits của Claude Console; vượt Scale thì liên hệ sales (Custom tier).
Lỗi thường gặp
  • Retry 429 ngay lập tức trong vòng lặp chặt ⇒ càng làm cạn bucket và kích hoạt ramp limit. Phải tôn trọng retry-after và dùng backoff.
  • Coi mọi 429 là "chờ một lát là được" — 429 do enforced_spend_limit_reached sẽ kéo dài tới đầu tháng sau.
  • Giảm max_tokens để "tiết kiệm OTPM" — vô ích, vì OTPM chỉ tính token thực sinh.
  • Job đêm bắn hàng nghìn request ngay giây đầu ⇒ ramp limit. Hãy rải đều, hoặc dùng Message Batches API (giới hạn riêng, ví dụ Start tier: 1,000 RPM, 200,000 batch request trong hàng đợi, 100,000 request mỗi batch).
Mẹo thực chiến (Pro Tip)

Ứng dụng RAG liên tục bị 429 vì ITPM, mỗi request gửi lại cùng một tài liệu dài ⇒ bật prompt caching cho phần tài liệu: token đọc từ cache không tính vào ITPM, vừa rẻ hơn vừa tăng throughput thực tế. Muốn tách quota giữa dev và prod ⇒ đặt giới hạn theo workspace.

  3. Bài tập 3 – Client chịu tải. Viết wrapper gọi Messages API: (a) log các header anthropic-ratelimit-*-remaining sau mỗi request; (b) khi gặp 429 thì đọc error.details.error_code: ramp_limit_exceeded hoặc rate limit ⇒ chờ theo retry-after và giảm tốc; enforced_spend_limit_reached ⇒ dừng hẳn và cảnh báo. Kết quả mong đợi: wrapper không bao giờ retry vô hạn, không nuốt lỗi spend cap, và in ra cảnh báo khi remaining dưới 10% giới hạn.
  4. Bài tập 4 – Một codebase, ba nền tảng. Viết hàm make_client() đọc biến môi trường CLAUDE_PLATFORM (api | bedrock | vertex) và trả về Anthropic(), AnthropicBedrockMantle(aws_region=...) hoặc AnthropicVertex(project_id=..., region="global"), kèm hàm model_id("opus") trả đúng ID cho từng nền tảng (claude-opus-5-5 / anthropic.claude-opus-5-5 / claude-opus-5-5). Kết quả mong đợi: cùng một lời gọi client.messages.create(...) chạy được trên cả ba nền tảng; code không chứa bất kỳ key nào; có kiểm tra để không gọi Batch API khi đang ở Bedrock/Vertex.

Tóm tắt ghi nhớ

Key takeaways
  • Chọn model = cân bằng capabilities – speed – cost; chỉnh effort thường là đòn bẩy tốt hơn đổi model. Đa số workload bắt đầu với Opus 5.5; cần rẻ/nhanh nhất ⇒ Haiku 5.5; cần năng lực cao nhất ⇒ Fable 5.2.
  • Hai chiến lược: efficiency-first (Haiku → nâng cấp khi cần) và capability-first (Opus → tối ưu xuống). Luôn quyết định bằng eval riêng.
  • Giá tính theo MTok, output đắt gấp 5 lần input. Cache write 1.25x (5 phút) / 2x (1 giờ), cache read 0.1x (0.05x với Opus/Sonnet 5.5). Batch API giảm 50%. inference_geo: "us" nhân 1.1x. Haiku 5.5 có mức giá cao hơn khi prompt > 100,000 token.
  • Tokenizer từ Claude Opus 4.7 sinh khoảng 30% token nhiều hơn ⇒ đếm lại bằng /v1/messages/count_tokens (miễn phí, là ước tính, không hỗ trợ server tools/MCP connector/URL source).
  • Rate limit đo bằng RPM, ITPM, OTPM theo usage tier, dùng token bucket. ITPM không tính cache read; OTPM không phụ thuộc max_tokens. Có thêm ramp limit cho tăng tải đột ngột.
  • 429 do spend cap (enforced_spend_limit_reached) không có retry-after và kéo dài tới đầu tháng sau; spend limit tự đặt trả 400.
  • Bedrock: model ID có tiền tố anthropic., client AnthropicBedrockMantle, regional +10%. Google Cloud: client AnthropicVertex với project_id + region, multi-region/regional +10%. Cả hai không có Message Batches API; quota và hóa đơn do nhà cung cấp cloud quản lý.

Thuật ngữ (Glossary)

Model selection
Chọn mô hình – cân bằng năng lực, tốc độ, chi phí để chọn model Claude cho một use case.
Efficiency-first / Capability-first
Ưu tiên hiệu quả / ưu tiên năng lực – bắt đầu từ model rẻ rồi nâng cấp, hoặc từ model mạnh rồi tối ưu xuống.
Effort
Mức nỗ lực – tham số đổi giữa độ thông minh với độ trễ và chi phí trong cùng một model (ví dụ medium, high, xhigh, max).
Model ID / snapshot
Mã định danh mô hình – chuỗi như claude-opus-5-5; mỗi ID là một snapshot cố định.
Input tokens / Output tokens
Token đầu vào / đầu ra – token bạn gửi đi và token Claude sinh ra; tính giá riêng.
MTok
Triệu token – đơn vị tính giá: "$4 / MTok" = $4 cho mỗi 1 triệu token.
Tokenizer
Bộ tách token – thành phần chia văn bản thành token; tokenizer từ Claude Opus 4.7 sinh khoảng 30% token nhiều hơn.
Token counting
Đếm token – endpoint /v1/messages/count_tokens ước tính số input token trước khi gửi.
Cache write / Cache read
Ghi / đọc bộ nhớ đệm – cache_creation_input_tokens và cache_read_input_tokens trong usage.
Batch API (Message Batches)
Xử lý theo lô – gửi nhiều request bất đồng bộ, giảm 50% giá input và output.
Data residency / inference_geo
Lưu trú dữ liệu – chọn nơi chạy inference; "us" nhân giá 1.1x.
Fast mode
Chế độ nhanh – tới 2.5x tốc độ output, giá premium, không dùng với Batch API.
Rate limits
Giới hạn tốc độ – số request/token tối đa mỗi phút ở cấp organization.
RPM / ITPM / OTPM
Request / input token / output token mỗi phút – ba loại rate limit của Messages API.
Usage tier
Hạng sử dụng – Start, Build, Scale, Custom (và Evaluation cho tổ chức mới); quyết định rate limit và spend cap.
Spend limit / spend cap
Giới hạn chi tiêu – mức chi tối đa mỗi tháng; cap theo tier hoặc limit do bạn tự đặt.
Token bucket
Thùng token – thuật toán rate limiting bổ sung năng lực liên tục tới mức trần.
Ramp limit
Giới hạn tăng tốc – giới hạn tốc độ tăng lưu lượng; lỗi ramp_limit_exceeded.
retry-after
Header thời gian chờ – số giây nên chờ trước khi gửi lại sau lỗi 429.
Workspace
Không gian làm việc – nhóm API key trong organization, có thể đặt giới hạn riêng thấp hơn.
Amazon Bedrock (bedrock-mantle)
Nền tảng AI của AWS – phục vụ Messages API trên hạ tầng AWS; model ID có tiền tố anthropic..
Google Vertex AI / Agent Platform
Nền tảng AI của Google Cloud – "Claude Models on Google Cloud (Google managed)", gọi qua AnthropicVertex.
Global / Regional endpoint
Endpoint toàn cầu / theo vùng – global định tuyến động không phụ phí; regional/multi-region cố định vùng, phụ phí 10%.

Câu hỏi luyện tập

Một công ty thương mại điện tử cần phân loại khoảng 2 triệu bình luận khách hàng mỗi ngày thành 5 nhãn cảm xúc. Yêu cầu: độ trễ thấp, chi phí càng thấp càng tốt, tác vụ đơn giản. Theo hướng dẫn chọn model của Anthropic, nên bắt đầu với model nào?
  1. Claude Fable 5.2, vì là model có năng lực cao nhất nên phân loại chính xác nhất.
  2. Claude Opus 5.5, vì tài liệu nói đa số workload bắt đầu với Opus 5.5.
  3. Claude Haiku 5.5 theo hướng efficiency-first, rồi chỉ nâng cấp nếu eval cho thấy thiếu năng lực.
  4. Claude Sonnet 4.6, vì model cũ luôn rẻ hơn model mới.
Đáp án C. Tác vụ khối lượng lớn, đơn giản, nhạy độ trễ và chi phí đúng là trường hợp tài liệu khuyên đi efficiency-first với Haiku 5.5 (model được mô tả "for high-volume, latency-sensitive tasks such as classification"). A sai: Fable 5.2 dành cho suy luận khó và agent dài hơi, giá $8/$40 là lãng phí. B sai: "đa số workload bắt đầu với Opus 5.5" là mặc định chung, nhưng ma trận chọn model chỉ rõ cần độ trễ và giá thấp nhất ⇒ Haiku 5.5. D sai: Sonnet 4.6 giá $3/$15, đắt hơn cả Sonnet 5.5 ($2/$10) và Haiku 5.5; model cũ không mặc nhiên rẻ hơn.
Một ứng dụng nhận được trường usage sau: 
{ "input_tokens": 50,
  "cache_creation_input_tokens": 0,
  "cache_read_input_tokens": 200000,
  "output_tokens": 600 }
Theo cơ chế cache-aware ITPM, request này tiêu tốn bao nhiêu token vào giới hạn ITPM?
  1. 50 token.
  2. 200,050 token.
  3. 200,650 token.
  4. 0 token, vì request có dùng cache nên được miễn ITPM.
Đáp án A. Chỉ input_tokens + cache_creation_input_tokens tính vào ITPM: 50 + 0 = 50. B sai: 200,050 là tổng input (cộng cả cache read), nhưng cache read không tính vào ITPM. C sai: còn cộng cả output token, vốn thuộc OTPM. D sai: phần token chưa cache (50) vẫn tính; chỉ phần đọc từ cache được loại ra.
Giữa tháng, toàn bộ request của một startup bỗng trả HTTP 429 với "error_code": "enforced_spend_limit_reached". Những phát biểu nào đúng? (Chọn 2)
  1. Chỉ cần chờ theo header retry-after vài chục giây rồi gửi lại là xong.
  2. Response này không có header retry-after; retry, kể cả retry tự động của SDK, đều thất bại cho tới khi quyền truy cập được khôi phục.
  3. Đây là lỗi do spend limit mà chính tổ chức tự đặt, nên mã HTTP đúng ra phải là 400.
  4. Nếu không làm gì, API tạm dừng tới 00:00 UTC ngày đầu tháng sau; lên tier cao hơn sẽ khôi phục truy cập sớm hơn.
  5. Giảm max_tokens của mọi request sẽ giải quyết lỗi ngay lập tức.
Đáp án B, D. Chạm spend cap của tier: lỗi 429 rate_limit_error với enforced_spend_limit_reached, không có retry-after, dừng tới 00:00 UTC đầu tháng sau, hoặc khôi phục khi lên tier cao hơn. A sai: spend-cap 429 không có retry-after và không tự hết sau vài giây. C sai: spend limit tự đặt mới trả 400 invalid_request_error; mã enforced_spend_limit_reached là cap của tier. E sai: vấn đề là ngân sách tháng đã cạn, không liên quan max_tokens.
Một developer gọi client.messages.count_tokens(...) cho request có khai báo web search tool (server tool) và nhận invalid_request_error. Cách xử lý đúng là gì?
  1. Thêm cache_control vào request để endpoint đếm được server tool.
  2. Đổi sang model Haiku 5.5 vì chỉ Haiku mới hỗ trợ đếm token có server tool.
  3. Gửi ảnh và tài liệu dạng URL thay vì base64 để giảm kích thước request.
  4. Endpoint đếm token không hỗ trợ server tools (trừ advisor tool); hãy đọc số token thật trong trường usage của response Messages API.
Đáp án D. Tài liệu nêu count_tokens trả invalid_request_error với server tools như web search, web fetch, code execution, tool search; với các request này hãy dùng usage của Messages API. A sai: count_tokens không dùng caching, và cache_control không liên quan đến hỗ trợ server tool. B sai: mọi active model đều hỗ trợ đếm token, giới hạn nằm ở loại input chứ không ở model. C sai và ngược: nguồn url/file cũng bị count_tokens từ chối; phải dùng base64.
Đoạn code sau chạy trên Amazon Bedrock nhưng báo lỗi model không hợp lệ: 
from anthropic import AnthropicBedrockMantle
client = AnthropicBedrockMantle(aws_region="us-east-1")
client.messages.create(model="claude-opus-5-5", max_tokens=1024,
    messages=[{"role": "user", "content": "Hello"}])
Cần sửa gì?
  1. Đổi sang client AnthropicVertex vì Bedrock không hỗ trợ Opus 5.5.
  2. Dùng model ID có tiền tố provider: anthropic.claude-opus-5-5.
  3. Thêm ngày snapshot: claude-opus-5-5-20261101.
  4. Thêm tham số anthropic_version vào body request.
Đáp án B. Trên Claude in Amazon Bedrock, model ID mang tiền tố anthropic., ví dụ anthropic.claude-opus-5-5. A sai: AnthropicVertex là client cho Google Cloud; Bedrock có Opus 5.5 (xem bảng Supported models). C sai: model từ thế hệ 4.6 dùng ID không ngày, và chuỗi ngày này là tự bịa. D sai: đặt anthropic_version trong body là đặc điểm của cURL tới Google Cloud, SDK Bedrock tự xử lý header.
Một job phân tích chạy qua Message Batches API với Claude Sonnet 5.5, tổng cộng 2 triệu input token và 1 triệu output token, không dùng cache. Theo bảng giá (Sonnet 5.5: $2 input / $10 output mỗi MTok, Batch giảm 50%), chi phí là bao nhiêu?
  1. $7
  2. $14
  3. $3.50
  4. $12
Đáp án A. Giá batch Sonnet 5.5 là $1 input / $5 output mỗi MTok: 2 × $1 + 1 × $5 = $7. B sai: $14 là giá thường (2 × $2 + 1 × $10), quên chiết khấu 50%. C sai: giảm hai lần (50% của $7). D sai: lấy 2 × $1 + 1 × $10, chỉ giảm giá input mà quên rằng Batch giảm cả output.
Một ngân hàng châu Âu dùng Claude Opus 5.5 trên Google Cloud (Google managed) và yêu cầu dữ liệu chỉ được xử lý trong EU. Cấu hình AnthropicVertex nào phù hợp?
  1. region="global", vì global endpoint không có phụ phí.
  2. region="europe-west1" (regional endpoint) để có data residency một region.
  3. region="eu" (multi-region endpoint), chấp nhận giá cao hơn 10% so với global.
  4. Thêm inference_geo: "eu" vào request và giữ region="global".
Đáp án C. Multi-region "eu" định tuyến trong các region EU, phụ phí 10%. A sai: global gửi tới bất kỳ region nào có capacity, không đáp ứng yêu cầu chỉ trong EU. B sai: regional endpoint trên Google Cloud chỉ phục vụ Claude Sonnet 4.6 trở về trước; model mới hơn phải dùng global hoặc multi-region. D sai: inference_geo là tham số data residency của Claude API (first-party); tài liệu Pricing chỉ nêu giá trị "us" và "global", còn Google Cloud chọn vị trí xử lý qua endpoint.
Một hệ thống RAG thường xuyên bị 429 vì vượt ITPM. Mỗi request gửi lại cùng một bộ tài liệu tham chiếu 150k token; một phần là job tổng hợp báo cáo chạy đêm, không cần kết quả ngay. Những biện pháp nào giúp giảm áp lực rate limit? (Chọn 2)
  1. Bật prompt caching cho bộ tài liệu tham chiếu, vì cache_read_input_tokens không tính vào ITPM.
  2. Giảm max_tokens xuống thấp để giảm mức tiêu thụ ITPM.
  3. Chuyển job báo cáo chạy đêm sang Message Batches API, vốn có rate limit riêng và không chịu ramp limit.
  4. Retry ngay lập tức mỗi khi gặp 429 để không mất thời gian chờ.
  5. Chuyển một nửa traffic sang inference_geo: "us" để dùng một pool rate limit khác.
Đáp án A, C. Cache read không tính vào ITPM (ví dụ trong tài liệu: 2M ITPM + 80% cache hit ⇒ xử lý được 10M token/phút); Message Batches API có giới hạn riêng, không bị ramp limit, lại rẻ hơn 50%. B sai: max_tokens không ảnh hưởng ITPM, và cũng không ảnh hưởng OTPM. D sai: retry ngay làm cạn bucket thêm và có thể kích hoạt ramp limit; phải tuân theo retry-after. E sai: rate limit dùng chung cho mọi giá trị inference_geo, và "us" còn làm giá tăng 1.1x.
Một nhóm đang dùng Claude Opus 5.5 ở effort mặc định cho trợ lý phân tích hợp đồng; chất lượng đạt yêu cầu nhưng chi phí và độ trễ hơi cao. Theo tài liệu "Choosing the right model", bước tiếp theo hợp lý nhất là gì?
  1. Chuyển ngay sang Haiku 5.5 vì rẻ hơn 40 lần ở giá input.
  2. Chuyển lên Fable 5.2 để chạy nhanh hơn.
  3. Bật inference_geo: "us" để giảm độ trễ.
  4. Thử hạ effort rồi chạy lại bộ eval; chỉ cân nhắc hạ model khi effort thấp hơn vẫn chưa đủ hiệu quả.
Đáp án D. Tài liệu nói tuning effort thường là đòn bẩy tốt hơn đổi model, và chiến lược capability-first gợi ý tăng hiệu quả bằng cách hạ effort hoặc hạ model theo thời gian, luôn kèm eval. A sai: đổi model mà không eval có thể làm giảm chất lượng; tài liệu nhấn mạnh benchmark trước khi đổi. B sai: Fable 5.2 đắt gấp đôi Opus 5.5 và có độ trễ "Moderate" như nhau. C sai: inference_geo: "us" là tùy chọn data residency, làm giá tăng 1.1x chứ không phải công cụ giảm độ trễ.
Một hệ thống đang chạy Claude Sonnet 4.5 có báo cáo ngân sách dựa trên số token đo được trong 6 tháng qua. Nhóm định chuyển sang Claude Haiku 5.5 và dùng lại các số token cũ để dự báo chi phí. Nhận định nào đúng?
  1. Dùng lại được, vì cùng một đoạn văn bản luôn có cùng số token trên mọi model Claude.
  2. Không nên: Claude 4.7 trở về sau dùng tokenizer mới, sinh khoảng 30% token nhiều hơn; cần đếm lại bằng count_tokens với model="claude-haiku-5-5".
  3. Dùng lại được, chỉ cần nhân với tỉ lệ giá giữa hai model.
  4. Không cần đếm, vì count_tokens chỉ hỗ trợ model đời cũ.
Đáp án B. Theo trang Token counting và Pricing, Claude 4.7 và các model sau dùng tokenizer mới, tạo khoảng 30% token nhiều hơn cho cùng văn bản; tài liệu khuyên đếm lại với model định dùng. A sai: số token phụ thuộc tokenizer của model. C sai: chỉ đổi giá mà bỏ qua chênh lệch số token thì dự báo vẫn lệch. D sai: mọi active model, kể cả claude-haiku-5-5, đều hỗ trợ token counting.
